📡 Fixed Reader Dashboard (va_fixed_reader.aspx)

The Fixed Reader Dashboard is the real-time health and activity monitoring console for all permanently-installed RFID readers at a facility. It answers three operational questions at a glance: are my readers online, are they detecting tags, and which locations are seeing the most traffic?

✅ Live data — no page reload required.
All data is fetched asynchronously via two API endpoints baked into the same page (?api=readers and ?api=readerstats). The page loads its shell instantly, then populates each panel with animated counters as data arrives. Clicking Refresh re-fetches both endpoints without reloading the page.

Intended Audience

RoleHow They Use This Page
Biomedical / IT Staff Primary users. Monitor reader online/offline status, identify hardware failures, and confirm readers are actively observing tags before and during inventory operations.
Supply / Logistics Supervisors Use tag observation counts and top-location trends to understand passive inventory activity between manual scans — e.g., confirming equipment moved through a fixed reader zone.
VISN / Program Analysts Use the Fixed vs. Mobile read breakdown to evaluate ROI on fixed reader infrastructure relative to handheld scanning effort.
iDash Administrators Use alongside Reader Config to validate that newly registered readers are reporting correctly after installation.
ⓘ Access Control
This page requires the rpt_fixed_reader tile permission. Users without it will not see the tile on the iDash hub and will be redirected if they navigate directly to the URL. Tile assignments are managed in User Management (va_user_management.aspx).

Page Sections

1.  KPI Summary Row

Four at-a-glance metric cards displayed across the top. Values animate in with an eased counter when they first load or when Refresh is clicked.

CardWhat It ShowsSource
Total Readers All readers registered in AssetWorx for the selected site. Sub-label shows total antenna count across all readers. AssetWorx REST API → reader list
Online Readers currently reporting status = "Up". Sub-label shows percentage of total. AssetWorx REST API → reader status
Offline Readers reporting any status other than "Up". Sub-label shows percentage of total. AssetWorx REST API → reader status
Antennas Total physical antenna ports connected across all readers. A single reader may have 2–8 antennas depending on model. AssetWorx REST API → reader list

2.  Reader Status Overview

A proportional segmented bar showing the online/offline ratio, with a legend repeating raw counts and percentages below it. Built purely from API response values — no SQL involved.

ⓘ What "Offline" means operationally
A reader shown as Offline has not successfully communicated with the AssetWorx server during its last expected check-in interval. This can mean a network failure, power loss, IP conflict, or firmware hang. Biomedical should investigate any reader offline for more than one check-in cycle. See Reader Configuration docs for IP address correction steps.

3.  Fixed Reader Tag Observations

Four time-windowed counters showing how many RFID tag observation events have been recorded by fixed readers for the selected site. Sourced from dbo.v_asset filtered by lastinventoried date, restricted to assets last read by a fixed reader device type.

4.  Inventory Reads by Device Type

A proportional segmented bar and legend breaking all inventory reads into three categories. Answers: what fraction of total inventory activity comes from fixed readers vs. handheld scanners?

SegmentColorMeaning
Fixed Reader■ GreenAssets whose last inventory event was written by a permanently-installed RFID reader (passive detection)

5.  Top Observed Locations — 30 Days

A ranked table of physical locations where the most RFID tag observations occurred in the rolling 30-day window. Location names come from dbo.location.name joined to dbo.v_asset.locationid. The count represents observation events, not unique assets — an asset passing a reader repeatedly counts each time.

Use this to identify high-traffic zones (receiving docks, corridors, ORs) and to confirm readers in those zones are contributing meaningful volume. A previously busy location dropping off the list may indicate a reader failure or physical relocation.

6.  Reader Inventory Table

A sortable, filterable table listing every registered fixed reader for the selected site. Primary lookup tool for Biomedical and IT staff troubleshooting a specific device.

ColumnDescription

Sorting and filtering operate entirely client-side on the already-loaded dataset — no server round-trip is required. Clearing a filter input restores all rows instantly.

Site Selector

The dropdown in the page header filters the Tag Observations, Device Type Breakdown, and Top Locations panels by facility (dbo.company). The KPI Row and Reader Inventory Table are populated from the AssetWorx REST API, which is scoped to the credentials in Site Config — the dropdown does not re-filter those panels.

ⓘ Multi-site users
Users assigned to more than one site see an "All My Sites" option. Single-site users have their site auto-selected and the dropdown may be hidden. Users with no site assignment will see "No sites assigned" and no SQL-panel data will load.

🚧 Developer Notes

Architecture Overview

va_fixed_reader.aspx is a hybrid ASP.NET Web Forms + client-side SPA. The code-behind (va_fixed_reader.aspx.cs) handles auth, site dropdown, and two JSON API endpoints. The UI panels are populated entirely by fetch() calls after DOMContentLoaded.

API Endpoints

QuerystringHandler MethodReturns
?api=readers HandleReadersApi() JSON: { summary: { totalReaders, online, offline, pctOnline, pctOffline, totalAntennas }, readers: [...] }
Proxies to the AssetWorx REST API using credentials stored in va_site_config. Server-side proxy is required — AssetWorx API has no CORS headers.
?api=readerstats&companyid=N HandleReaderStatsApi() JSON: { tagReads: { today, week, month, quarter }, topLocations: [...], deviceReads: { fixed, mobile, notRead, pctFixed, pctMobile, pctNotRead } }
Queries dbo.v_asset directly via SQL. Site-scoped by companyid parameter.

AssetWorx API Dependency

?api=readers requires a valid API base URL and credentials in Site Config (va_site_config.aspx). If missing, the KPI row, status bar, and reader table show an error. The SQL-powered panels (Tag Observations, Top Locations, Device Type) remain functional independently because they query the local database directly.

Auth & Authorization Chain

  1. Session["IsAdminAuthenticated"] check → redirect to index.aspx if false
  2. UserManager.CanAccessTile(role, tiles, "rpt_fixed_reader") → redirect to index.aspx?err=access if denied
  3. UserManager.GetAllowedCompanyIds(Session, ConnStr) → populates site dropdown; restricted users cannot traverse to unauthorized sites

Client-Side Data Flow

  1. DOMContentLoaded → loadAll()
  2. loadReaders() and loadTagStats() fire in parallel
  3. loadReaders() calls ?api=readers → populates KPI row, status bar, reader table
  4. loadTagStats() calls ?api=readerstats&companyid=N → populates tag windows, top locations, device breakdown
  5. Header Refresh button re-calls loadAll() — no page reload

Sorting & Filtering Internals

Reader data is stored in the module-scoped readerData JS array after the first load. sortTbl(th, colIdx) sorts this array in place and re-renders via renderReaderTable(). filterTbl(colIdx, val) creates a filtered copy without modifying readerData, so clearing a filter box restores all rows without a network call.

Adding a New KPI Card

  1. Add a <div class="glass kpi-card"> block to the .kpi-row container in the ASPX markup
  2. Return the new value inside the summary object from HandleReadersApi() or HandleReaderStatsApi()
  3. Call animVal('your-element-id', d.summary.yourField, 800) in the corresponding JS fetch handler

Known Limitations

  • The reader table is not paginated. Sites with more than ~200 readers should add client-side pagination to renderReaderTable().
  • ?api=readers adds server-side latency equal to the AssetWorx API round-trip. If AssetWorx is unreachable, reader panels fail while SQL panels succeed.
  • lastSeen is an ISO-8601 UTC string. formatDate() converts it using the browser's local timezone, not the server's.

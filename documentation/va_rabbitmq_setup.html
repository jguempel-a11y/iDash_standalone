🐇 RabbitMQ MQTT Broker — Installation & Configuration Guide

Complete setup guide for deploying RabbitMQ as the enterprise MQTT broker for iDash fixed reader tag observation routing. This replaces the defective iDash internal broker for fixed reader data while preserving the existing print notification system.

💡 Rationale
The vendor-embedded iDash MQTT broker does not currently route published messages to subscribers (see Problem Statement below). Rather than incur an additional expense to have the vendor address what is a defect in their shipped product, RabbitMQ — an industry-standard, VA-approved, open-source message broker — was deployed as a reliable, well-supported alternative for fixed reader tag observation routing.

🚨 Problem Statement: The iDash Broker Defect

The iDash web application (iDash.Web.exe) includes an internal MQTTnet-based broker that was sold as the MQTT infrastructure for both label printing and fixed reader tag observation routing. Extensive diagnostic testing confirmed:

  • CONNECT — works. Clients authenticate and receive CONNACK(0).
  • SUBSCRIBE — works. Subscribers receive SUBACK.
  • PUBLISH → subscriber delivery — BROKEN. Messages published to the broker are never routed to subscribers.

This was tested with 4+ credential sets, self-publish tests (publisher = subscriber on same client), and TCP packet analysis. The broker accepts everything but routes nothing. The dbo.mqttclient table in the iDash database contains explicit ACL columns (publishtopic, subscribetopic) proving this feature was designed and sold — it simply doesn't work.

⚠ Note: This routing capability was included in the original product scope. The vendor has been notified of the defect. Until a vendor-side fix is delivered, RabbitMQ provides a production-grade workaround that does not depend on the vendor’s internal broker for fixed reader traffic.

Windows Firewall Commands

Run in an elevated (Admin) PowerShell on the iDash server:

# Allow inbound MQTT from reader subnet (adjust -RemoteAddress for your network) New-NetFirewallRule ` -DisplayName "RabbitMQ MQTT (Port 1883)" ` -Direction Inbound ` -LocalPort 1883 ` -Protocol TCP ` -Action Allow ` -RemoteAddress 192.168.4.0/24 ` -Description "FX9600 fixed reader MQTT tag publish to RabbitMQ" # Verify the rule was created Get-NetFirewallRule -DisplayName "RabbitMQ MQTT*" | Format-Table DisplayName, Enabled, Direction, Action # Expected: Enabled=True, Direction=Inbound, Action=Allow # Optional: verify port is listening Get-NetTCPConnection -LocalPort 1883 -State Listen # Expected: LocalAddress=0.0.0.0, LocalPort=1883, State=Listen
⚠ Scope the rule: Use -RemoteAddress to limit access to only the reader subnet or specific reader IP(s). Do NOT leave it open to Any unless your network policy permits it. For multiple readers on different subnets, create separate rules or use a comma-separated list: -RemoteAddress 192.168.4.0/24, 10.1.2.0/24

6 iDash Code Changes

Four changes were made to AntennaLocationService.cs and one to Web.config.

6a. Web.config — Port Change

- <add key="AntennaService_MqttPort" value="8883" />
+ <add key="AntennaService_MqttPort" value="1883" />

6b. AntennaLocationService.cs — TLS/TCP Toggle

Added AntennaService_UseTls config option. Defaults to true for port 8883, false for port 1883. When false, uses plain NetworkStream instead of SslStream.

+ bool useTls = Setting("AntennaService_UseTls", port == 8883 ? "true" : "false") + .Equals("true", StringComparison.OrdinalIgnoreCase);

6c. AntennaLocationService.cs — SslStream → Stream

Changed all 7 MQTT helper method signatures from SslStream to Stream (the base class that both SslStream and NetworkStream implement). Also fixed Stream.Write(byte[]) calls to use the 3-parameter overload Write(byte[], offset, count).

- private static void SendMqttConnect(SslStream ssl, ...)
+ private static void SendMqttConnect(Stream ssl, ...)

Applied to: SendMqttConnect, ReadMqttConnAck, SendMqttSubscribe, SendMqttPingReq, ReadMqttSubAck, ReadMqttPacket, WriteMqttPacket

6d. AntennaLocationService.cs — hostName Parsing (camelCase)

FX9600 MQTT payloads use data.hostName (capital N), not data.hostname. Added hostName to both top-level and nested field lookups.

6e. AntennaLocationService.cs — Fuzzy Reader Name Matching

MQTT payload sends FX9600F78C85 (no underscore) but the database stores FX9600_F78C85 (with underscore). Added fuzzy matching that strips underscores/hyphens when the exact lookup fails.

6f. AntennaLocationService.cs — Format 4 Tag Parser

Added parser for the FX9600 single-tag MQTT format:

// FX9600 MQTT payload format (one tag per message): { "data": { "antenna": 2, "eventNum": 572, "format": "epc", "hostName": "FX9600F78C85", "idHex": "613ee13440ff", "peakRssi": -69, "reads": 2 }, "timestamp": "2026-08-31T13:19:40.143-0700", "type": "INVENTORY" }

🔧 Troubleshooting

Issue: RabbitMQ service won't start

  • Check Erlang version: Get-ChildItem "C:\Program Files\Erlang OTP" -Filter "erts-*"
  • ERTS 15.x = OTP 27 (correct). ERTS 17.x = OTP 29 (incompatible).
  • Clear stale database: Remove-Item "$env:APPDATA\RabbitMQ\db" -Recurse -Force
  • Check log: Get-Content "$env:APPDATA\RabbitMQ\log\rabbit@*.log" -Tail 20

Issue: rabbitmqctl says "unable to perform operation"

  • Erlang cookie mismatch. Service runs as SYSTEM, CLI runs as your user.
  • Fix: Copy-Item "C:\Windows\System32\config\systemprofile\.erlang.cookie" "$env:USERPROFILE\.erlang.cookie" -Force

Issue: {unknown_instruction, {line, ...}} in logs

  • Erlang version too new for RabbitMQ version.
  • RabbitMQ 4.3.5 requires Erlang 27.x. If you have OTP 28 or 29, downgrade to 27.3.4.

Issue: "Unknown reader: FX9600F78C85"

  • Reader physicalId in database doesn't match MQTT hostName exactly.
  • The fuzzy match (added in this deployment) handles underscore differences automatically.
  • If using a different reader, ensure dbo.reader.physicalId matches the data.hostName from the MQTT payload.

Issue: FX9600 won't connect to RabbitMQ

  • Verify protocol is TCP, not TLS.
  • Verify port is 1883.
  • Verify credentials match the user created in RabbitMQ.
  • Check Windows Firewall: New-NetFirewallRule -DisplayName "RabbitMQ MQTT" -Direction Inbound -LocalPort 1883 -Protocol TCP -Action Allow

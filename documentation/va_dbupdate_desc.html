va_dbupdate.sql - Security and Operations Documentation

Overview

The va_dbupdate.sql script is designed to securely and efficiently import VA asset data from a flat-file extract into the iDash SQL database.

⚠ Idempotent Execution (Safe for Multiple Runs)

This script is designed to be completely safe to run multiple times. If run repeatedly against the same data file, it will ONLY insert new assets and locations. It relies on robust existence checks (e.g., checking RFID Tag, Asset Name, and Company ID combinations) before inserting any records into the production tables, ensuring no duplicate entries are ever created.

Step-by-Step Execution Breakdown

Phase 1: Environment & Security Setup

  • 1. Permissions Adjustment: Grants the idashadmin service account sysadmin server-level privileges. This ensures the automated account has the elevated permissions required to perform bulk imports and database modifications.
  • 2. Global Session Settings: Configures execution settings (such as XACT_ABORT and NOCOUNT) to ensure that if any severe error occurs during execution, the entire transaction is rolled back safely without leaving partial data.
  • 3. Metrics Storage: Creates a temporary in-memory table (#ImportStats) to accurately track the number of new insertions, skipped records, and any errors encountered during the import run.

Phase 2: Staging Area Preparation

  • 4. Staging Tables Creation: Ensures the persistent staging tables (dbo.locationtemp and dbo.assettemp) exist in the database. These tables hold the data temporarily while transformations are applied.
  • 5. Clear Previous Staging Data: Purges any residual data left over in dbo.locationtemp and dbo.assettemp from previous runs to ensure a clean slate.
  • 6. Raw File Landing Table: Drops and recreates a raw landing table (dbo.AssetFileRaw) tailored exactly to the column headers expected in the source data file.

Phase 3: Data Ingestion

  • 7. Bulk Insert (File Ingestion): Reads the contents of the target text file (C:\VA_RFID\VA On Network\allsitedata\ALLV5SITEdata.txt) directly into the dbo.AssetFileRaw landing table utilizing SQL Server's high-speed bulk import capability.
  • 8. Mapping Raw Data to Staging: Transfers the data from the raw landing table into dbo.assettemp. During this transfer, initial cleansing is performed: leading/trailing spaces are trimmed off text fields, random unique identifiers are generated if entry numbers are missing, and Service Pointer ('SP') prefixes are standardized.

Phase 4: Data Transformation & Normalization

  • 9. Compute Identifiers & Relationships:
    • Analyzes asset names to standardizes their formatting and generates a matching EPC (Electronic Product Code) rfidtag.
    • Determines the appropriate CompanyID (e.g., specific facilities like Clarksburg or Beckley) based on naming conventions and Station Codes.
    • Validates and standardizes date representations.
  • 10. Stage Unique Locations: Extracts a distinct list of facility locations from the asset data and places them into the dbo.locationtemp table.

Phase 5: Production Ingestion (Safe Inserts Only)

  • 11. Insert New Locations (Transaction Safe): Checks the existing dbo.location table. It safely inserts locations from staging only if they do not already exist for that specific company.
  • 12. Prepare Assets (Deduplication Check): Scans the locally staged assets and filters out duplicate records within the import file itself.
ℹ 13. Insert New Assets

This is the core idempotent step. The script joins the staged assets against the live dbo.asset table. It will only insert an asset if neither its Name (within its respective CompanyID) nor its rfidtag already exist in the database. Any pre-existing assets are safely ignored and skipped.

Phase 6: Integrity & Linking

  • 14. Clean Legacy Data: Runs a pass over all existing assets in the system to ensure legacy data complies with the "SP" prefix standardization for Service Pointers and validates that their CompanyID assignments match their Station format.
  • 15. Link Location IDs: Assigns the proper internal SQL database locationid to the newly inserted subset of assets based on their text-based location properties.
  • 16. System Helpers: Performs minor system maintenance, ensuring required Company records and standardized dropdown values (e.g., Asset Use Statuses like "IN USE" or "LOANED OUT") exist in the system tables.

Phase 7: Completion

  • 17. Final Report Checkout: Prints an operational summary to the SQL console outlining exactly what happened during the run, including the metric counts for new assets inserted and assets intentionally skipped. Cleans up remaining temporary tables.

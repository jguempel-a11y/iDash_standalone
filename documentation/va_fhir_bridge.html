Why This Exists

The Problem

iDash collects detailed asset and location data through RFID scanning, barcode capture, and manual inventory across VA medical centers. This data lives in the local iDash SQL Server database (dbo.asset, dbo.company) and is highly accurate because it represents physically observed equipment states — not just administrative records.

However, getting this data back into VistA (the VA's system of record) currently requires manual ENNX file generation, email submission, and human-driven import processes. This creates delays, introduces transcription errors, and makes real-time equipment visibility impossible.

The Solution

The FHIR Bridge provides a standards-based, automated pipeline from iDash to VistA using HL7 FHIR R4 — the same interoperability standard that the VA has adopted through its Lighthouse API platform. Instead of flat-text ENNX files, assets and locations become structured FHIR resources that can be validated, versioned, and transmitted over REST APIs.

Why FHIR and not a custom API?
The VA has invested heavily in FHIR as its primary interoperability standard. Using FHIR means: (1) the data format is standardized and can be validated by any FHIR-compliant tool, (2) the VA Lighthouse API already has the infrastructure to receive it, (3) no custom server-side code needs to be deployed on VA infrastructure, and (4) the same approach can be reused across any VISN or facility without site-specific modifications.

What This Is NOT

  • Not patient-facing: This module never creates, reads, or transmits patient data, clinical records, or any PHI/PII.
  • Not a replacement for ENNX: The ENNX workflow continues to work as-is. The FHIR Bridge is an additional export path using modern standards.
  • Not a VistA modification: No code runs on VistA servers. The FHIR Bridge runs entirely on the iDash web server and communicates through standard HTTPS REST APIs.
  • Not a database migration: iDash SQL remains the source of truth. The FHIR Bridge reads from it and generates outbound payloads.

Data Flow (Step by Step)

1
Asset Selection — Operator selects a site (company) from the dropdown. The code-behind queries dbo.asset joined with dbo.company to load the latest 200 assets for that station. Operator checks individual rows to include in the export.
2
FHIR Mapping — Each selected asset row becomes a FHIR Device resource. Unique locations are deduplicated and become FHIR Location resources. The field mapping is deterministic and documented below.
3
Bundle Assembly — All resources are wrapped in a FHIR Bundle (type: transaction). Each entry includes a request block specifying the HTTP method (PUT) and target URL for idempotent upserts.
4
Preview & Export — The JSON is displayed in a preview textarea. Operator can copy to clipboard or download as a .json file. Both client-side (JavaScript) and server-side (C#) bundle builders exist for redundancy.
5
Transmission (Phase 2) — Once VA sandbox credentials are configured, the Bundle will be POSTed to the FHIR endpoint with a Bearer token obtained through the OAuth 2.0 Client Credentials Grant flow (JWT signed with the RSA private key).

🔑 RSA Key Generation

Why RSA Keys?

The VA Lighthouse FHIR API uses OAuth 2.0 Client Credentials Grant (CCG) for server-to-server authentication. Unlike user-facing OAuth (which uses browser redirects), CCG requires the client (iDash) to prove its identity by signing a JSON Web Token (JWT) with an RSA private key. The VA verifies the signature using the corresponding public key (which was registered during sandbox setup in JWK format).

How Keys Are Generated

The FHIR Bridge uses .NET RSACryptoServiceProvider (available in .NET Framework 4.8, which is what runs on the VA server) to generate a 2048-bit RSA key pair. This is mathematically equivalent to running: 

openssl genrsa -out private.pem 2048
openssl rsa -in private.pem -pubout -out public.pem

The advantage of using .NET crypto is that no OpenSSL installation is required on the VA server. The .NET runtime (already present for IIS/ASP.NET) handles all cryptographic operations. The reference for the OpenSSL equivalent is OpenSSL 3.0 RSA Notes.

Two Generation Methods

MethodHowWhen to UseOutput Format
Web UI Click “Generate RSA Key Pair” on the FHIR Bridge page (RSA Keys tab). Normal use. Keys are generated server-side via the code-behind. XML (RSA ToXmlString)
PowerShell powershell -ExecutionPolicy Bypass -File Generate-VA-RSA-Key.ps1 Scripted/automated deployments, or when IIS access is unavailable. PEM (PKCS#1 DER encoded)

Both methods produce the same JWK output (the format required by VA Lighthouse).

JWK Format Reference

{
  "kty": "RSA",
  "n":   "<base64url-encoded modulus (256 bytes for 2048-bit key)>",
  "e":   "AQAB",
  "kid": "<auto-generated key ID from SHA-256 of modulus>",
  "use": "sig",
  "alg": "RS256"
}

Field breakdown:

FieldValuePurpose
kty"RSA"Key type. Always RSA for VA CCG.
nBase64url-encodedRSA modulus. The “public number” of the key pair.
e"AQAB"RSA exponent. Always 65537 (standard).
kid16-char hashKey ID. Auto-generated from SHA-256 of the modulus. Used for key rotation.
use"sig"Key usage: signing (not encryption).
alg"RS256"Algorithm: RSA with SHA-256.
⚠ Security: The private.pem file must never leave the server. Do not commit it to source control. Do not email it. Do not copy it to shared drives. If compromised, regenerate the key pair immediately and re-register with VA Lighthouse.

Bundle Structure

All resources are wrapped in a FHIR Bundle with type: "transaction":

{
  "resourceType": "Bundle",
  "type": "transaction",
  "timestamp": "2026-07-07T18:30:00.000Z",
  "meta": { "source": "idash-fhir-bridge" },
  "entry": [
    {
      "fullUrl": "urn:uuid:location-SP-ROOM-101",
      "resource": { /* Location resource */ },
      "request": { "method": "PUT", "url": "Location/idash-loc-SP-ROOM-101" }
    },
    {
      "fullUrl": "urn:uuid:device-12345",
      "resource": { /* Device resource */ },
      "request": { "method": "PUT", "url": "Device/idash-12345" }
    }
    // ... more entries
  ]
}

Ordering: Location resources are placed first in the entry array, followed by Device resources. This ensures that when the transaction is processed, Location references in Device resources can be resolved.

Idempotency: All entries use PUT (not POST), with deterministic IDs (idash-{id}). This means re-sending the same bundle updates existing resources rather than creating duplicates.

🔒 OAuth 2.0 Client Credentials Grant Flow

Technical reference for how authentication works (Phase 2 implementation):

1. iDash builds a JWT assertion:
   Header:  { "alg": "RS256", "kid": "<from JWK>" }
   Payload: {
     "iss": "<client_id>",
     "sub": "<client_id>",
     "aud": "https://sandbox-api.va.gov/oauth2/token",
     "iat": <now>,
     "exp": <now + 300s>,
     "jti": "<unique UUID>"
   }

2. iDash signs the JWT with the RSA private key (RS256).

3. iDash POSTs to the token endpoint:
   POST /oauth2/token
   Content-Type: application/x-www-form-urlencoded

   grant_type=client_credentials
   &client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
   &client_assertion=<signed JWT>
   &scope=system/Device.read system/Device.write system/Location.read system/Location.write

4. VA Lighthouse verifies the JWT signature against the registered JWK.

5. VA returns an access token:
   { "access_token": "<bearer token>", "token_type": "bearer", "expires_in": 300 }

6. iDash uses the bearer token for FHIR API calls:
   POST /services/fhir/v0/r4
   Authorization: Bearer <access_token>
   Content-Type: application/fhir+json

   { /* FHIR Bundle */ }

This flow is identical to the pattern used by IdashApiClient.cs for the existing REST API (which also uses OAuth 2.0 with token caching and expiry checks via EnsureToken()). The FHIR CCG flow adds JWT signing as the authentication mechanism instead of client_secret.

Design Decisions & Rationale

Every architectural choice in this module was made deliberately. This section documents why each decision was made, so that future developers understand the reasoning before proposing changes.

1

Why .NET Crypto Instead of OpenSSL?

VA servers have strict software installation policies. Installing OpenSSL would require an additional ATO (Authority to Operate) review. .NET RSACryptoServiceProvider is already present on every Windows Server running IIS/.NET Framework. Same math, zero new dependencies.

2

Why JSON Config Instead of web.config?

Modifying web.config triggers an IIS application pool recycle, which destroys all active user sessions across the entire iDash portal. Storing FHIR config in config/fhir/fhir_config.json avoids this. This is the same pattern used by users.json, email_recipients.json, and printer_routing.json throughout iDash.

3

Why FHIR Device + Location (Not SupplyDelivery)?

Device is the correct FHIR resource for physical asset instances (serial-numbered equipment). SupplyDelivery is for consumable supply shipments. Location represents physical places where assets reside. These are the resources that VA Lighthouse explicitly supports. SupplyRequest may be added in Phase 3 for inventory movement tracking.

4

Why Phase 1 = JSON Generation Only?

The VA Lighthouse FHIR API is primarily read-only for most consumers. Write access requires explicit VA authorization. Building the FHIR Bundle generator first means: (1) the mapping can be validated immediately, (2) bundles can be downloaded and submitted through whatever channel VA approves, (3) no blocked progress while waiting for sandbox credentials. Direct API POST will be enabled in Phase 2 once CCG authentication is configured.

5

Why Both Client-Side and Server-Side Bundle Builders?

The client-side builder (JavaScript) provides instant preview without a server round-trip. The server-side builder (C#) is used for downloads and API transmission because it has direct SQL access and can handle parameterized queries. Both use the same mapping logic and produce identical output.

6

Why PUT Instead of POST for Bundle Entries?

PUT with deterministic resource IDs (idash-{id}) makes every bundle submission idempotent. Re-sending the same bundle updates existing resources instead of creating duplicates. This is critical for retry scenarios and scheduled automation.

7

Why Station-Scoped Asset Loading?

Assets are loaded per-station (matching the existing DdlCompany pattern used throughout iDash). This prevents cross-station data leakage and keeps payloads manageable. Each station's data should be pushed independently to maintain clear managingOrganization references in the FHIR Location resources.

🔒 Security Model

  • The FHIR Bridge page is protected by iDash session authentication (same as all other pages).
  • Access should be restricted to admin role users only (via tile access control: docs_arch).
  • The page manages cryptographic keys and external API credentials — non-admin users should not see it.

  • All VA Lighthouse API communication uses HTTPS (TLS 1.2+).

  • No inbound ports are opened. The FHIR Bridge is always the initiator.

📦 Developer Handoff

Everything a developer needs to understand, modify, or extend this module.

How to Add a New FHIR Resource Type

  1. Define the mapping from iDash SQL columns to FHIR resource properties (document it in the mapping table above).
  2. In va_fhir_bridge.aspx.cs: create a new method like BuildSupplyRequestResource(DataRow row) following the same pattern as BuildFhirBundleJson.
  3. In va_fhir_bridge.aspx (JavaScript): add the corresponding client-side resource builder in the generatePreview() function.
  4. Add the new resource entries to the Bundle's entry array in both builders.
  5. Update the data-attributes on the asset checkboxes if new SQL columns are needed.
  6. Update this documentation page with the new mapping table.

How to Implement Phase 2 (Direct API POST)

  1. Implement GenerateClientAssertion() in the code-behind: build a JWT with the header/payload described in the OAuth section, sign it with the RSA private key using RSAPKCS1SignatureFormatter.
  2. Implement AcquireToken(): POST the JWT to the token URL, parse the response for access_token and expires_in. Cache the token and check expiry (same pattern as IdashApiClient.EnsureToken()).
  3. Implement PushBundle(string bundleJson): POST the Bundle JSON to the FHIR base URL with Authorization: Bearer {token} and Content-Type: application/fhir+json.
  4. Add a “Push to VistA” button handler that calls AcquireToken then PushBundle.
  5. Log the response (status code, response body) to the transaction log.

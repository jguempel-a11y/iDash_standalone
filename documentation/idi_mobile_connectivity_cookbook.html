🏗️ System Architecture Overview

Understand what connects to what before touching any settings.

The iDash RFID asset tracking system consists of four major physical and logical layers that must all communicate correctly for scanning and printing to work.

LayerComponentRoleNetwork
Mobile Scanners Zebra TC53 + RFD40 RFID Sled Handheld asset scanning & label printing trigger WiFi — mobile1md
Application Server VA Windows Server (IIS + ASP.NET) Hosts iDash web client & iDash management portal VA server VLAN — static IP
Database Server VA SQL Server instance Stores all asset, location, print job, and user data VA data VLAN — port 1433
Label Printers IQ350 / Large Metal / Standard Small Physical RFID label printing via BarTender Hardwired Ethernet — static IP — port 9100
🔄 Data Flow Summary
Scan event: TC53 scanner → WiFi (mobile1md) → iDash server (HTTPS 443) → SQL Server (TCP 1433)
Print event: TC53 triggers print → iDash server queues print job in SQL → PowerShell spooler dequeues job → BarTender → label printer (TCP 9100)
Fixed reader: Zebra FX9600 → MQTT over TCP 1883 → iDash MQTT broker → SQL Server
iDash portal: Any workstation/browser → HTTPS 443 → iDash server

📱 Mobile Side

  • Zebra TC53 handheld (Android)
  • Zebra RFD40 RFID sled (Bluetooth to TC53)
  • iDash mobile app (browser-based over HTTPS)
  • WiFi: mobile1md SSID

🏠 Server Side

  • Windows Server — VA standard image
  • IIS hosting iDash.WebClient + iDash
  • BarTender Enterprise (Seagull Scientific)
  • PowerShell print spooler (always running)

📶 WiFi Coverage — Preferred, Not Mandatory
Both iDash mobile and the iDash scanning pages (VA Site Inventory, Tag Team Scan) support offline and batch mode. Scan data is queued locally on the device and synced to the server when connectivity is restored — so RFID tags scanned in a dead zone are not lost. WiFi coverage is still strongly recommended for real-time session status, live print triggering, and immediate sync. Run a site survey before deployment and address any significant coverage gaps, but an isolated dead zone will not cause data loss.

📱 Onboarding a Zebra TC53 Scanner

Step-by-step process to register and connect a new TC53 to the VA network.
⚙️ What You Need
  • Zebra TC53 handheld computer (fully charged)
  • Zebra RFD40 RFID sled (paired via Bluetooth)
  • OIT network ticket to register the MAC address on mobile1md
  • iDash server hostname or IP address
  • Confirmation that MAC has been registered (from OIT)

Step 1 — Collect the MAC Address

On the TC53, go to Settings → About phone → Status
Record the Wi-Fi MAC address (format: XX:XX:XX:XX:XX:XX)
Also record the Serial Number from the same screen for asset records
Label the physical device with its serial number using a permanent marker or label

Step 2 — Submit MAC to VA OIT for Network Registration

Open a standard VA OIT hardware approval ticket
Include: Device model (Zebra TC53), Serial Number, WiFi MAC, SSID (mobile1md), facility building, and assigned team
Wait for OIT confirmation that the MAC has been registered before attempting to connect

Step 3 — Configure WiFi on the TC53

Go to Settings → Network & Internet → Wi-Fi
Tap Add network and enter SSID: mobile1md
Set Security to WPA2-Enterprise (or as directed by OIT for this SSID)
Enter EAP credentials or select certificate per site-specific OIT instruction
Tap Connect — device should obtain a DHCP address and show “Connected”

Step 4 — Configure the iDash Server URL

Open the TC53 browser (Chrome recommended)
Navigate to: https://[idashServerHostname]/
Accept the VA SSL certificate if prompted (certificate must be VA-issued and trusted)
Bookmark or set as the browser homepage for the user
✅ Success Criteria: The TC53 connects to mobile1md with a valid IP, the iDash login screen loads over HTTPS, and scanning records appear in the iDash dashboard after a test scan. Note: scanning in offline / batch mode will queue records locally and sync when WiFi is restored — test both connected and reconnect scenarios.
R4

🔗 Connecting an RFD40 RFID Sled

Pair the Zebra RFD40 RFID sled to the TC53 via Bluetooth for RFID scanning capability.
ℹ️ How it Works
The RFD40 is a Bluetooth-connected RFID sled that snaps onto or is held alongside the TC53. The TC53 runs the iDash web app in its browser; the RFD40 sends scanned RFID EPC strings to the TC53 as keyboard/HID input, which the web app captures. No separate network registration is required for the RFD40 — only the TC53 needs to be on WiFi.
⚙️ What You Need
  • Zebra RFD40 RFID sled (charged)
  • TC53 with Bluetooth enabled
  • Zebra 123SCAN or Bluetooth settings on TC53
Power on the RFD40 by pressing and holding the power button until the LED flashes blue
On the TC53, go to Settings → Connected devices → Pair new device
Wait for the RFD40 to appear in the list (name: RFD40-XXXXXX)
Tap the RFD40 to pair — accept the pairing request on both devices if prompted
Open the Zebra 123SCAN app (or DataWedge) and confirm the RFD40 shows as connected
Configure the scan output profile to Keyboard Wedge / HID mode so scanned EPCs are sent as keystrokes to the active app
Open the iDash browser session and tap the scan input field — trigger a scan; the EPC should populate the field
⚠️ Bluetooth Range
The RFD40 operates on Bluetooth, not WiFi. Effective range is approximately 10 meters line-of-sight. Keep the TC53 holstered or in hand while scanning. If the Bluetooth connection drops, re-pair from the TC53 Bluetooth settings.
✅ Success Criteria: Triggering the RFD40 trigger button while the iDash scan field is active populates the EPC tag value automatically.

🔎 Verifying Scanner-to-Server Connectivity

Use these tests to confirm the TC53 can reach the iDash server before going live.

Test 1 — WiFi IP Address Check (on TC53)

On the TC53: Settings → Network & Internet → Wi-Fi → tap the connected SSID
Confirm the IP address is in the expected mobile1md DHCP range (provided by OIT)
Confirm DNS server addresses match VA DNS configuration

Test 2 — HTTPS Connectivity (on TC53)

Open Chrome on the TC53
Navigate to: https://[idashServerHostname]/
✅ Expected: iDash login screen loads without certificate warnings or connection errors
❌ If it times out: ACL or firewall is blocking port 443 from mobile1md VLAN to server VLAN
❌ If certificate error: VA SSL cert is not trusted on the device, or the cert has expired

Test 3 — Server-Side Connectivity Tests (from iDash server)

Run from an elevated PowerShell session on the iDash server:

# Test SQL Server connectivity
Test-NetConnection -ComputerName <SQLServerHostname> -Port 1433

# Test printer reachability (repeat for each printer IP)
Test-NetConnection -ComputerName <PrinterIP> -Port 9100

# Verify IIS is listening
netstat -ano | findstr :443
netstat -ano | findstr :80

# Confirm iDash app pool is running
Get-WebConfiguration system.applicationHost/applicationPools/add |
    Where-Object { $_.name -like '*iDash*' } | Select-Object name, state
✅ All Tests Pass When: SQL connection returns TcpTestSucceeded: True, all printer ports respond, IIS shows active listeners on 443/80, and the TC53 browser loads the login page cleanly.

🔁 VLAN Routing & Inter-Segment Traffic

Ensure routed connectivity between all three network segments.

The iDash deployment spans three distinct network segments that must be able to communicate. VA OIT Network team must configure inter-VLAN routing (Layer 3 switch or firewall) to permit the following flows:

Source VLANDestination VLANPort(s)Why Required
mobile1md (scanners) Server VLAN 443, 80 Scanners access iDash web app
Workstation VLAN Server VLAN 443, 80 Staff and admin access iDash portal
Server VLAN Database VLAN 1433 iDash server reads/writes SQL database
Server VLAN Printer VLAN (or same) 9100 BarTender sends print data to printers
Server VLAN VA SMTP relay 25 / 587 iDash automated report emails
ℹ️ Printer VLAN Note
Printers are typically placed on the same VLAN as the server or on a dedicated printer VLAN. Either configuration works as long as the server can reach each printer on port 9100. Printers do not need to reach the mobile VLAN or the database VLAN.

URL Format

🔒 SSL Certificate & HTTPS Configuration

Generate, bind, and deploy the VA SSL certificate for secure scanner connectivity. Includes TLS 1.3 fix and TC53 certificate installation.
⚙️ Requirements
  • VA-issued SSL certificate for the server’s FQDN (Fully Qualified Domain Name) — generated via the VA PKI certificate request process
  • IIS Manager access on the iDash server
  • DNS record for the FQDN pointing to the server’s static IP
  • Physical or remote access to each Zebra TC53 scanner

Part A — Generate the SSL Certificate via VA Process

Determine the server’s FQDN (e.g., VHABLTIDASH.v05.med.va.gov). This is the full DNS hostname that scanners will use to reach the server.
Submit a VA PKI certificate request through the standard VA process (typically via the VA Certificate Authority / PKI team). The Common Name (CN) and/or Subject Alternative Name (SAN) on the certificate must exactly match the server’s FQDN.
Once issued, download the certificate file (typically .pfx or .cer format) from the VA PKI system.
Import the certificate into the Windows Certificate Store on the iDash server: open MMC → Certificates (Local Computer) → Personal → Certificates → right-click → All Tasks → Import.
ℹ️ Why FQDN Matters
The SSL certificate must be issued to the server’s FQDN, not just a short hostname or IP address. Mobile scanners (TC53) resolve the server via DNS and will reject the connection if the certificate CN/SAN does not match the URL they are connecting to. Using an IP address or a mismatched hostname will cause “Your connection is not private” errors on the scanner.

Part B — Bind Certificate in IIS & Disable TLS 1.3

Open IIS Manager on the iDash server.
In the left panel, expand the server name → Sites → select the iDash website.
Click Bindings... in the right-hand Actions panel.
If an HTTPS binding on port 443 already exists, select it and click Edit. Otherwise click Add and set Type: https, Port: 443.
In the SSL certificate dropdown, select the VA-issued certificate you imported in Part A.
CRITICAL — Disable TLS 1.3: In the binding dialog, locate the “Disable TLS 1.3” checkbox and check it (enable the disable). This is required because the Zebra TC53 Android browser has known compatibility issues with TLS 1.3 negotiation, causing connection failures or intermittent SSL errors.
Click OK to save the binding, then close the Bindings dialog.
Run iisreset from an elevated command prompt to apply the changes.
Verify from a workstation: Invoke-WebRequest https://[FQDN]/ -UseBasicParsing — should return HTTP 200 with no SSL errors.
⚠️ TLS 1.3 Must Be Disabled
If TLS 1.3 is left enabled on the IIS 443 binding, Zebra TC53 scanners running Android may experience intermittent or persistent SSL handshake failures. The scanners will display connection errors or refuse to load the page entirely. Always check the “Disable TLS 1.3” checkbox in the IIS site binding for port 443. TLS 1.2 remains fully secure and is the recommended protocol for VA mobile device connectivity.

Part C — Export Certificates from the Server (Both Levels)

The TC53 scanner needs to trust the entire certificate chain. You must export two certificates from the server:

#Certificate LevelWhat It Is
1 Root CA Certificate The top-level VA Certificate Authority that signs all intermediate CAs. This is the “trust anchor” for the entire chain.
2 Intermediate CA Certificate The subordinate CA that directly issued your server’s SSL certificate. Without this, the chain is broken and the TC53 will not trust the server cert.

How to Export Both Certificates

On the iDash server, open MMC (press Win + R, type mmc, press Enter).
Go to File → Add/Remove Snap-in → Certificates → Computer Account → Local Computer → Finish → OK.
Navigate to Personal → Certificates. Find and double-click the iDash SSL certificate (the one bound to IIS).
Go to the Certification Path tab. You will see the full chain, typically 2–3 levels:
• Top level = Root CA (e.g., VA Internal Root CA)
• Middle level = Intermediate CA (e.g., VA Internal Issuing CA)
• Bottom level = Your server certificate (the leaf cert)
Export the Root CA: Click the top-level entry in the chain → View Certificate → Details tab → Copy to File... → Next → Select DER encoded binary X.509 (.CER) → Save as VA_Root_CA.cer.
Export the Intermediate CA: Click the middle-level entry in the chain → View Certificate → Details tab → Copy to File... → Next → Select DER encoded binary X.509 (.CER) → Save as VA_Intermediate_CA.cer.
Copy both .cer files to a USB drive, shared network folder, or email them to the person configuring the TC53 scanners.

Part D — Install Both Certificates on Zebra TC53 Scanners

Both the Root CA and Intermediate CA certificates must be installed on every TC53 scanner that will connect to iDash

Transfer the two .cer files (VA_Root_CA.cer and VA_Intermediate_CA.cer) to the TC53 — via USB cable, email attachment, or file share download.
On the TC53, open Settings → Security → Encryption & credentials → Install a certificate.
Select CA certificate when prompted for certificate type.
Browse to and select VA_Root_CA.cer. Tap Install. Accept any confirmation prompt.
Repeat: Go to Install a certificate again. Select VA_Intermediate_CA.cer. Tap Install.
Open Chrome on the TC53 and navigate to: https://[ServerFQDN]/
Verify: The padlock icon should be green/locked with no certificate warnings. Tap the padlock to confirm the certificate chain shows the correct Root CA → Intermediate CA → server certificate.
⚠️ Both Certificates Are Required
If you only install the Root CA but skip the Intermediate CA (or vice versa), the TC53 will still show certificate errors. The Android certificate store requires the full chain to be explicitly trusted. Always install both levels.
✅ Certificate is Correctly Configured When: Chrome on TC53 shows a green padlock with no “Your connection is not private” warnings, the certificate details show the correct FQDN hostname and a VA issuer, and the TLS connection negotiates using TLS 1.2 (not 1.3).

🔄 Replacing or Adding a Scanner

Process for adding a new device or swapping a failed scanner without disrupting operations.
Power on the new/replacement TC53 and collect its WiFi MAC address (see Recipe R3, Step 1)
Submit an OIT ticket to register the new MAC on mobile1md
While waiting for OIT, configure the WiFi SSID on the device (it will fail to connect until the MAC is registered — this is expected)
Once OIT confirms MAC registration, connect to mobile1md and verify IP is assigned
Open the iDash URL in Chrome and bookmark it
Pair the RFD40 sled if applicable (see Recipe R4)
Update the device inventory spreadsheet with the new serial number, MAC, and assigned user
If replacing a failed unit: deregister the old MAC from OIT’s network access list to prevent orphaned registrations
ℹ️ No Software Installation Required
iDash runs as a web application in the Chrome browser. No software is installed on the scanner. A replacement unit is fully operational as soon as it has WiFi access and the URL is bookmarked.

🚫 Troubleshooting: Scanner Won’t Connect

Diagnose and resolve WiFi and HTTPS connectivity failures on TC53 scanners.
❌ TC53 connects to WiFi but can’t reach the iDash URL
Likely Cause: ACL blocking port 443 from mobile1md VLAN to server VLAN.
Fix: Contact OIT Network team. Verify ACL permits TCP 443 from the mobile1md VLAN range to the iDash server IP. Test: Test-NetConnection -ComputerName [ServerIP] -Port 443 from a device on the same VLAN.
❌ TC53 won’t join the mobile1md SSID at all
Likely Cause: Device MAC address not registered by OIT, or incorrect WiFi credentials/certificate.
Fix: Confirm OIT has registered the device’s WiFi MAC on the mobile1md SSID. Double-check MAC address from Settings → About → Status → Wi-Fi MAC address and resubmit to OIT if needed.
❌ Certificate error / “Your connection is not private” in Chrome
Likely Cause: VA root CA and/or intermediate CA not trusted on the TC53, SSL certificate has expired, or TLS 1.3 is still enabled on the IIS binding.
Fix (cert not trusted): Install both the VA Root CA and Intermediate CA certificates on the TC53 (see Recipe R10, Parts C & D).
Fix (cert expired): Contact VA PKI / OIT to renew the certificate and rebind in IIS.
Fix (TLS 1.3): Disable TLS 1.3 in the IIS 443 binding (see Recipe R10, Part B).
❌ Scanner loses WiFi mid-scan / enters a dead zone
Note: iDash mobile and iDash scanning pages (VA Site Inventory, Tag Team Scan) support offline / batch mode. Scan data queues locally and syncs when WiFi reconnects — records are not lost.
Best Practice: Let the scan complete, return to a coverage area, and pull down to sync. For persistent coverage gaps: run a site survey, enable 802.11r fast roaming, and set DHCP lease to 8+ hours. Print jobs require connectivity at time of print trigger (not buffered offline).
❌ iDash page loads but scan data doesn’t save
Likely Cause: SQL Server connectivity failure on the server side (port 1433 blocked, SQL service down, or wrong credentials).
Fix (on server): Test-NetConnection -ComputerName [SQLHost] -Port 1433. Check Windows Event Viewer for SQL connection errors. Verify web.config connection string credentials.

🚫 Troubleshooting: Print Jobs Not Printing

Diagnose print pipeline failures from scan trigger to physical label output.
❌ Print triggered on scanner but nothing comes out of the printer
Likely Cause: Print spooler PowerShell script is not running on the server.
Fix: On the iDash server, open Task Manager or check Task Scheduler. Confirm Run_Bypass_Spooler.ps1 is running. If not, start it in an elevated PowerShell window: C:\idash_prints\Run_Bypass_Spooler.ps1 or restart the scheduled task.
❌ All print jobs go to the wrong printer
Likely Cause A: Wrong printer_routing.json file is being read (multiple copies on server).
Likely Cause B: Printer name in JSON doesn’t match Windows printer name exactly.
Fix A: Get-ChildItem C:\ -Filter "printer_routing.json" -Recurse — find all copies and edit the one in the same folder as the running spooler script.
Fix B: Get-Printer | Select-Object Name and copy-paste the exact name into the JSON value.
❌ BarTender error: “The document could not be opened”
Likely Cause: The template.filename in the SQL database has an incorrect path, missing extension, or points to a file that doesn’t exist.
Fix: Run in SQL: SELECT id, name, filename, printmethod FROM template ORDER BY id;
Ensure filename is a full path with .btw extension (e.g., C:\idash_prints\AW_Std_Small.btw) and printmethod = Bartender.
Fix: UPDATE template SET filename = 'C:\idash_prints\AW_Std_Small.btw', printmethod = 'Bartender' WHERE id = 1;
❌ Printer is reachable but jobs queue without printing
Likely Cause: TCP port 9100 blocked between server and printer, or printer is offline/paused.
Fix: Test-NetConnection -ComputerName [PrinterIP] -Port 9100. If it fails, contact OIT Network to open port 9100 from the server VLAN to the printer. Also check the physical printer (paper, ribbon, power).
❌ All scans print the same template regardless of tag type
Likely Cause: template.name in SQL doesn’t match the tag type strings used by the mobile app, so all jobs fall back to template id=1.
Fix: Run SELECT TOP 10 id, recordid, templateid FROM printjob ORDER BY id DESC. If all rows show the same templateid, check SELECT id, name, filename FROM template and update name values to match the mobile app tag type strings exactly (e.g., IQ350, Small_Standard, Large_Metal).

🚫 Troubleshooting: iDash Web Errors

Resolve IIS and ASP.NET configuration errors on the server.
❌ HTTP Error 500.19 — Error Code 0x80070021
Cause: Configuration sections locked — ASP.NET 4.8 or ISAPI features not installed in Windows Features.
Fix: Enable in Windows Features: IIS → World Wide Web Services → Application Development Features → ASP.NET 4.8, .NET Extensibility 4.8, ISAPI Extensions, ISAPI Filters. Then run iisreset.
❌ HTTP Error 500.19 — 32-bit / 64-bit mismatch
Cause: Application Pool set to 32-bit while handler uses Framework64.
Fix: IIS Manager → Application Pools → select the iDash pool → Advanced Settings → set Enable 32-bit Applications = False.
❌ Raw web.config XML shown in browser instead of the app
Cause: The iDash folder has not been converted to an IIS Application.
Fix: IIS Manager → expand the site → right-click iDash folder → Convert to Application. Assign the iDash App Pool.
❌ “Cannot connect to the database” / iDash shows no data
Cause: SQL Server connectivity failure — wrong connection string, port 1433 blocked, or service account credentials.
Fix: From the server: sqlcmd -S [SQLHost] -U idashadmin -P [password] -d idash -Q "SELECT TOP 1 * FROM asset". If it fails, check port 1433 ACL and credentials in web.config.

📱 Universal Scanner Architecture & Security

Technical specification and security review for the universal_scan.aspx module and its supporting backend API (aw_scan_api.aspx). This document details the data flow, access controls, and threat mitigation strategies implemented for remote handheld scanning.

📋 1. Purpose & Use Case

The Universal Scanner module provides a responsive, hardware-agnostic web interface designed primarily for Zebra RFD40 handhelds utilizing DataWedge keyboard emulation. It enables warehouse staff and supply technicians to perform rapid, continuous "point-and-shoot" asset verification directly from the floor, without requiring native Android/iOS application deployments or direct database connectivity.

⚙ 2. Architecture & Data Flow

The system relies on a strict separation of concerns, ensuring the mobile device only handles rendering and input capture, while the server handles all database transactions securely.

ComponentTechnologyResponsibility
Frontend UI
universal_scan.aspx		 HTML/JS A lightweight client interface. It automatically traps and maintains focus on a hidden input field, capturing rapid keyboard-emulated hardware scans. It transmits the payload via asynchronous fetch() requests to prevent page reloads and UI blocking.
API Boundary
aw_scan_api.aspx		 C# .NET The internal REST-like endpoint. It receives the raw EPC or Barcode string from the frontend, validates the payload, executes the database query, and returns a formatted JSON response.
Database Layer
AssetWorx SQL		 T-SQL The central database holding the dbo.v_asset and dbo.asset tables. It processes the read-only lookup and returns the asset metadata.

🔒 3. Security & Threat Mitigation

Because these devices operate wirelessly on the floor, the scanning architecture implements several defensive layers to protect the central AssetWorx database.

SQL Injection Defense

  • Implementation: The backend API endpoint strictly utilizes parameterized queries via the C# SqlCommand object.
  • Impact: The user input (the scanned string) is bound as a safe SqlParameter and is never concatenated directly into the SQL command string. This completely neutralizes the risk of malicious barcode payloads attempting to execute arbitrary SQL commands.

Principle of Least Privilege

  • Implementation: The aw_scan_api.aspx endpoint is hardcoded to perform only tightly constrained SELECT TOP 1 read operations across a limited set of fields.
  • Impact: The API code contains exactly zero INSERT, UPDATE, or DELETE statements. Even if the API is intentionally triggered via external tools (like Postman), it is physically incapable of mutating or deleting database records.

No Direct Database Exposure

  • Implementation: The client device's browser communicates exclusively with the IIS Web Server over HTTP/HTTPS (Port 80/443).
  • Impact: Mobile devices never connect directly to the SQL Server (Port 1433). The IIS server acts as a secure intermediary layer. Raw database connection strings and credentials remain safely stored server-side in the web.config and are never transmitted to the client.

Inherited Authentication Context

  • Implementation: The system inherits the rigorous IIS Application Pool identity and Active Directory execution mechanisms already deployed on the host server.
  • Impact: Internal network boundary protections, SSL certificates, and domain-level access controls apply organically to the scanner endpoints without requiring separate authentication layers for the basic lookup functionality.

🔌 4. WebSerial API Security Model

As of 07/03/2026, four scanning modules (ENNX Live Scan, EIL Live Scan, Universal ENNX Creator, and VA Site Inventory) support connecting USB RFID readers and serial devices directly through the browser via the WebSerial API. This section documents the security characteristics of that integration.

Explicit User Consent Required

  • Implementation: The WebSerial API requires a user-initiated gesture (button click) to trigger the browser's native serial port picker dialog. JavaScript cannot silently open or enumerate serial ports.
  • Impact: No serial device is ever accessed without the user's explicit, per-session permission. Malicious scripts on the same page cannot hijack serial ports.

Non-Persistent Permissions

  • Implementation: Serial port permissions are not persisted across browser sessions. Each time the user revisits the page, they must re-select their serial port via the browser dialog.
  • Impact: Even if a workstation is shared, a previous user's serial port access does not carry over. This prevents unintended data capture from serial devices left connected.

HTTPS Enforcement

  • Implementation: The WebSerial API is only available on pages served over HTTPS (or localhost). The iDash scanning pages detect this at load time and display a "Not Available" message if the prerequisite is not met.
  • Impact: This enforces transport-layer encryption for all serial data flowing through the browser. On plain HTTP deployments, WebSerial is automatically disabled — keyboard/DataWedge scanning continues unaffected.

Browser Compatibility Boundary

  • Implementation: WebSerial is supported only in Chromium-based browsers (Chrome, Edge). Firefox, Safari, and other browsers do not implement the API.
  • Impact: All four scanning pages gracefully degrade: if navigator.serial is undefined, the WebSerial panel either hides or shows a clear "Not Available" notice. No errors are thrown, and all other scanning functionality operates normally.

Data Flow: Serial → Scan Pipeline

  • Implementation: Serial data is read as raw bytes, decoded as UTF-8, buffered until a newline delimiter is received, then passed into the same handleScan() (or __doPostBack) function used by keyboard input. No serial data bypasses the existing scan validation pipeline.
  • Impact: All existing security controls — EPC filtering, parameterized SQL, cross-site guards, format validation — apply identically to serial-sourced scans. WebSerial is an input method, not a bypass.

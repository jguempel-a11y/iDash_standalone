🔁 Field Server Sync — Technical Reference

The Field Server Sync pipeline pulls live asset data from a field VISN server into a central executive reporting database — automatically, nightly. A .bak file from the field server's iDash database is restored to a local staging-only database, and a cross-database merge then applies all changed and new asset rows to the live reporting database using the existing table structure.

✅ Deployment Status — Active — VISN5 Baltimore (512)
This pipeline is live and fully automated for VISN5 Baltimore. The field server at visn5baltimore uploads a nightly .bak to a shared OneDrive folder at 5:30 PM. The central iDash server pulls it down at 6:00 PM and places it in the watch folder — where iDash picks it up automatically. No manual steps required.
✅ iDash database — Zero Schema Changes
This process never modifies the iDash database schema in any way. No tables are created or dropped. No columns are added. No stored procedures, views, or indexes are altered. The merge reads and writes only data rows into the existing dbo.asset, dbo.location, and dbo.company tables that iDash already owns and manages. The iDash application continues to function identically before and after any sync.
🔁 What this is NOT
This is not a full database restore. It never replaces or wipes the central database. It is a selective, field-comparison merge that only applies data that is actually different between the field server and the central database. Existing records in the central database are preserved — the merge never overwrites a populated field with a blank value.

Why This Exists

The VA RFID asset tracking project deploys iDash field servers at individual VISN medical centers (e.g., Baltimore 512, Martinsburg 613, Beckley 517). Each field server has its own local iDash database with asset and location data specific to that site.

The problem: Executive leadership needs a single consolidated view of all assets across all VISN sites for reporting, KPI tracking, and tagging progress. But each field server is isolated — there's no built-in multi-site aggregation in iDash.

The solution: This sync pipeline pulls nightly backups from each field server into a central reporting database. The merge is non-destructive, additive, and fully automated. The result is a single idash database that contains assets from all VISN sites, enabling cross-site dashboards like Site Maps, Asset Statistics, and the executive KPI tiles on the iDash hub.

Two-Stage Process

StageWhat happensDatabase target
Stage 1 — Restore The .bak is restored to idash_staging using RESTORE DATABASE ... WITH REPLACE, MOVE. The staging database is completely overwritten each run — it is a scratch database and holds no permanent data. idash_staging
Stage 2 — Merge va_field_sync_merge.sql runs cross-database queries against idash_staging.dbo.asset and idash.dbo.asset. It syncs companies, locations, updates changed assets, and inserts new ones. idash (live)

2. Merge Logic — What Gets Updated and Why

The merge SQL compares actual field values between the staging and central databases to determine what has changed:

⚠ Critical Design Decision: Field Comparison, Not Timestamps
The field server's .bak export does not reliably set the lastmodified column — it is often NULL in the backup. An earlier version of this merge used WHERE s.lastmodified > m.lastmodified as the update condition, which caused zero rows to match even when thousands of assets had real data differences.

As of July 2026, the merge now compares the actual data fields (text6–20, description, rfidtag, listvalue1, lastinventoried) to detect changes. This correctly identifies all assets that differ between the field and central databases, regardless of timestamp state.
OperationConditionFields affected
Companies synced Station number prefix (first 3 chars of company name) in staging not matched in central New company row created in central
Locations synced Location name + company combo in staging not in central New location row inserted; company ID re-mapped by station prefix
Assets UPDATED Any tagging field differs: text6–20, description, rfidtag, listvalue1, or lastinventoried is newer All text, list, date, status, and descriptor fields — never overwrites a populated field with blank
Assets INSERTED Asset name + company not found in central, and no RFID tag collision Full asset row inserted; locationid re-linked by name after insert
Location IDs re-linked After all updates/inserts Auto-assigned IDs differ between servers — linked by location name after merge

Company ID Mapping

Field servers and the central database have different auto-increment IDs for companies. For example, "512 Baltimore" might be companyid = 2 on the field server but companyid = 6 on the central server. The merge maps between them using the first 3 characters of the company name (the station number): SUBSTRING(mc.name,1,3) = SUBSTRING(sc.name,1,3).

This means company names in the central database must start with the station number (e.g., "512 Baltimore", "613 Martinsburg"). The field server's company name is typically just the number (e.g., "512").

✅ Safety: Central data is never blindly overwritten
If the central database has a value in a field and the field server's record has a blank, the central value is preserved. The merge uses CASE WHEN NULLIF(RTRIM(s.field),'') IS NOT NULL THEN s.field ELSE m.field END on every text column — meaning blanks and NULLs from the field are ignored, and only actual populated values flow through.

3. Page Buttons — What Each One Does

The Field Sync page has four action buttons plus automation controls. Here's what each one does:

🔍 Preview Sync (Dry Run)

Reads only. Makes zero changes to any database.

Runs SELECT COUNT(*) queries against both the staging and central databases to calculate:
  • Locations to Add — location names in staging not yet in central
  • Assets to Update — existing assets with field-level differences (text6–20, description, rfidtag, etc.)
  • Assets to Insert — brand-new assets not yet in the central database
  • Errors — should always be 0 on a clean run
Requires: The staging database must already exist (run Restore BAK Only first if it doesn't).
When to use: Always run this before committing. It tells you exactly what will change.

▶ Full Sync (Restore + Merge)

The one-click option for daily syncs.

Does both stages in sequence:
  1. Restores the selected .bak file to idash_staging (overwrites any existing staging data)
  2. Runs the full merge SQL (va_field_sync_merge.sql) to push changes into the live idash database
  3. Moves the processed .bak to va_sync\processed\ with a timestamp suffix
Duration: 1–5 minutes depending on database size (176K+ assets takes ~2 minutes).
When to use: Normal daily/nightly sync. This is what the automated scheduled task runs.

📄 Restore BAK Only

Loads the .bak into staging without touching the live database.

Restores the selected .bak file to idash_staging using RESTORE DATABASE ... WITH REPLACE, MOVE. The staging database is completely overwritten. The live idash database is not touched at all.

When to use: When you want to inspect the field server's data before merging. After restoring, you can:
  • Run Preview to see what would change
  • Query idash_staging directly in SSMS to inspect data
  • Run Merge Only when you're satisfied

🔀 Merge Only

Merges from the currently loaded staging database without re-restoring.

Runs va_field_sync_merge.sql against the existing idash_staging database. Skips the restore step entirely.

Requires: A staging database must already be loaded (via Restore BAK Only or a previous Full Sync).
When to use: After a Restore-only + Preview workflow. Also useful if you need to re-run the merge after fixing the merge SQL or troubleshooting.

4. Recommended Workflow

For the safest sync experience, follow this sequence:

1
Check that a .bak is in the watch folder

The BAK File Selection panel shows all .bak files detected in C:\VA_RFID\va_sync\incoming. If no file is listed, either wait for the nightly OneDrive pull, or manually copy one in. You can also enter a full path manually and click Copy to Watch Folder.

2
Click Restore BAK Only

This loads the field data into the staging database without touching the live DB. Takes 1–2 minutes.

3
Click Preview Sync (Dry Run)

Review the numbers. You should see a non-zero count for "Assets to Update" if the field server has any changes. If all zeros, the data is already in sync (or the wrong .bak was loaded).

4
Click Merge Only

Since the staging DB is already loaded from step 2, this applies the changes without re-restoring. Check the Last Sync Results panel for the final counts.

5
Verify in dashboards

Open Site Maps or Asset Statistics and confirm the new data is reflected in the KPIs and tagging numbers.

ℹ Shortcut for routine syncs: If you trust the data (e.g., this is a nightly automated run), you can skip steps 2–4 and just click Full Sync (Restore + Merge). This does everything in one click. The automated scheduled task uses this one-click path.

6. Prerequisites & Permissions

✅ Only One Permission Change Required — Ever
The only setup action needed on the SQL Server is granting idashadmin the ability to create a database so it can restore the .bak to a local staging DB. Run this once as SA: 
ALTER SERVER ROLE [dbcreator] ADD MEMBER [idashadmin];
That is the complete list of permission changes. Nothing else is granted, altered, or elevated. The idashadmin login already has read/write access to idash as part of the standard iDash installation — no change needed there.

Filesystem Permissions

FolderRequired ACLWhy
C:\VA_RFID\va_sync\ IIS_IUSRS — Modify (M) IIS must write log files, the PowerShell script, and manage the incoming/processed subfolders. Without this, clicking Create Task or running sync produces "Access Denied".
C:\VA_RFID\va_sync\staging_db\ SQL Server service account — Full Control SQL Server writes the MDF/LDF files here during RESTORE DATABASE.
⚠ OneDrive / Network Paths and IIS
The IIS worker process (IIS AppPool\iDash or IIS_IUSRS) runs under a restricted service account that cannot access user-profile folders like C:\Users\john\OneDrive or network shares (\\server\share).

If you enter a manual .bak path pointing to OneDrive, the page will show "Cannot access manual BAK path" with a specific error message. The solution is to either:
  • Click Copy to Watch Folder (which copies the file to the watch folder using the current user's credentials)
  • Manually copy the .bak file into C:\VA_RFID\va_sync\incoming\ using File Explorer

10. SQL Server Service Account & Network Share Permissions

When SQL Server needs to read or write files on a network share (e.g., restoring a .bak from \\server\share\, or writing an export to a shared folder), the SQL Server service account must have NTFS file-system permissions AND SMB share-level permissions on that path. This section explains how to identify which account SQL Server runs as, and how to grant it the correct access.

💡 Why this matters for Field Sync
The field sync pipeline restores .bak files from a watch folder. If that folder is on a different server or a network share, SQL Server's RESTORE DATABASE command will fail with "Operating system error 5 (Access is denied)" unless the SQL service account has read access to the .bak file AND write access to the staging database folder.

Step 1: Identify the SQL Server Service Account

There are three methods to find which Windows account runs your SQL Server instance:

Method A: Services Console (GUI)

  1. Press Win+R, type services.msc, press Enter
  2. Scroll to SQL Server (SQLEXPRESS) or SQL Server (MSSQLSERVER)
  3. Right-click → Properties → Log On tab
  4. The account is shown in the "This account" field
✅ Common values you'll see:
NT Service\MSSQL$SQLEXPRESS — Virtual Service Account (default install)
NT AUTHORITY\NETWORK SERVICE — Built-in service account
DOMAIN\svc_sqlserver — Domain service account (enterprise)
.\LocalUser — Local user account

Method B: PowerShell (Fastest)

Run this in an elevated PowerShell prompt:

# Find all SQL Server service accounts on this machine
Get-WmiObject Win32_Service | Where-Object {
    $_.Name -like "MSSQL*" -or $_.Name -like "SQLAgent*"
} | Select-Object Name, StartName, State | Format-Table -AutoSize

Example output:

Name                StartName                        State
----                ---------                        -----
MSSQL$SQLEXPRESS    NT Service\MSSQL$SQLEXPRESS      Running
SQLAgent$SQLEXPRESS NT Service\SQLAgent$SQLEXPRESS    Running

Method C: From SQL Server (T-SQL)

Run this query in SSMS or sqlcmd:

-- Returns the Windows account running the SQL Server service
EXEC xp_regread
    @rootkey = 'HKEY_LOCAL_MACHINE',
    @key = 'SYSTEM\CurrentControlSet\Services\MSSQL$SQLEXPRESS',
    @value_name = 'ObjectName';

-- Alternative (simpler)
SELECT servicename, service_account
FROM sys.dm_server_services;

Step 2: Grant NTFS File System Permissions

The SQL service account needs NTFS permissions on the actual folder on disk. This applies whether the folder is local or on a remote server.

GUI Method

  1. Navigate to the shared folder on the remote server
  2. Right-click the folder → Properties → Security tab
  3. Click Edit → Add
  4. Click Object Types and ensure Computers is checked (for virtual service accounts)
  5. Click Locations and select the SQL server's domain or machine
  6. Enter the account name (see table below) and click Check Names
  7. Grant Read & Execute (for .bak reads) or Modify (for writes)

PowerShell Method (on the file server)

# Grant the SQL server's computer account Read/Write to the share folder
# Replace YOURSERVER$ with the SQL server's hostname + dollar sign
$path = "D:\SharedBackups\va_sync"
$acl = Get-Acl $path
$rule = New-Object System.Security.AccessControl.FileSystemAccessRule(
    "DOMAIN\YOURSERVER$",     # or "DOMAIN\svc_sqlserver" for domain accounts
    "Modify",                  # Read, Write, Modify, or FullControl
    "ContainerInherit,ObjectInherit",
    "None",
    "Allow"
)
$acl.AddAccessRule($rule)
Set-Acl $path $acl

Step 3: Grant SMB Share-Level Permissions

In addition to NTFS, the share itself has a separate ACL. Both must allow access.

GUI Method

  1. On the file server, right-click the shared folder → Properties → Sharing tab
  2. Click Advanced Sharing → Permissions
  3. Add the same account with Change permission (or Full Control)

PowerShell Method

# Grant the SQL server machine account share-level Change permission
Grant-SmbShareAccess -Name "va_sync" `
    -AccountName "DOMAIN\YOURSERVER$" `
    -AccessRight Change -Force

-- If xp_cmdshell is disabled, enable it temporarily:

EXEC sp_configure 'xp_cmdshell', 1; RECONFIGURE;

EXEC sp_configure 'xp_cmdshell', 0; RECONFIGURE;
⚠ Common Gotchas
1. Two layers of permissions. Both NTFS (Security tab) AND Share permissions must allow access. The most restrictive wins.

2. Virtual Service Accounts use the computer account on the network. You cannot add NT Service\MSSQL$SQLEXPRESS to a remote share — it's a local-only identity. Add DOMAIN\SERVERNAME$ instead.

3. Workgroup (non-domain) servers cannot authenticate to domain shares. Both servers must be on the same domain, or you must use matching local accounts with identical passwords on both machines.

4. After changing permissions, restart the SQL Server service. Token-based permission changes may not take effect until the service restarts.

Access Model Concepts

iDash uses a three-dimensional access model: a portal role provides baseline permissions; tile access permissions granularly grant access to specific application tools and documentation; site permissions control which VA medical center data they can interact with and what they can do to it.

DimensionControlsValues
Portal Role Baseline user state and global administrative override admin, user, readonly
Tile Access PermissionsGranular, per-tile access to Scanning tools, Reports, Documentation, and Admin PanelsList of permitted functional tiles (e.g. scan_tagteam, admin_users)
Site Permission Per-site: what the user can do with that site's data full, ennx, or no entry (no access)
Admins bypass site permissions entirely. A user with the admin role always has full access to every site in the database — the site permission grid is stored but never enforced for them.

Portal Roles

Administrator

  • ←“ All reports, research tools, and ENNX generation
  • ←“ All scanning and tagging tools (VA Site Inventory, TagTeam, etc.)
  • ←“ Admin panel on the hub (DB Update, Log Viewer, AutoDB, etc.)
  • ←“ Documentation library
  • ←“ User Management (this page)
  • ←“ Ignores site access rules — always full access to all sites

Use for ID Integration technical staff who need to manage the system. This is the only role that can access the admin panel and create other users.

Standard User

  • ←“ Reports and research tools — limited to their assigned sites
  • ←“ Scanning and tagging tools — limited to their assigned sites and site permission level
  • ←— Admin panel hidden
  • ←“ Documentation library
  • ←— Cannot manage users

Use for VA staff or field technicians who need to actively work with inventory data at assigned sites.

Read-Only

  • ←“ Reports and research tools — limited to assigned sites
  • ←“ Can generate ENNX reports (if site permission = ennx or full)
  • ←— Cannot scan assets, operate TagTeam, or move inventory
  • ←— Admin panel hidden
  • ←“ Documentation library

Use for VA supervisors, auditors, or report consumers who only need to view data and pull ENNX exports.

Site Permissions

After setting a portal role, you assign which VA medical center sites the user can access, and what level of permission they have at each site. Sites come directly from dbo.company in the iDash database.

PermissionCode ValueWhat the User Can DoWhat is Blocked
Full Access full View all site data, scan assets, commit location moves, tag assets, generate ENNX output, run sweeps, export results, email reports. Every inventory write operation is permitted. Nothing — complete site access.
ENNX / Report Only ennx View site reports, ENNX generation, research and look-up tools, export to Excel/CSV, email results. Read operations only. Cannot commit asset moves. Cannot scan assets in VA Site Inventory or TagTeam Scan. The "Commit Scans" button will not appear. Location writes are blocked server-side.
No Entry (key absent) Nothing. Site data is not visible. Everything — site is completely hidden from the user's dropdowns and reports.
Wildcard Site ("*"): Instead of listing sites individually you can set a single entry with the key * and a permission value. This grants that permission level to all current and future sites in the database without needing to update the user when new sites are added.

Typical Configurations

ScenarioSetup
Field tech covering two specific buildingsAdd those two site names with full
VA supervisor who reviews reports for their VISNAdd their sites with ennx
National auditor viewing all facilitiesSet wildcard * ←’ ennx
ID Integration admin managing everythingUse admin role — no site setup needed

Creating a New User — Step by Step

You must be logged in with an Administrator account to access User Management. Navigate to the hub, log in under Admin Tools, then click the User Management tile.
1
Open the Add User form

Click the green + Add User button in the top-right of the Portal Users card. A modal dialog slides in.

2
Fill in account details
FieldRequiredNotes
UsernameYesLogin name. Auto-lowercased. Must be unique. No spaces. E.g. jsmith
Display NameNoHuman name shown in grids and welcome messages. Defaults to username if blank.
PasswordYesMinimum 6 characters. SHA-256 hashed before writing to disk — never stored in plain text.
Confirm PasswordYesMust match password exactly.
Portal RoleYesSee Role table above. Controls which sections are visible in the portal.
NotesNoInternal notes about this account (e.g. "Regional Baltimore field tech").
3
Assign Site Access Permissions

The Site Access Permissions section below the divider shows a grid of every site from dbo.company. For each site you wish to grant access:

  1. Tick the checkbox next to the site name. The row highlights green and a permission dropdown appears.
  2. Choose Full Access (can move assets, commit scans) or ENNX / Report Only (view + export only).
  3. Repeat for each site that should be accessible to this user.

Shortcuts

  • All — Full button: ticks all sites with Full Access in one click.
  • All — ENNX button: ticks all sites with ENNX Only in one click.
  • Clear All button: unticks all sites (no access).
If the role is set to Administrator, a blue notice appears explaining that site assignments are ignored — admins always have full access to everything. You may still fill in the grid for documentation purposes, but it has no enforcement effect.
4
Click "Create User"

Client-side validation runs first (password length, match, username required). If all checks pass, a server postback fires, the user is written to App_Data\idash_users.json, and a green success message confirms the account was created.

The user can now log in immediately using the login panel on the hub.

This user can scan, move, and commit assets at Baltimore and Perry Point, but cannot see data from any other site, cannot access the admin panel, and cannot manage users.

Editing an Existing User

Click the Edit button in the Actions column for any user. The Edit modal pre-populates with all current values including site access checkboxes.

FieldBehavior
PasswordLeave blank to keep the current password. Only enter a new value if you are changing it. The hash in the JSON file is updated only if you type a new password.
RoleChanging role takes effect immediately on the user's next page load (not next login). A currently-logged-in user's session role is not retroactively updated.
Site AccessThe existing site checkboxes and permission dropdowns are pre-selected. Modify as needed and save. Sites not checked are removed from the user's access.
Account StatusSet to Disabled to immediately prevent the user from logging in without deleting the account. Their historical LastLogin data is preserved.
Self-protection: You cannot disable or delete your own account while you are logged in. This prevents accidental lock-out of the last admin. A server-side check enforces this regardless of what is submitted.

Disabling vs. Deleting Users

Disable (Recommended for Temporary Suspension)

Use the Edit modal, change Account Status to Disabled. The user record is retained with full history. The Enabled: false flag in the JSON causes UserManager.Authenticate() to reject all login attempts with the generic "Invalid username or password, or account is disabled" message (no hint to the user which reason applies).

Delete (Permanent)

Click the red Delete button. A browser confirmation dialog runs first. On confirm, the server removes the record entirely from idash_users.json. This is irreversible — the account, password hash, site access, and login history are all erased.

No undo for Delete. If you need to re-create the user later, you must add them fresh and re-assign all site permissions.

How Users Are Stored

All user records live in a single JSON file: App_Data\idash_users.json. This file is created automatically on first use, seeded with the default idashadmin account.

Example Record

  "Username":     "jsmith",
  "PasswordHash": "e3b0c442...sha256hex...",
  "Role":         "user",
  "DisplayName":  "John Smith",
  "Notes":        "Baltimore field tech",
  "Enabled":      true,
  "CreatedDate":  "2026-04-20 20:35",
  "LastLogin":    "2026-04-21 08:12",`r`n  "TileAccess":   ["scan_tagteam", "rpt_overview", "scan_maps", "admin_autodb"],`r`n  "SiteAccess": {

SiteAccess Field Format

KeyMeaning
"SiteName" (exact match)Permission applies to that specific site only
"*"Wildcard — applies to every site in the system
ValueMeaning
"full"Full read/write — can move assets and commit scans
"ennx"ENNX/report access only — view, filter, export, email reports
File location: App_Data is not browseable via IIS (protected by default web.config). Treat the JSON file as a sensitive credential store — back it up when migrating servers, and restrict filesystem access accordingly.

Security Notes

Password Storage

Passwords are hashed with SHA-256 before storage (UserManager.HashPassword()). The raw password is never written to disk or logged. The hash is compared at login — if the hashes match and the user is enabled, the session is granted.

SHA-256 without a salt is suitable for this internal-network tool but is not hardened production-grade password storage. For externally exposed deployments, consider migrating to bcrypt or Argon2 via a stronger password library.

Session Model

Session KeyTypePurpose
IsAdminAuthenticatedboolSet to true on successful login. Controls login panel visibility.
IdashUserRolestringadmin, user, or readonly. Evaluated on every page load.
IdashUsernamestringLogged-in username. Used for self-protection guards.
IdashTileAccessList<string>Array of permitted functional tiles. Verified by CanSeeTile().

Sessions expire with the ASP.NET session timeout (default 20 minutes of inactivity unless configured otherwise in IIS). There is no "remember me" — users must log in again after a session expires.

Default Account

The default seeded account is idashadmin / idashadmin. Change this password immediately after first deployment. Edit the default admin account, enter a new strong password, and save.

Admin Lock-Out Prevention

The server enforces that you cannot disable or delete your own account while logged in. Always ensure at least one other admin account exists before modifying your own credentials.

Where Permissions Are Enforced

The UserManager class exposes three site-check helpers that modules should use:

// Returns "full", "ennx", or null
UserManager.GetSitePermission(user, siteName)

// True if the user can see data for this site
UserManager.CanAccessSite(user, siteName)

// True if the user can commit location moves / scans
UserManager.CanWriteSite(user, siteName)

// True if the user can view data and run ENNX exports
UserManager.CanReportSite(user, siteName)

Hub Tile Enforcement (index.aspx)

Every tile on the hub is wrapped in a server-side <% if (CanSeeTile("key")) { %> guard. The CanSeeTile() method reads the user's IdashTileAccess session list and calls UserManager.CanAccessTile(). Admin users bypass all checks and see every tile.

SectionGuard PatternExample Keys
Scanning & Field Tools Each tile individually guarded scan_tagteam, scan_inventory, scan_maps, scan_locator
ENNX Generation Each tile individually guarded scan_ennx, scan_eil, scan_universal_ennx, rpt_ennx
Printing Section: CanSeeAny("print_mapping", "admin_printer_routing") print_mapping, admin_printer_routing
MQTT & Fixed Readers Each tile individually guarded admin_reader_config, admin_mqtt
Reports & Analytics Each tile: CanSeeTile("rpt_xxx") rpt_overview, rpt_tagging, rpt_ennx, rpt_automation, rpt_asset_master
Search / Lookup Each tile individually guarded search, search_history
Database & Data Mgmt Each tile individually guarded admin_manualdb, admin_autodb, admin_sql, admin_bcp, admin_workbench
Admin Panel Panel requires login + at least one admin_* tile.
Each admin tile individually guarded by CanSeeTile("admin_xxx").		 admin_users, admin_print, admin_restore, admin_logs
Guides & Downloads Each tile individually guarded downloads, docs, docs_arch, docs_label_sop, docs_cookbook

Module-Level Enforcement

ModuleEnforcement Point
VA Site Inventory (va_inventory.aspx) Site dropdown pre-filtered to user's accessible sites.
"Commit Scans" button hidden if CanWriteSite returns false for the active site.
Server-side commit handler verifies CanWriteSite before executing any SQL UPDATE.
ENNX Export (va_ennx.aspx) Site filter dropdown limited to sites where CanReportSite is true.
Reports & Research Site selectors scoped to accessible sites only.
TagTeam Scan (va_tagteam_scan.aspx) Write API verifies CanWriteSite before persisting any scan record.
User Management (va_user_management.aspx)Server-side gate checks CanAccessTile(role, tiles, "admin_users") before rendering the page. Non-admin users with the admin_users tile permission can access user management.
Documentation Hub (documentation/index.aspx)Guides and technical manuals are dynamically shown or hidden based on the user's functional tile permissions using the same CanSee() pattern (e.g., granting scan_tagteam automatically shows the Tag Team Scan documentation).
Defense in depth: Enforcement is applied both at the UI layer (hiding buttons, filtering dropdowns, gating tiles) and at the server-side handler level (verifying permission before SQL execution). A user who tries to call a protected endpoint without the correct session role will receive a 403-like error response.

📝 Login History

Every sign-in attempt to iDash (success or failure) is logged to a persistent audit file. The Login History card at the bottom of this page displays the most recent 50 entries along with KPI summary cards:

KPIDescription
Logins TodayNumber of successful sign-ins since midnight
Failures TodayNumber of failed sign-in attempts since midnight
Unique Users (7d)Distinct usernames with successful logins in the last 7 days
Total EntriesTotal number of entries in the audit log file

Storage

Audit entries are stored in logs/login_audit.jsonl (JSON Lines format — one JSON object per line). Each entry contains:

  • ts — Timestamp (ISO 8601 local time)
  • user — Username attempted
  • ip — Client IP address
  • ok — true for success, false for failure
  • role — User role (only populated on successful login)

File Size Control

The audit file is automatically maintained so it never grows unbounded:

  • 90-day rolling window — entries older than 90 days are trimmed
  • 5,000 entry cap — if the file exceeds this, the oldest entries are dropped
  • Trimming runs automatically on every write (~<10ms)
  • Maximum steady-state file size: ~500 KB

Also Available On

The same audit data is also available on the Log Viewer page (va_log_viewer.aspx) under the Login Audit tab, which shows the last 100 entries.

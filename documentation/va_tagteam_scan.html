Tag Team Scan va_tagteam_scan.aspx

The Tag Team Scan module is a high-speed, mobile-friendly interface designed for rapid physical asset scanning, location tracking, and real-time physical tag printing.

Last Updated: 2026-06-30 — Files: va_tagteam_scan.aspx + va_tagteam_scan.aspx.cs + sw.js

High-Level Overview

During an inventory sweep, technicians use this page to walk through a room, scan the room's barcode, and then rapidly scan all equipment (EE Tags) found inside that room. The page automatically groups these assets under the last scanned location.

Once assets are scanned, the system performs the following in real-time:

  • Autocommit to SQL: Every scan is instantly written to the database. No manual "Save" button is required to persist data.
  • Status Flagging: The system automatically flags assets marked as "Not In Use" (Turned In, Lost, etc.) with a distinct orange badge.
  • Site Validation: Assets belonging to a different site (Site Mismatch) are flagged with a "Wrong Site" warning.
  • Auto Print: If enabled, scanning an asset instantly triggers a physical tag print.
  • Bulk Tagging: Users can mark entire rooms as "Tagged" with a single click, which instantly updates the database records.
  • OIT / 78 CMR Filtering: Assets with CMR/EIL (text8) starting with "78" can be excluded from ENNX reporting and database updates via a checkbox.
  • No-Data Asset Tracking: Assets not found in the database are tracked separately and excluded from ENNX output.

Note: To prevent data entry errors, the system enforces strict validation. You must select a Site and a Default User before scanning. Spurious locations or locations belonging to a different site will be automatically rejected.

Detailed User Process Flow

  1. Select the Context: Choose the Site from the dropdown, the current "Operator", and the "Tag Date". These metadata fields will apply to everything you scan. A Site and Operator must be selected before you can proceed.
  2. Using "Load Scans" (Loading History): If you want to see what someone has been working on recently, pick their name from the Operator dropdown, optionally set a date range (From/To), and hit the Load Scans button. The system will fetch up to the last 250 assets matching the selected user and date range at your currently selected site. Use the Untagged Only checkbox if you just want to find things they scanned but forgot to finish tagging.
  3. Scan the Location First: Place your cursor in the "Scan Location" box and trigger your barcode scanner. The system will query the database to ensure the location exists and belongs to your selected Site. If valid, the page will immediately update the "Current Location" text. You cannot scan assets until a valid location is set, and cross-site location scanning is automatically blocked.
  4. Scan Your Assets: Place your cursor in the "Scan Asset Barcode" box. Scan as many equipment tags as you find in the room. They will appear instantly in the grid below and are automatically saved to the database as you scan.
  5. Review Status Badges: Watch the "Scan Status" column. A green Saved badge confirms persistence. An orange Not In Use badge appears if the asset is logically retired in SQL. A yellow Wrong Site badge appears if the asset belongs to a different station.
  6. Auto Print Mode (Optional): Check the "Auto Print" box. With this enabled, every scan triggers an immediate physical tag print.
  7. Offline Mode Support: If you lose Wi-Fi connection, the system automatically detects the outage via real-time connectivity probing (XHR HEAD requests every 3 seconds). A red "OFFLINE" indicator appears in the status bar, an animated toast banner slides up from the bottom, and all scanning seamlessly switches to local mode. Scans are queued to localStorage with full metadata (barcode, location, operator, tag type, notes, date). When connectivity returns, a green "Sync Now" toast appears — tap it or use the Sync Now button in the Offline Queue card to upload the backlog. No data is ever lost.
  8. Mark Assets as Tagged (Bulk): Use the bulk tagging buttons (Mark All/Selected) to update the Tagged = YES status for the room. These changes are also saved instantly.
  9. Finalize / Retry: Use the green button at the bottom to re-try any scans that failed due to temporary network errors (marked with a red Error badge).
  10. Preview ENNX: Click "Preview ENNX File" to generate the ENNX output. Review the content and use it for reporting.
  11. Review Excluded Assets: Click "Show No Data Assets" or "Show OIT Assets Scanned" to see assets excluded from ENNX and understand why.
  12. Use Grid Filters: Type in the filter boxes below each column header to instantly narrow the grid to matching rows. Use the ☰ Columns button to show/hide columns as needed.
  13. Hide/Show the Config Panel: Click the ⚙ Hide Config button in the header to collapse the Site/Operator/Location panel when scanning, giving more screen space to the scan grid. The state is remembered across page loads.

🛡 Barcode Format Validation — Added 2026-06-24

To prevent invalid data from entering the database and polluting ENNX reports, all scanned barcodes are validated before any database lookup or save occurs.

Expected Format

Every physical asset barcode across all VA sites begins with a 3-digit station prefix (e.g., 512, 517, 540, 581, 613), followed by a space, EE, and the asset identifier (including optional alphanumeric suffixes):

  • 613 EE123456 — ✅ Valid (Martinsburg)
  • 512 EE789012 — ✅ Valid (Baltimore — all physical tags use 512)
  • 517 EE10244 — ✅ Valid (Beckley)
  • 540 EE9999 — ✅ Valid (Clarksburg)
  • 581 EE5555 — ✅ Valid (Huntington)
  • 613 EE12345A — ✅ Valid (Alphanumeric asset suffix)
  • 61 3EE123456 — ❌ Invalid (Malformed station prefix)
  • 613EE123456 — ❌ Invalid (No space after station prefix)
  • 613 E123456 — ❌ Invalid (Single 'E' instead of 'EE')
  • 613 ES41881 — ❌ Invalid ('ES' instead of 'EE')
  • SP102-519 — ❌ Invalid (Location tag scanned into asset box)
Substation Identification: Physical barcodes never contain substation division codes (e.g. 512A4 or 512A5). All physical tags use the 3-digit station prefix (512). Substation association is resolved via automated database lookup of the asset record and location codes.

What Happens on Rejection

ScenarioBehavior
Online scan Red error banner displays the bad barcode and the expected format. Nothing is saved to the database. Nothing is added to the scan list. The input field is cleared and re-focused so the operator can immediately re-scan.
Offline sync Invalid barcodes are skipped entirely (not saved to DB). They appear in the grid with an Error status and description "INVALID FORMAT" so the user can see which scans were rejected.
Load Scans Any previously saved barcodes in the database that do not match the valid format are silently filtered out and will not appear in the loaded results.
Why This Matters: Before this validation, a mis-scanned barcode (e.g., "61 3EE...") would be committed to the database immediately. Even if the operator clicked the X to remove it from their grid, the bad data persisted in the database and would keep appearing in ENNX reports for all users. This validation ensures bad data never reaches the database.

✖ Remove Row (X Button) — Updated 2026-06-24

Each row in the scan grid has an X button that removes the asset from the list.

Previous Behavior (Before 2026-06-24)

  • The X button only removed the item from the in-memory session list.
  • The database record was not modified — the scan data persisted.
  • The removed item would reappear whenever anyone loaded scans or generated ENNX reports.

Current Behavior

  • The X button removes the item from the session list and clears all scan-related fields in the database.
  • Fields cleared: text13 (operator), text16 (location tagged), text17 (tag date), text18 (tagged flag), text19 (tag type), text20 (notes).
  • The asset record itself is preserved (not deleted) — only the tagging data is cleared, as if the asset was never scanned.
  • A green confirmation message shows: "Removed EE123456 and cleared scan data from database."
  • The item will no longer appear in future Load Scans queries or ENNX reports.
⚠ This action is immediate and permanent. Once you click X, the scan data for that asset is cleared from the database. If you need to re-scan the asset, simply scan it again normally.

📡 Offline Scanning Architecture — Updated 2026-06-26 Major

The Tag Team Scan page is a fully offline-capable Progressive Web App. Technicians can continue scanning assets even when network connectivity is lost — in basements, server rooms, or buildings with poor Wi-Fi. The offline system operates through multiple redundant safety layers that guarantee zero data loss.

How It Works — Layered Defense

LayerTechnologyWhat It Does
1. Connectivity Probe XMLHttpRequest HEAD Every 4 seconds, an XHR HEAD request probes the server (bypasses Service Worker). Validates both IIS web server and SQL database connectivity. Updates the _isOnline flag and status bar indicator in real time.
2. __doPostBack Intercept JavaScript override Overrides ASP.NET's __doPostBack() function. Before every postback, performs a 2-second XHR probe. If the server is unreachable, the barcode is queued locally instead of submitted.
3. form.submit() Override & Enter Key Capture Monkey-patch HTMLFormElement.prototype.submit & keydown listener Blocks all form submissions when offline. Direct keydown (Enter/13) listeners on TxtAssetScan and TxtLocationScan halt offline browser reloads immediately and process scans locally.
4. Submit Event Listener window.addEventListener('submit') Redundant capture-phase listener that blocks any submit event when offline. Stashes in-flight barcodes in localStorage before submission.
5. Service Worker v11 sw.js (idash-scanners-v11) Intercepts failed POSTs and returns the cached page shell so the browser never shows "This site can't be reached." Caches ASPX shells (network-first, 7s timeout) and static assets (cache-first) for instant offline load.
6. Pending Barcode Recovery localStorage: TagTeam_PendingBarcode If a barcode is in-flight when a POST fails (race condition / network drop), it is recovered automatically on next page load and added to the offline queue.

Offline Queue & State Persistence

  • Scans are stored as JSON objects in localStorage under the key TagTeam_OfflineQueue. Re-scanning an existing barcode updates the item in place (deduplication).
  • Each queued item includes: Barcode, Location, LocTagged, CompanyId, EmplId, TagType, Notes, TagDate, Tagged, and Status.
  • Users can edit tag types on queued items via inline dropdowns (streamlined to the 4 standard types), and remove items with the X button — all before syncing.
  • Barcode validation is enforced even while offline (client-side regex matches the server rule). Invalid barcodes are rejected with an alert and never queued.
  • State persistence: Current Location (TagTeam_CurrentLocation), Selected Site (TagTeam_SelectedSite), and Operator (TagTeam_SelectedOperator) are all persisted in localStorage and restored automatically on page load.

Sync Process (?action=sync Endpoint)

  1. When connectivity returns, the user taps the green "☁ Sync Now" button (or the toast banner).
  2. The client POSTs the entire TagTeam_OfflineQueue JSON array to va_tagteam_scan.aspx?action=sync.
  3. The server processes each item: looks up the asset in DB, performs barcode validation, resolves company/site from location, flags wrong-site items, and calls SaveScanToDb().
  4. Invalid barcodes are marked with Status = "Error" and Description = "INVALID FORMAT" — they appear in the grid so the user can see which scans were rejected.
  5. On success, localStorage is cleared and the page reloads with all synced items visible in the grid.

📅 Tag Date Stale Guard — Added 2026-06-26 New

Prevents technicians from accidentally scanning with a stale (previous day's) tag date — a common source of data errors when resuming work from a previous day's browser session.

Behavior

  • On every page load, the system compares the Tag Date (TxtCurrentDate) to today's date.
  • If the date is not today, the date input is highlighted with a red border and glow, a warning banner displays the stale date, and a green "OK – Confirm Date" button appears.
  • Scanning is blocked until the user either updates the date to today or explicitly confirms they intend to use the old date by clicking the confirm button.
  • Both online and offline scan paths enforce this check.
  • Non-scan actions (Load Scans, etc.) are not blocked — only asset barcode scans.
Why This Matters: Previously, if a technician opened the scan page on Monday and resumed scanning on Tuesday without refreshing the page, all Tuesday scans would be recorded with Monday's date. This made reporting inaccurate and required manual SQL corrections. The stale guard makes this impossible without explicit user confirmation.

⚠ Barcode Prefix ↔ Site Validation — Added 2026-06-26 New

Warns the operator when the 3-digit barcode prefix doesn't match the selected site. This catches the most common cross-site scanning mistake: having the wrong site selected in the dropdown while scanning.

How It Works

  • The first 3 characters of the selected site name (e.g., "613" from "613 Durham") are compared to the first 3 characters of the scanned barcode (e.g., "613" from "613 EE123456").
  • If both are numeric and they don't match, a warning banner is displayed: "Prefix Mismatch: Scanned prefix '512' does not match selected site '613 Durham' (expected prefix 613)."
  • Validation runs on both client-side (JavaScript, including offline mode) and server-side (C# code-behind) for defense in depth.
  • The scan is not rejected — it proceeds with a warning. This is intentional because technicians legitimately encounter assets from other sites (OIT equipment).
Why This Matters: A technician scanning 200 assets with the wrong site selected means all 200 assets get flagged as "Wrong Site" and must be re-scanned. The prefix warning catches this on the very first scan instead of discovering the mistake 200 scans later.

How it Works (Under the Hood)

The SQL & Postback Architecture

The page uses a Zero-Touch Persistence model. Every scan, edit, or bulk-tagging action triggers an asynchronous background save to the SQL database. Because the page already utilizes postbacks for scanner integration, this provides robust data protection with no perceived latency. The ScanList in the ASP.NET session acts as a transaction log for the current user's session, allowing for instant grid rendering and easy retries of failed network requests.

The Print Server MQTT Subsystem

When you press the "Print Checked" button, the page executes the client-side JavaScript function printCheckedTags() instead of performing an ASP.NET postback. Alternatively, if Auto Print is enabled, scanning an asset instantly calls SaveScanToDb() in the C# backend to obtain a valid Asset ID, which then invisibly injects the printSingleTag() JavaScript function back to the client interface for immediate execution.

This JavaScript:

  • Fetches a Bearer Token from the iDash API using client-credentials logic injected into the page via C#.
  • Compiles a JSON payload of the selected Asset IDs.
  • Resolves routing logic. It checks your manual dropdown overrides, defaults to print_mapping_config.json, and queries SQL for template default targets (Service vs Client).
  • Calls /api/printjobs/print.
The backend ASP.NET Web API inserts the record into the printjob SQL table, which is instantly picked up by the iDash.PrintServer Windows Service listening internally via Mosquitto MQTT on Port 8883. The Web Application automatically operates a lightweight Mosquitto MQTT Broker attached to w3wp.exe!

Important Troubleshooting Note: If printing fails instantly, ensure the MQTTPrint user is properly registered in both the mqttclient and printclient SQL tables, and that BarTender Designer has an active underlying SQL connection on the target template.

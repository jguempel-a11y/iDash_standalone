⚙️ Database Update Workflows

The iDash Database Update module enables administrators to bulk-import asset data into the iDash database via dynamically executed SQL scripts.

This document outlines the difference between the Standard DB Update script and the Enrichment script, as well as how the manual and automated processes function — and explains why these scripts require zero per-site modification when deployed to any VA VISN around the country.

🌎 VISN-Agnostic Design — Works on Any VA Site Without Modification

A common point of confusion is whether these scripts need to be edited for each VA site. They do not. The scripts were deliberately engineered to be fully site-agnostic from the ground up. Every site-specific value — station number, company ID, asset prefix, EPC tag — is derived dynamically at runtime from the data file the VA sends. No hardcoded values need to change.

✅ Zero-Touch Deployment
Copy the iDash folder to any VA VISN server. Run the one-time site setup SQL below. All subsequent imports, enrichments, and CMR recoveries work automatically for that site's station number.

One-Time Site Setup SQL (Run Once Per Server at Install)

The only site-specific action required is creating the company record with a human-readable name. This is a one-time step at initial deployment. All subsequent imports are fully automatic. 

-- Run this ONE TIME when first deploying to a new site.
-- Replace station number and site name with the actual values.
-- Example for site 649, San Diego:

USE [idash];

IF NOT EXISTS (SELECT 1 FROM dbo.company WHERE SUBSTRING(name,1,3) = '649')
    INSERT INTO dbo.company (name) VALUES ('649 San Diego');

-- That's it. All imports will now automatically map to this company.
ℹ If you skip this step
The scripts will still work — they auto-create a fallback company row named "NNN Unknown" (e.g. "649 Unknown") the first time a file is imported. You can rename it later in iDash. No assets will be lost or skipped.

What Changed to Achieve This (April 2026)

Two targeted changes were made to eliminate the last remaining hardcoded station lists:

  • va_dbupdate.sql — Step 5.5 (Company Pre-seed): Replaced a CASE statement naming known sites (512 Baltimore, 613 Martinsburg, etc.) with a dynamic fallback that names any unknown station "NNN Unknown".
  • va_dbupdate.sql — Step 13 (Legacy Company Fix): Replaced a.text7 IN ('517','581','540','512','613','688') with a dynamic SUBSTRING join against dbo.company that matches any station number present in the database.
  • va_dbupdate_upsert_enrich.sql — Step 15 (Company Seed): Removed a hardcoded INSERT INTO dbo.company VALUES ('649') and replaced it with a dynamic INSERT that seeds a company row for any station number in the staged data that doesn't already have a matching company.

1. Standard vs. Enrichment Data Imports — and When to Use Each

When performing an update, you upload a Tab-Delimited text file or an Excel (.xlsx) file, along with a .sql script. The SQL script dictates exactly how that data is parsed and merged into the system. Two primary scripts are available, and they are designed to be run together, in sequence, against the same data file.

📄 Standard Two-Pass Import Workflow

Every routine data load — whether a new site's first import or a periodic update at an established VISN — uses the same VA data file and runs two scripts back-to-back.

va_dbupdate_upsert_enrich.sql

  2. Upload the VA data file under Data File
  3. Upload va_dbupdate_upsert_enrich.sql under SQL Script
    (download from Secure Downloads → Administrative)
  4. Recommended: click Preview Run first to confirm counts
  5. Click Run DB Update Script
→ Inserts new assets and fills blank fields on existing assets.
Location rows and company mapping resolved automatically.
② PASS 2 — Run Second
va_dbupdate.sql
  1. Keep the same data file (or re-upload if the page refreshed)
  2. Upload va_dbupdate.sql under SQL Script
    (the root-level script in the iDash folder — not from the Administrative folder)
  3. Click Run DB Update Script
→ INSERT-ONLY safety pass. Assets already inserted in Pass 1 are skipped.
Also runs legacy normalization and seeds Use Status dropdown values.
✅ Expected Result: Pass 1 shows a non-zero Assets Inserted + Assets Updated count. Pass 2 will show zero or near-zero new inserts — this is correct. It confirms Pass 1 worked. If Pass 2 shows a significant number of inserts, re-check that the enrich script ran without errors.
ⓘ Brand-New Site? Before Pass 1, run the one-time company setup SQL from the VISN-Agnostic section above. Otherwise the company will be auto-named "NNN Unknown" — the import still works, you can rename it later in iDash.

Option A: The Standard Import (va_dbupdate.sql)

This is the default script executed by the automation engine and used for basic provisioning.

Behavior: INSERT ONLY
  • If the asset in the Excel file does not exist in iDash, it creates it.
  • If the asset in the Excel file already exists, it completely skips it.
  • IMPORTANT: It will never update or backfill missing fields on existing assets.

Option B: The Advanced Enrichment Import (va_dbupdate_upsert_enrich.sql)

This script was introduced to allow administrators to fill in missing metadata (e.g. Serial Numbers, Use Status, Equipment Categories) for assets that were already partially created, perhaps by handheld scanners.

Behavior: INSERT MISSING + UPDATE BLANK FIELDS
  • If the asset does not exist, it inserts it (just like the standard script).
  • If the asset already exists, it checks every column. If the database record has a NULL or empty field, and the Excel file provides a value for that field, the database is updated.
  • Safety: It will never overwrite existing data. If the database already has a value in a field, the Excel file's data for that field is ignored.

The va_dbupdate_upsert_enrich.sql script can be downloaded from the "Secure Downloads" section of the iDash portal under the Administrative category.

2. Manual DB Update Process (va_dbupdate.aspx)

The manual tool requires an authenticated administrator. It allows you to select exactly which data file and which SQL script to use.

  • Data File Conversion: If you upload a .xlsx file, the web worker converts it to a clean UTF-8 tab-delimited text file (without a Byte-Order-Mark) to prevent SQL Bulk Insert syntax errors.
  • SQL Parameter Injection: The string {{DATAFILE}} in your uploaded SQL script is dynamically replaced by the absolute path of the converted text file living in a temporary staging directory.
  • Execution Mode: The C# runtime parses the uploaded SQL file, splits it by the GO keyword, and executes each batch sequentially against the database.
  • Safety Gate: By default, destructive terms like DROP, TRUNCATE, and ALTER are blocked unless the administrator explicitly checks the "Allow dangerous SQL" checkbox.

3. Automated DB Update Process (va_autodbupdate.aspx)

The automated pipeline watches a specific network directory (default: C:\VA_RFID\va_dbupdate\autoload) for incoming data files.

  • Standard Execution: When a generic data.txt or data.xlsx is detected, it executes va_dbupdate.sql against it.
  • .BAK Processing: If a full database backup (.bak) is uploaded instead, the pipeline detects the extension and re-routes execution to va_bak_merge.sql, which handles full database restores safely over an existing system.
  • Logging & Fault Tolerance: Standard outputs and failure messages are written to va_autodbupdate.log in the watch folder. If an exception prevents execution, an emergency SMS is dispatched immediately via AlertingService.SendAdminSms().

4. Preview Run — Dry Run Before Committing

The Preview Run (Dry Run) button (yellow, on the va_dbupdate.aspx page) allows you to safely simulate an Enrichment run and see exactly which assets will be modified before making any permanent changes to the database.

✅ Zero Risk — Nothing is Permanently Written
The Preview Run wraps the entire SQL execution inside a database transaction and immediately issues a ROLLBACK after gathering results. The database is left exactly as it was. No assets are inserted, updated, or touched in any way.

Step-by-Step: How to Run a Preview

  • Step 1: Open va_dbupdate.aspx from the iDash hub.
  • Step 2: Upload your Excel or Text data file under Data File.
  • Step 3: Download va_dbupdate_upsert_enrich.sql from the Secure Downloads Center → Administrative folder, then upload it under SQL Script.
  • Step 4: Click the Preview Run (Dry Run) button.
  • Step 5: A summary will show how many locations, assets, and enrichments would have occurred. A table shows the first 25 records that would have been inserted or enriched, including their Name, RFID, Description, and Location.
  • Step 6: If everything looks correct, click the blue Run DB Update Script button to permanently apply the same process.
ⓘ Note on Script Compatibility
The Preview Run feature works with any uploaded SQL script, not just the Enrichment script. However, the preview table (showing affected records) is only populated when using a script that includes the #PreviewLog table logic — which is built into va_dbupdate_upsert_enrich.sql. Standard scripts will still show the summary counts, but no per-record preview rows.

⚠ Recovering Accidentally Deleted or Wiped Field Data

If a bulk operation, manual error, or failed import has accidentally cleared out a field across many asset records — such as CMR numbers, Serial Numbers, Manufacturers, or Equipment Categories — the Enrichment script can fully restore that data from any historical or current data file that contains the correct values.

⚠ Prerequisite: The field must now be NULL or empty in the database.
The Enrichment script will only write into a field if the database currently holds NULL or an empty string for that field. If the field was accidentally overwritten with bad data (not just cleared), you would need a targeted SQL UPDATE instead. Both true NULL and empty string '' are treated as blank and will be overwritten.

Fields That Can Be Recovered This Way

  • text1 — Manufacturer
  • text2 — Model
  • text3 — Serial #
  • text4 — Equipment Category
  • text5 — Service Pointer
  • text6 — SP + Location
  • text8 — CMR / EIL Number
  • text9 — Purchase Order #
  • text10 — Physical Inventory Date (raw)
  • description — Equipment Name
  • lastobservedlocation — Last Known Location
  • disposalstatus — Use Status (In Use / Disposed / etc.)

📄 Targeted CMR Recovery Script (va_cmr_recovery.sql)

For cases where the standard Enrichment script cannot match existing assets — typically because the VA data file uses a different entry number format than what is stored in the database — a dedicated CMR recovery script is available in the Downloads Center under the Administrative folder.

Why a Dedicated Script Is Needed

The standard Enrichment script matches assets by their full constructed asset name (e.g. 649 EE10109) plus Company ID, or by exact RFID tag. The VA sends data files in inconsistent entry number formats — sometimes raw numbers only (10109), sometimes full prefix (649 EE10109), sometimes concatenated (649EE10109). The standard script cannot reconcile these differences and incorrectly identifies all existing assets as new records, reporting thousands of phantom inserts with zero enrichments. The dedicated recovery script solves this entirely.

Entry Number Format Normalization

✅ All Three VA Export Formats Are Handled Automatically
  • File: 10109 → Normalized: 10109 → Matches DB asset: 649 EE10109 ✓
  • File: 649 EE10109 → Normalized: 10109 → Matches DB asset: 649 EE10109 ✓
  • File: 649EE10109 → Normalized: 10109 → Matches DB asset: 649 EE10109 ✓
The script detects whether EE is present in the entry number and takes everything after it. If no EE is found, the raw value is used as-is. The resulting clean number is matched against what is extracted from the database asset name using the same stripping logic.

Performance Architecture — Why It Completes in Seconds

A naive match using LIKE '%EE10109' (leading wildcard) forces SQL Server to perform a full table scan for every single file row. On 48,000 assets with 7,000 file rows, that is over 336 million string comparisons with no index possible — causing multi-minute hangs or outright timeouts.

The recovery script uses a three-stage precomputed index strategy instead:

  • Stage 1 — Build #AssetIndex: Scans the asset table once, extracts the numeric entry portion from each name (649 EE10109 → 10109), stores it in an indexed session-scoped temp table. This scan happens one time only regardless of file size.
  • Stage 2 — Build #NormalizedEntries: Normalizes file entry numbers into a second indexed temp table using the same stripping logic.
  • Stage 3 — Exact Equality Join: All preview, count, and update operations use ExtractedEntryNumber = CleanEntryNumber — a fully index-assisted equality join. No wildcards, no scans. Completes in seconds on any dataset size.

Session Isolation — No Lock Contention

All staging uses #-prefixed temp tables. These are completely session-scoped — invisible to every other database connection, automatically dropped when the session ends. An earlier design using permanent dbo. tables caused DDL schema lock contention between concurrent web sessions, manifesting as 4-5 minute hangs even after browser cancellation. The current session-isolated design eliminates this class of problem entirely. Each web request gets its own private staging environment.

Step-by-Step: CMR Recovery Procedure

  • Step 1: Open the Secure Downloads Center from the iDash hub → Administrative folder → download va_cmr_recovery.sql.
  • Step 2: Open va_dbupdate.aspx.
  • Step 3: Upload your VA data file (Excel or tab-delimited text). The entry number format does not matter — normalization is automatic.
  • Step 4: Upload va_cmr_recovery.sql as the SQL Script.
  • Step 5: Click the yellow Preview Run (Dry Run) button. The summary shows how many assets will be updated (Assets Updated counter). The preview table lists the first 25 matches with action CMR RESTORE, the asset name as stored in the database, the RFID tag, and the CMR value that would be written.
  • Step 6: Verify the count and sample records are correct. Then click Run DB Update Script to permanently commit the CMR restoration.
ⓘ Production Validated Result
This workflow was validated live on a production iDash database containing 48,000+ asset records. After CMR data (text8) was accidentally cleared across the entire site, the recovery script:
  • Identified 6,391 matching records with empty CMR and available file data
  • Completed the full preview (including index build, normalization, and matching) in under 30 seconds
  • Restored all 6,391 CMR values on commit with zero duplicate records created and zero other fields modified on any asset
  • The Preview Run confirmed the entire match set before a single byte was permanently written to disk

📝 Changelog — June 30, 2026

Summary of all changes made to va_dbupdate.aspx, va_dbupdate.aspx.cs, the SQL import scripts, and the Service Worker during this session.

📱 Server-Side File Selection (Mobile Support)

Problem: The page used browser <input type="file"> controls. On mobile devices and across multiple VISN servers, users had to navigate their phone's filesystem to find SQL scripts and data files — impractical and error-prone.

Solution: Replaced both file upload controls with ASP.NET DropDownList controls that automatically scan the iDash application root directory for available files:

  • Data File dropdown — lists all .xlsx and .txt files
  • SQL Script dropdown — lists all .sql files
  • Refresh File Lists button — re-scans the server directory for newly added files
  • Manual upload fallback — hidden behind an "or upload manually" link for edge cases. Manual uploads override dropdown selections.

Files changed:

FileChange
va_dbupdate.aspxNew DdlDataFile and DdlSqlScript DropDownList controls, .ddl CSS class, collapsible upload fallback panel
va_dbupdate.aspx.csPopulateFileDropdowns() method scans Server.MapPath("~/") on page load. ExecuteUpdate() resolves files from dropdown or upload with priority: upload > dropdown.

Why: The DB update process runs on several different servers and needs to be fully mobile-accessible. Users now tap a dropdown instead of browsing a filesystem. All SQL scripts and data files live in the iDash root — no downloads/Scripts/ subdirectory needed.

⏱ Row Count, Estimated Time & Live Progress Timer

Problem: Running an import on 80K+ rows with no feedback created anxiety — users couldn't tell if the process was running, stuck, or had failed. Imports can take 5–10 minutes.

Solution: Three layers of feedback:

  1. On file select — When a data file is chosen from the dropdown, an AutoPostBack fires, the server counts rows (via ClosedXML for XLSX or File.ReadAllLines for TXT), and displays an info bar: "79,280 data rows — estimated processing time: 5 - 10 minutes"
  2. On Run click — A progress panel appears with:
    • Animated CSS spinner
    • Selected file names and row count
    • Estimated completion time (based on row count tiers)
    • Live elapsed timer counting up in MM:SS format
    • Reminder not to close the page
  3. On completion — Page reloads with the standard results summary

Files changed: va_dbupdate.aspx (progress panel HTML/CSS/JS), va_dbupdate.aspx.cs (DdlDataFile_SelectedIndexChanged handler, HidRowCount hidden field)

⚠️ ASP.NET Script Timeout Fix

Root cause of "blank screen after 30+ minutes": The default ASP.NET Server.ScriptTimeout is 110 seconds. Imports with 80K+ rows take 5–10 minutes. After 110 seconds, IIS silently killed the request — the browser kept waiting for a response that would never arrive, while the SQL transaction rolled back on the server.

Fix: Added Server.ScriptTimeout = 1800 (30 minutes) at the start of ExecuteUpdate(). Also added Async="true" to the page directive.

Note: The SQL CommandTimeout was already set to 0 (unlimited) in the batch executor — only the ASP.NET layer was timing out.

🔬 Scientific Notation Prevention (Excel Conversion)

Problem: When Excel stores serial numbers as numeric values, the .Text property returns scientific notation (e.g., 1.23457E+10) instead of the actual number (12345678901). The old code used ws.Cells[r,c].Text for all cells, so these garbled serial numbers were imported into the database.

Fix in ConvertXlsxToTxt():

  • Detects cells where cell.Value is double or cell.Value is decimal
  • If the value is a whole number (no fractional part), formats as a plain integer via ((long)d).ToString()
  • Non-integer and text values continue to use cell.Text as before

Design decision: The fix is applied only in the C# conversion layer (clean data in, clean data out). An earlier attempt to add a SQL cleanup step (Step 12.7) during the import was removed because:

  • The SQL ISNUMERIC() function is unreliable — it accepts values that cannot actually be CAST to FLOAT
  • The CAST(text3 AS FLOAT) caused "Error converting data type varchar to float" on dirty data
  • The CAST(... AS BIGINT) caused "Arithmetic overflow" on values with large exponents
  • Full-table JOINs against the asset table on 80K+ staging rows caused unacceptable processing times

Files changed: va_dbupdate.aspx.cs (ConvertXlsxToTxt method). va_dbupdate.sql and va_dbupdate_upsert_enrich.sql (Step 12.7 removed).

🚧 Service Worker: Admin Page Exclusion

Problem: The Service Worker (designed for scanner offline support) intercepted all .aspx POST requests. When va_dbupdate.aspx timed out or lost connection during a long import, the SW caught the failed POST and served the scanner offline fallback page ("You are offline. Your scan has been saved locally...") — which was confusing and incorrect for an admin page.

Fix: Added an exclusion list in the SW fetch handler. Pages containing va_dbupdate or va_autodbupdate in the URL are now passed through to normal browser handling, bypassing the offline interception entirely.

Files changed: sw.js (fetch event handler, cache bumped to v9)

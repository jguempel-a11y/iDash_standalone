📡 ENNX → VistA Push

📡 ENNX Scanner 🏥 VistA / AEMS/MERS 🗄 SQL MERGE Pipeline 🔒 No PHI/PII

Streamlined workflow that replaces the VA's manual copy/paste process for updating equipment locations in AEMS/MERS after RFID scans. Takes ENNX scan session data from iDash, previews the content, and pushes directly to the VA SQL Server via an automated MERGE pipeline.

🔄 What This Replaces

Previous Manual Process (What VA Staff Did Before):
  1. Scanner operator performs RFID inventory scan at a VA facility
  2. ENNX file is generated and saved to disk
  3. VA staff manually opens the ENNX file
  4. VA staff copies/pastes content into AEMS/MERS terminal
  5. Each asset's location and inventory date is updated one at a time

Now: One button click. Select the scan session, review the ENNX, push to VistA.

📄 ENNX File Format

The ENNX format is a simple line-based text file generated by RFID scanners. It encodes which assets were scanned at which locations.

ENNX ← Header (always first line) ID ← Identifier line SP 2-223 ← Location (room/space identifier) 512 EE12345 ← Asset scanned at SP 2-223 512 EE12346 ← Another asset at SP 2-223 SP 2-224 ← Next location 512 EE12400 ← Asset scanned at SP 2-224 512 EE12401 ← Another asset at SP 2-224 ***END***^7 ← Trailer with total line count (ID + locations + assets)

Parsing Rules

Line PatternMeaningExample
ENNXFile header — skipENNX
IDIdentifier line — skipID
SP*Location/room identifierSP 2-223, SP A-101B
512 EE* or 512EE*Asset name (VA EE-number format)512 EE12345
***END***^NTrailer with total line count (ID + locations + assets). Parser skips any line starting with ***END******END***^7

Asset number extraction: The parser extracts digits after EE to create a numeric match key. For example, 512 EE12345 yields asset number 12345, which is matched against the asset.name column using a LIKE '%EE12345' pattern.

🛠 3-Step Workflow

1 Select ENNX Scan Session

Choose a scanner (user) and scan date from the dropdowns, then click 🔍 Load Sessions.

  • The Scanner (User) dropdown is populated from distinct CreatedBy values in EnnxLiveSession
  • The Scan Date filter matches against CreatedLocal
  • Results show in a grid with SessionId, Date/Time, Station, Scanner, and Summary
  • Click 📄 Load on any row to load that session's ENNX text
↓

2 Preview ENNX Content

The loaded ENNX content appears in a read-only preview textarea. Stats are displayed in the Session Info panel:

  • Assets in ENNX — total count of asset lines (512 EE*)
  • Locations — unique location count (SP*)
  • Scan Date — when the session was created

Optionally click 📄 Download ENNX File to save a copy.

↓

3 Push to VistA

Click 🚀 Push to VistA to execute the full 7-step pipeline:

StepActionDetails
1Parse ENNXExtracts asset→location mappings from ENNX text
2Match in iDashFinds each asset by EE number in local dbo.asset
3Update local DBSets text6, lastobservedlocation, text17, lastinventoried
4Connect to VA SQLOpens connection to VA server using configured credentials
5Stage dataINSERTs matched assets into dbo.AWPushStaging
6MERGEUpserts into dbo.AWAssetSync on rfidtag
7CleanupDrops staging table

Each step displays a green checkmark (✅) on success, amber warning (⚠) for skipped items, or red error (❌) on failure.

✅ Prerequisites

  • EnnxLiveSession table: Must exist in the local iDash database. Created automatically the first time an ENNX Live Scan session is saved via ENNX Live Scan.
  • Network access: The web server must be able to reach OITPORSQL016.R01.MED.VA.GOV on port 1433 (SQL Server). VPN or internal network required.
  • VA SQL credentials: Valid vadbuser account with INSERT/UPDATE/CREATE/DROP permissions on the VAAssetSync database.
  • Completed ENNX scans: At least one ENNX Live Scan session must have been saved to SQL for the session picker to have data.

🔄 MERGE Logic (Upsert Pattern)

The SQL MERGE uses rfidtag as the match key:

MERGE dbo.AWAssetSync AS tgt USING dbo.AWPushStaging AS src ON tgt.[rfidtag] = src.[rfidtag] WHEN MATCHED THEN UPDATE SET tgt.[name] = src.[name], tgt.[lastobservedlocation] = src.[lastobservedlocation], tgt.[lastobservedtime] = src.[lastobservedtime], tgt.[lastinventoried] = src.[lastinventoried], ... (all 26 columns) WHEN NOT MATCHED BY TARGET THEN INSERT ([id], [name], ...) VALUES (src.[id], src.[name], ...)

🔮 Future: Direct VistA Integration via FileMan

The current pipeline pushes data to a SQL staging area (AWAssetSync on the VA SQL Server). VA staff or scheduled processes then import this data into VistA's core database.

VistA uses VA FileMan 22.2 as its database layer (built on MUMPS/M). The FileMan Developer's Guide (May 2018, Patch DI*22.2*10) documents APIs that could enable direct integration in a future phase:

FileMan APIPurposeRelevance
UPDATE^DIE()Updates records in FileMan filesCould directly update AEMS/MERS equipment records
FILE^DDMP()Data Import from external sourcesCould import ENNX/TSV data directly into VistA
FIND^DIC()Record lookup by cross-referenceFind existing equipment to update
$$FIND1^DIC()Single record finderLocate specific asset by EE number
EXPORT^DDXP()Data ExportPull current VistA data for comparison/validation
$$GET1^DIQ()Data Retriever (single field)Read current equipment field values
GETS^DIQ()Data Retriever (multiple fields)Bulk read equipment data
⚠ Requirements for Direct VistA Access:
  • RPC Broker or VistaLink endpoint access
  • FileMan file numbers for AEMS/MERS equipment tables
  • Security keys and access codes (DUZ, DIC("A"))
  • VA approval for external system write access

Reference: VA SQLI (SQL Interface)

VA FileMan's SQLI module (Patch DI*21.0*38) provides a relational mapping layer over VistA's hierarchical MUMPS globals. This creates SQL-compatible views of FileMan data, enabling potential interoperability between our SQL pipeline and VistA's native storage.

Key SQLI components:

  • SQLI_TABLE_ELEMENT — maps FileMan fields to SQL columns
  • SQLI_DATA_TYPE — maps MUMPS data types to SQL types
  • SQLI_DOMAIN — groups related tables
  • SQLI_KEY_FORMAT — defines primary/foreign key relationships

✎ iDash Architecture Rationale & Developer Handoff Guide

Rev. 2026-09-10 Production System Executive & Developer Reference

This document serves three audiences: company leadership evaluating the platform's scope and value, developers taking over support or extending the codebase, and implementation teams deploying iDash to VA medical centers, VISNs, and mobile tagging cart fleets nationwide. It explains what iDash is, why it is built the way it is, what business problems it solves, and gives any technical team member a clear map of how everything fits together.

Bottom line up front: iDash is a purpose-built VA operations portal comprising 64 ASP.NET modules with 117 dedicated documentation pages. It provides live RFID scanning, RFID asset location hunting, executive reporting dashboards, automated ENNX generation, fixed reader management, RFID print routing, database administration, dual-layer cryptographic licensing with air-gapped activation, mobile cart fleet registry, unified user access control (both iDash portal and AssetWorx/RFID users), multi-site field server data sync, login audit trail, secure file exchange, and automated email delivery — all from a single IIS deployment with zero external build dependencies. It deliberately layers direct SQL analytics on top of (not instead of) the AssetWorx REST API, because the API was never designed to serve pre-aggregated dashboard data.

Addressing the "Not Fully on API" Concern

The concern raised is that iDash should be routing all data access through the AssetWorx REST API rather than talking to SQL Server directly. Here is why that concern, while understandable, does not apply to what iDash is doing:

🔴 What "fully API" would require

  • A dedicated API endpoint for every aggregate query (inventory aging buckets, CMR lifecycle stats, tagging completion %, ENNX session rollups, etc.)
  • The AssetWorx backend team adding 20+ custom report endpoints that don't exist today and aren't on the roadmap
  • Turning every dashboard page into an async JavaScript SPA making multiple API calls just to render a single KPI card
  • Losing the ability to write ad-hoc SQL optimization without touching the backend codebase

🟢 What iDash actually does

  • Uses the REST API for all entity-level write operations: print jobs, live scan commits, EIL reconciliation
  • Uses direct SQL only for read-only multi-row analytics that the API doesn't expose—aggregations, bucket counts, joins across tables
  • The API client (AssetworxApiClient.cs) is fully wired and used; it is not decoration
  • A feature flag (UseAssetWorxApi in web.config) controls which path is active
A REST API is an interface contract, not a performance substitute for SQL. Asking the API for 5,000 individual asset records and summing them in C# is not better than writing a single SELECT COUNT(*) GROUP BY query. iDash picks the right tool for each job.

Architecture at a Glance

iDash has three clearly defined data access layers. Every page in the system falls into one of these categories or intentionally uses a combination:

1
Direct SQL Analytics Database Driven

Used by reporting and dashboard pages: va_asset_stats.aspx, va_cmr_stats.aspx, va_tag_stats.aspx, va_data_quality.aspx, and others. These pages run server-side C# code (.aspx.cs) with parameterized SQL queries against the local AssetWorx SQL Server database. Dashboard/report pages typically query dbo.v_asset (a view with INNER JOINs), while scanning and ENNX pages query dbo.asset directly (the base table) to ensure visibility of all scanned records including those missing foreign-key relationships. This is intentional — the data is complex, pre-aggregated, and cannot be practically fetched from a REST endpoint.

2
REST API Integration API Driven

Used for all write operations and entity-level lookups: printing, scan commits, live scan payloads, and asset explorer queries. The AssetworxApiClient.cs class handles OAuth 2.0 client-credentials token management and is called from code-behind on pages like va_tagteam_scan.aspx, va_eil_live_scan.aspx, and others. The JavaScript frontend also calls /api/printjobs/print directly with a Bearer token.

3
Hybrid — SQL Read + API Write Hybrid

Pages like va_tagteam_scan.aspx and va_ennx_live_scan.aspx use direct SQL to load and filter asset data efficiently, then use the AssetWorx REST API to commit changes. This is by design — reads are fast SQL, writes go through the authoritative API layer to ensure business logic rules are enforced at the API level.

Unified User Management

As of July 2026, user management is consolidated into a single page (va_user_management.aspx) with a system toggle at the top:

  • iDash Portal Users — JSON-backed authentication for the iDash web portal. Create/edit/delete users with role, site, and tile-level permissions.
  • AssetWorx & RFID Users — SQL-backed (dbo.sysuser) authentication for RFID scanners and the AssetWorx thick client. Managed via an embedded iframe (va_aw_user_management.aspx?embed=1) to preserve ASP.NET ViewState isolation.
Why the iframe? The AssetWorx user management page uses ASP.NET postbacks and ViewState. Embedding it inline would cause ViewState corruption when the parent page's form also posts back. The iframe pattern isolates the two form contexts completely.

Storage & Portability

  • iDash users are stored locally in App_Data/idash_users.json, fully decoupled from the AssetWorx SQL Database.
  • AssetWorx users are stored in dbo.sysuser in the SQL database and managed through the legacy ASPX forms.
  • Passwords are secured via SHA-256 hashing (iDash) or the AssetWorx native hash scheme (AssetWorx).
  • In the event of an authentication lockout, deleting the JSON file forces UserManager to auto-seed the default assetworxadmin account on the next load.

Login Audit Trail

Every sign-in attempt (success or failure) is logged to logs/login_audit.jsonl by LoginAuditHelper.cs. Each entry records timestamp, username, IP address, role, and result. The file auto-trims at 90 days or 5,000 entries, keeping it under ~500 KB.

  • User Management (va_user_management.aspx) — Login History card with KPI stats (logins today, failures today, unique users this week) and last 50 entries.
  • Log Viewer (va_log_viewer.aspx) — Login Audit tab (Tab 4) with the same KPIs and last 100 entries.

Per-User Site Access Enforcement

As of July 2026, site access filtering is enforced server-side on all data pages. When a non-admin user logs in, their SiteAccess dictionary is stored in the session. Centralized helpers in UserManager.cs (GetAllowedCompanyIds, BuildSiteFilter, FilterCompanyDropdown) restrict SQL queries and dropdown options to only the sites the user has been granted access to. Admin users bypass all site filters.

Dual-Layer Licensing & Mobile Cart Registry Architecture

Operating in air-gapped VA hospital subnets imposes strict architectural constraints: cloud license servers, phone-home telemetry, and internet-based activation endpoints are strictly prohibited by VA OIT security policies. To solve this, iDash implements a dual-layer licensing architecture combining asymmetric cryptography for portal features with native SQL storage for RFID hardware devices.

🔐 Layer 1: iDash Portal Cryptographic License

The iDash web application is governed by LicenseManager.cs, an in-memory cryptographic verification engine that operates completely offline:

  • RSA-2048 Asymmetric Signatures: Licenses are generated by administrators using New-IdashLicense.ps1 with a private signing key. iDash embeds only the public key to verify authenticity and tamper-evidence.
  • Node Locking (Installation ID): Each iDash server or mobile tagging cart derives a deterministic IDASH-XXXX-XXXX-XXXX installation fingerprint from local machine parameters. Licenses are locked to this ID.
  • Zero Network Footprint: Verification happens entirely in memory during session authorization. Zero external calls, zero API dependencies.
  • Offline .idashlic Activation: Technicians transfer signed .idashlic files via USB or secure network share. va_license_activation.aspx reads the file client-side via JavaScript FileReader, automatically populates the validation pipeline, and persists activation.

📡 Layer 2: AssetWorx Core & Fixed Reader License

The underlying AssetWorx RFID tracking engine maintains its own hardware license layer:

  • Database-Backed: Stored as a Base64-encoded JSON payload directly inside dbo.applicationsetting under licensekey.
  • MAC Address Locking: Tied directly to the primary physical network adapter of the host Windows server.
  • Capacity Caps: Enforces physical RFID hardware limits (standard tier: 5 Fixed Readers) and client access seats (standard tier: 15 Handheld/Thick-Client Users).
  • Real-Time Reader Auditing: va_license_manager.aspx queries active reader configurations against database entitlements to alert administrators when reader limits are approached.

Mobile Carts & Workstations Registry

VA medical centers deploy mobile RFID tagging carts (e.g., Tagging Cart 1, Cart 2) and roaming workstations that travel between buildings, clinics, and satellite facilities. Rather than requiring isolated license tracking, iDash centralizes cart visibility in App_Data/cart_licenses.json:

  • Nationwide Fleet Registry: National and facility administrators can view all registered tagging carts, assigned station numbers, host names, installation IDs, and perpetual license statuses from a single screen.
  • Seamless Navigation: Integrated 3-tab navigation bar allows administrators to seamlessly pivot between Active Readers & Device Licenses, Mobile Carts & Workstations Registry, and Local iDash Activation without returning to the main hub.
  • Air-Gapped Portability: The JSON-backed cart registry is independent of SQL database restores, ensuring cart records are preserved during cross-site database merges or disaster recovery.

Why ASP.NET WebForms — A Deliberate Choice

It is fair to ask why iDash wasn't built as a React SPA, a Blazor app, or a .NET 8 Razor Pages project. Here is the honest answer:

  • iDash is a department-internal ops tool, not a product. It lives on a single IIS server already running the AssetWorx application pool. WebForms deploys in seconds — no build pipeline, no Node, no CI/CD. Any developer with a text editor can open a .aspx file and immediately understand the HTML structure.
  • WebForms does not mean "old" or "bad." The pages use modern HTML5 semantics, CSS custom properties, DataTables, Chart.js, and fetch-based JavaScript. The .aspx.cs code-behind is a thin controller that populates data — it is not WebForms-era spaghetti code. Every SQL call is parameterized. Every error is caught.
  • Re-writing in a modern framework would provide zero functional improvement for an internal dashboard — and would require standing up a new build environment, rewriting all SQL queries into API endpoint handlers, and retraining staff. The cost dramatically outweighs any benefit.
  • The code is not wrapped up or inaccessible. Every operation in iDash follows the same pattern: the .aspx file is the view (HTML), the .aspx.cs file is the controller (C#). There are no hidden layers, no compiled DLLs containing business logic, no opaque abstractions. Open any file and read it top to bottom.
Note on the decompiled files: DecompiledPrintServer.cs and related files in the root are reverse-engineered reference copies of the AssetWorx Print Server binary — they are for study only and are not compiled into iDash. They exist so the team can understand the print server's internal behavior without access to the vendor's source code.

WebSerial — Browser-Native USB Scanning

As of 07/25/2026, six scanning modules support the WebSerial API, a W3C standard implemented in Chrome and Edge that allows web pages to communicate directly with USB serial devices without any middleware.

Why WebSerial Was Added

The original scanning architecture relied exclusively on keyboard-wedge input (DataWedge on Zebra devices, or HID-mode barcode scanners that emulate a keyboard). This works well with handheld devices but creates friction for desktop-tethered USB RFID readers that communicate over a serial port (COM port). Previously, connecting these readers required a third-party COM-port relay application or DataWedge profile. WebSerial eliminates that middleware entirely.

  • No client software: No DataWedge, no COM-port relay, no native app. The browser handles it.
  • Any serial device: Works with any reader that outputs newline-terminated data over USB-serial.
  • Same scan pipeline: Serial data feeds into the exact same processing function used by keyboard input. All validation, filtering, and export logic applies identically.

Technical Flow (All Modules)

  1. User clicks "Select/Open Serial Port" inside a collapsible <details> panel.
  2. The browser displays its native serial port picker (explicit user consent required by the WebSerial spec).
  3. JavaScript opens the selected port at 115200 baud, 8N1, hardware flow control.
  4. An async read loop buffers incoming UTF-8 bytes. On each newline, the buffered line is trimmed and passed to the module's scan function.
  5. The scan function processes the input identically to keyboard input — all validation, filtering, and export logic applies.
Deployment prerequisite: WebSerial requires HTTPS (or localhost). If iDash is served over plain HTTP, the WebSerial panel displays "Not Available" on all six pages. Keyboard/DataWedge scanning is unaffected.

How to Make a Change — The Pattern

Every page in iDash follows a consistent pattern. Once you know it for one page, you know it for all of them.

Reading data from the database

// 1. Get the connection string from web.config — always
string connStr = WebConfigurationManager.ConnectionStrings["AssetWorx"].ConnectionString;

// 2. Open a connection, write a parameterized query
using (SqlConnection conn = new SqlConnection(connStr))
{
    conn.Open();
    // Use dbo.v_asset for reporting (INNER JOINed view)
    // Use dbo.asset for scanning/ENNX (base table, includes all records)
    string sql = "SELECT id, name FROM dbo.asset WHERE companyid = @cid ORDER BY name";
    using (SqlCommand cmd = new SqlCommand(sql, conn))
    {
        cmd.Parameters.Add(new SqlParameter("@cid", SqlDbType.Int) { Value = myCompanyId });
        using (SqlDataReader rdr = cmd.ExecuteReader())
        {
            // bind, read, render
        }
    }
}
Important: dbo.v_asset vs. dbo.asset
dbo.v_asset is a SQL view that INNER JOINs across company, location, and other lookup tables. Assets missing any of those foreign keys (common for newly-scanned assets) are silently excluded from this view. Scanning and ENNX pages now query dbo.asset directly with LEFT JOINs to ensure every scanned record is visible. Always use dbo.asset for any new scanning or operational pages. Use dbo.v_asset only for reports where you want fully-resolved, clean data.

Calling the AssetWorx API from code-behind

// Get a valid Bearer token (cached automatically, refreshed when expired)
string token = AssetWorxApiClient.GetToken();

// Inject the token into the page so JavaScript can use it for print calls
LitToken.Text = "<script>var AW_TOKEN = '" + token + "';</script>";

Adding a new configuration value

For infrastructure settings (server names, credentials, feature flags, SMTP config) that are set once per deployment: add it to web.config inside the <appSettings> block. Read it anywhere via ConfigurationManager.AppSettings["MyKey"]. Do not hardcode server names, credentials, or URLs anywhere in .aspx.cs files.

For user-editable settings (recipient lists, report schedules, toggle states that users change through the UI during normal operation): store them in a JSON file under the config/ directory. Writing to web.config at runtime triggers an IIS application pool recycle, which destroys all active sessions and forces every logged-in user to re-authenticate. Use System.IO.File.ReadAllText() / WriteAllText() with JavaScriptSerializer for reads and writes. See EmailHelper.cs and va_report_automation.aspx.cs for working examples of this pattern.

Adding a new page

  1. Create my_page.aspx (copy the shell from any existing page for consistent styling)
  2. Create the matching my_page.aspx.cs code-behind
  3. Add a link to index.aspx in the navigation section
  4. Create a documentation/my_page.html doc entry and link it from documentation/index.aspx

The Hybrid Strategy Going Forward

The current architecture is intentionally hybrid and will remain so. Here is how each layer will evolve:

Operation Type Recommended Layer Rationale
Write operations (scan commit, create asset, print job) AssetWorx API API enforces business rules, audit logs, and data integrity constraints
Entity lookups (single asset by ID, user by name) AssetWorx API API is authoritative for individual entity reads
Dashboard aggregates (counts, aging buckets, %, groupings) Direct SQL No equivalent API endpoint exists; SQL is the only practical option
Bulk data exports (CSV downloads, Excel, report generation) Direct SQL API pagination would require dozens of round-trips for the same data
Administrative operations (DB updates, SQL uploads, log viewing) Direct SQL These operations exist specifically because the API doesn't expose admin-level access
The migration path is clear: As the AssetWorx API team adds aggregate endpoints or reporting capabilities, the corresponding iDash pages can be updated to use them — one page at a time, controlled by the UseAssetWorxApi toggle in web.config. No big-bang rewrite required.

🚀 Deployment & Regional Server Setup

When deploying iDash to a new VA regional server, moving the AssetWorx SQL Database (.mdf) and IIS web files is not enough. You must also migrate the external state.

  • User Accounts: You must copy App_Data/idash_users.json, otherwise all portal users and their site-level permissions will be lost.
  • Print Configuration: You must copy print_mapping_config.json and ensure printer_routing.json exists alongside the PowerShell Spooler script.
  • Config Directory: You must copy the entire config/ directory, which contains email_recipients.json (global email recipient list) and report_automation.json (report scheduling settings). These files are not in web.config — they are stored separately to avoid IIS app pool recycles.
  • Automations: You must re-create the Windows Task Scheduler triggers for va_autodbupdate.aspx (autoload polling) and AutoReportRunner.ps1 (Daily ENNX exports).
  • Field Sync: You must copy va_field_sync_merge.sql and ensure downloads/Scripts/va_field_sync_merge.sql stays in sync. The merge script is executed by va_field_sync.aspx to sync field server data into the central database.
  • Mobile Carts Registry: You must preserve App_Data/cart_licenses.json and any applied .idashlic files, which maintain the nationwide mobile tagging cart registrations and local node-locked activation status.
  • Site Maps: You must copy the entire site_maps/ directory tree, which contains facility and site architectural floor plan images organized by building number.
  • Web.config: Ensure the SMTP server, database connection strings, and API credentials are updated for the new environment.
See the full map: Read the External State & Dependencies Guide for a complete checklist of files that exist outside the SQL database.

📋 Developer Handoff Checklist

If you are taking over iDash support, here is what you need to verify before you can work on it confidently:

  • Read web.config top to bottom. Every configurable value in the system is there. You will understand 80% of the app just from this file.
  • Browse to /documentation/index.aspx on the server. Over 50 individual module documentation pages exist. Read the one for any module before editing it.
  • Understand the two data layers. Dashboard/report pages query dbo.v_asset (a SQL view that INNER JOINs asset metadata across tables). Scanning and ENNX pages query dbo.asset directly (the base table) to include all records. Run SELECT TOP 10 * FROM dbo.v_asset and SELECT TOP 10 * FROM dbo.asset in SQL Server Management Studio to see the difference in shape and row count.
  • Know about the AssetWorx API. It runs at http://localhost/api (configurable in web.config via AssetWorx_ApiBase). It uses OAuth 2.0 client credentials — the client ID and secret are in web.config. Token management is entirely handled by AssetworxApiClient.cs.
  • Know about the Print Pipeline. The iDash print stack has three layers: (1) the mobile app selects a template via template.name matching in SQL, (2) the iDash web UI uses print_mapping_config.json to resolve template IDs when printing from Tag Team Scan, Asset Master, and Excel Print, and (3) AssetWorxApiHelper dispatches the print request natively via POST /api/printjob/print using site OAuth credentials. The API publishes the MQTT trigger on port 8883 to the native AssetWorx.PrintServer Windows service, which executes BarTender and routes the label to the hardware printer. The system operates 100% independently without requiring any external PowerShell scripts on VA production servers.
  • IIS runs two pipelines side by side. ASPX pages run under ASP.NET 4.8 (classic mode). The /api/* path is routed to an ASP.NET Core application via the AspNetCoreModuleV2 handler. Both are configured in web.config under <system.webServer><handlers>.

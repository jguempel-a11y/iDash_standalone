🏗 Section 1: Architecture Overview
How Data Flows from Reader to Live View
Each FX9600 reader scans RFID tags continuously and sends the data to iDash for processing. There are two supported data paths:
FX9600 Reader (Zebra IoT Connector) │ ├── HTTP-POST Path (Working) ──► va_rfid_ingest.ashx ──┐ │ Direct HTTP POST to iDash │ │ No broker needed │ │ ▼ └── MQTT Path (Broken) ──► AssetWorx.Web.exe ──► NOT ROUTING PUBLISH to broker ╳ port 8883/TLS AntennaLocationService (subscribes but receives nothing) │ ▼ AntennaLocationService ├── Parse JSON payload ├── Extract EPC + antenna port ├── Lookup reader in dbo.reader ├── Map antenna → location (dbo.antenna) ├── Update dbo.assetlocation ├── Write dbo.locationhistory ├── Detect cross-site observations └── Push to live feed ring buffer │ ▼ va_fixed_reader_live.aspx Polls every 2s, shows real-time tags

⚙ Section 2: FX9600 IoT Connector Setup
1 Access the Reader Web UI
Open a browser and navigate to https://<reader-ip>. Default credentials: admin / Admin4you! (change after first login).
2 Configure the HTTP-POST Endpoint
Navigate to Communication → Zebra IoT Connector → Configuration. Click Add EndPoint (or edit existing).

Endpoint Settings

  • Endpoint Name: iDash_HTTP
  • Endpoint Type: HTTP-POST
  • URL: http://<idash-server-ip>/iDash/va_rfid_ingest.ashx
  • Authentication: None (endpoint is unauthenticated)

Interface Mapping

  • Tag Data Interface1: iDash_HTTP
  • Tag Data Interface2: None
  • Management Interface: None (or MQTT_Broker)
  • Control Interface: None (or MQTT_Broker)
  • Mgmt Events Interface1: None (or MQTT_Broker)
Key: Tag Data Interface1 must be set to iDash_HTTP. This is the only interface needed for tag reads to flow to iDash.
3 Set Operating Mode to Inventory
Navigate to Communication → Zebra IoT Connector → Operating Mode.

Mode Settings

  • Mode: Inventory (continuous scanning)
  • Reporting Interval: 5
  • Units: SECONDS
  • Environment: HIGH INTERFERENCE

Tag Metadata (check these)

  • ☑ RSSI
  • ☑ SEEN_COUNT
  • ☑ ANTENNA (required — maps port to location)
  • ☑ HOSTNAME (required — identifies the reader)
Important: ANTENNA and HOSTNAME must be checked. Without ANTENNA, iDash cannot map tags to locations. Without HOSTNAME, iDash cannot identify which reader sent the data.
4 Configure Antenna Ports
On the same Operating Mode page, under Antenna Configuration:
  • Enable only the ports that have antennas physically connected
  • Set Transmit Power to 27 dBm (default, adjust based on read range needs)
  • FX9600 has 4 ports; FX7500 has 4 ports; each port maps to one dbo.antenna row in the database
5 Start Cloud Operations
Navigate to Communication → Zebra IoT Connector → Connection.
  • Verify all mapped interfaces show connected
  • Click the Start button under Cloud Operations
  • The reader will begin scanning tags and posting data to iDash
Cloud Operations must be Started. Setting Inventory mode alone does NOT start the radio. You must click Start on the Connection page. After a reboot, Cloud Operations must be re-started.
🔧 Section 3: iDash Configuration
1 Register the Reader in the Database
Each reader needs a row in dbo.reader and its antennas need rows in dbo.antenna. Use the Fixed Reader management page at va_fixed_reader.aspx.

dbo.reader

  • physicalid: Must match reader hostname (e.g., FX9600_F78C85)
  • name: Display name (can be same as physicalid)
  • companyid: Site/company this reader belongs to

dbo.antenna

  • readerid: FK to dbo.reader.id
  • number: Antenna port (1, 2, 3, or 4)
  • locationid: FK to dbo.location — where this antenna "sees" tags
  • companyid: Same as reader’s companyid
How it works: When a tag is read on antenna port 2 of reader FX9600_F78C85, iDash looks up the antenna row with readerid=21, number=2, gets locationid=32841, and updates the asset’s location to that location.
2 Web.config Settings
The following appSettings keys in Web.config control the AntennaLocationService:

✅ Section 4: HTTP-POST Data Path (Current Workaround)
How HTTP-POST Works
Each FX9600 reader POSTs a JSON array of tag reads directly to iDash every Reporting Interval seconds. No MQTT broker is involved.
FX9600 ──HTTP POST──► http://server/iDash/va_rfid_ingest.ashx │ │ │ JSON payload: │ RfidIngestHandler: │ [{ │ 1. Read request body │ "data": { │ 2. Call ProcessHttpPayload() │ "idHex": "E280...", │ 3. Parse tag array │ "antennaPort": 1, │ 4. Lookup reader by hostname │ "hostName": "FX9600_" │ 5. Map antenna → location │ } │ 6. Update database │ }, ...] │ 7. Push to live feed │ │ Response: {"ok": true} └── Done. No broker needed.
Advantages: Simple, reliable, no broker dependency, easy to debug (just check HTTP response codes). Works perfectly for the current single-reader test setup.
Limitation: At 40+ readers, each reader creates separate HTTP connections every few seconds. MQTT is more efficient at scale (single persistent connection per reader, one subscriber for all data).

🔌 Section 5: MQTT Data Path (Production Target)
How MQTT Should Work (Once Broker Bug Is Fixed)
For production with 40+ readers, MQTT is the correct architecture:
40 x FX9600 Readers │ Each connects once to broker (persistent TCP/TLS) │ Each PUBLISHES to: reader/tagobservation │ ▼ AssetWorx.Web.exe (MQTTnet Broker, port 8883/TLS) │ Routes all PUBLISH messages to matching subscribers │ ▼ AntennaLocationService (single subscriber) SUBSCRIBES to: reader/# Receives ALL tag data from ALL 40 readers Processes centrally, one background thread

FX9600 MQTT Endpoint

  • Endpoint Name: MQTT_Broker
  • Broker Address: <idash-server-ip>
  • Port: 8883
  • TLS: Enabled
  • Username: crosssite
  • Password: crosssite2026
  • Tag Data Topic: reader/tagobservation

Why MQTT at Scale

  • 40 readers = 40 persistent connections (vs 40 × HTTP requests/sec)
  • One subscriber receives all data
  • Lower latency (push vs poll)
  • Built-in keep-alive and reconnection
  • Standard IoT protocol
Currently blocked by AssetWorx broker bug. See Section 6 below.
🐛 Section 6: Bug Report — AssetWorx MQTT Broker Does Not Route Messages
BUG SUMMARY: The embedded MQTT broker in AssetWorx.Web.exe (MQTTnet.dll) accepts client connections, authenticates them, and accepts SUBSCRIBE and PUBLISH operations — but does NOT route PUBLISH messages to subscribers. This is a defect in the AssetWorx platform, not in iDash or the FX9600 reader.
Evidence
1. FX9600 is connected and publishing (confirmed via TCP):
LocalAddress:Port RemoteAddress:Port State 192.168.4.48:8883 192.168.4.47:50842 Established ← FX9600 connected
2. iDash subscriber is connected and subscribed (confirmed via AntennaService log):
09:59:01 [INFO] MQTT connected to 127.0.0.1:8883 09:59:01 [INFO] Subscribed to reader/# -- ready for tag reads (1 readers, 2 antennas)
3. FX9600 Connection page shows all interfaces connected:
InterfaceStatusError
Tag Data Events Interface1connected(none)
Management Events Interface1connected(none)
Management Interfaceconnectedsubscription failed (255)
Control Interfaceconnectedsubscription failed (255)
4. iDash received ZERO messages despite FX9600 Cloud Operations started and tags waved:
messagesReceived: 0 (after 30+ minutes of monitoring) rawMessages: 0 (spy buffer captured nothing)
5. HTTP-POST works immediately with same data:
Switching Tag Data Interface1 from MQTT_Broker to iDash_HTTP → Tags immediately flowing, dozens per second
6. Error 255 = MQTT SUBACK “Not Authorized”
The broker rejects SUBSCRIBE requests for gateway/cmd/# topics (Management and Control interfaces). This suggests the broker has an ACL that is too restrictive. The same ACL may be silently dropping PUBLISH routing even though it doesn’t return an error to the publisher.
Conclusion: The MQTT broker in AssetWorx.Web.exe has a message routing defect. It accepts connections and subscriptions but does not forward PUBLISH messages between connected clients. The crosssite user credentials authenticate successfully on both sides. The topic (reader/tagobservation) matches the subscription (reader/#). The broker simply does not route.

🚨 Section 11: MQTT Broker Diagnostic Report (2026-08-31)
Executive Summary
The AssetWorx MQTT broker does not route PUBLISH messages to subscribers. This was confirmed through exhaustive testing with multiple credential sets, topic configurations, fresh reboots, and a self-publish test. The broker accepts connections, accepts subscriptions, and responds to PING keepalives, but never delivers published messages to subscribing clients.
This is a broker limitation, not a configuration issue. The HTTP-POST workaround (iDash_HTTP endpoint) is fully operational and serving as the production data path.

⚖ Section 12: Resolution Options & Recommendation
Decision Context
The AssetWorx MQTT broker does not route messages (Section 11). Two resolution paths are available. This section provides the technical and cost analysis to support the decision.
Key fact: The dbo.mqttclient table contains pre-configured credentials for fx9600_f78c85 and idash_antenna with accesstagobservations = True. This proves the vendor designed and sold this system with the intention that MQTT routing would work. The broker’s failure to route is a defect in the delivered product, not a new feature request.
A Option A: Vendor Fixes AssetWorx Broker

Pros

  • Single integrated system — no additional software
  • Vendor-supported and maintained
  • Uses existing infrastructure and port 8883
  • Print system and reader system on same broker

Cons

  • Vendor quoting $17,000 for what is a defect fix
  • Timeline unknown — dependent on vendor schedule
  • Embedded broker (MQTTnet) is not enterprise-grade
  • No clustering, no HA, no monitoring dashboard
  • Ties critical infrastructure to a single vendor’s embedded component
Defect argument: The dbo.mqttclient table schema includes accessgatewaymessages, accesstagmovements, accesstagobservations, accessevents, accessalarms, and accessvtagsensors columns — a sophisticated ACL system clearly designed to control message routing. The vendor created per-reader credentials (fx9600_f78c85) and per-service credentials (idash_antenna) specifically for this use case. The routing code was either never implemented or is broken. This is a defect, not an enhancement.
B Option B: Deploy RabbitMQ as MQTT Broker (Recommended)

Pros

  • Already approved in VA — RabbitMQ runs on existing VA platforms (ATO precedent)
  • Enterprise-grade: clustering, high availability, mirrored queues
  • Built-in web management dashboard (port 15672)
  • MQTT plugin supports full MQTT 3.1.1 and 5.0 with proper message routing
  • TLS, LDAP, fine-grained ACLs — meets VA security requirements
  • Prometheus + Grafana monitoring out of the box
  • Open source, no licensing cost — $0 vs $17,000
  • Eliminates vendor dependency for critical message infrastructure
  • Scales to thousands of readers and millions of messages
  • Can be deployed alongside AssetWorx broker without disruption

Considerations

  • Additional service to install and maintain
  • Requires Erlang runtime (~100 MB)
  • MQTT is via plugin (not native), but fully compliant
  • Runs on a different port (e.g., 8884) — FX9600 endpoint update needed
  • ID Integration team manages instead of vendor
RabbitMQ Architecture (Option B)
FX9600 Reader ──MQTT/TLS──→ RabbitMQ (port 8884) ──routes──→ iDash AntennaLocationService publishes to: │ subscribes to: reader/tagobservation │ ✓ Messages routed reader/# │ │ Runs alongside, does NOT replace: │ MqttPrintNotifier ──MQTT/TLS──→ AssetWorx Broker (port 8883) ──→ Print Clients publishes to: │ ✓ Already working awrx/print/{user} │ ✓ Unchanged
Zero disruption: RabbitMQ runs on a separate port. The AssetWorx broker, print system, and all existing infrastructure remain completely untouched. Only the FX9600 endpoint and iDash Web.config point to the new port.

Recommendation
Recommended: Option B — Deploy RabbitMQ

RabbitMQ is already approved and running in VA environments, provides enterprise-grade reliability, costs $0, and can be deployed in under an hour with zero disruption to the existing AssetWorx infrastructure. The vendor should still be held accountable for the broker defect (the dbo.mqttclient ACL schema proves the feature was designed and sold), but the program should not be blocked on a $17K vendor quote for what is a bug fix.

Immediate action: Continue using HTTP-POST (iDash_HTTP) for current testing.
Short-term: Deploy RabbitMQ for production MQTT infrastructure.
Long-term: Require vendor to fix the AssetWorx broker as part of maintenance/warranty, at no additional cost.

🔄 2. Data Flow: How Label Data Gets to BarTender

✅ Method 1: Native iDash BarTender API (Modern Stateless SubStrings)

Implemented in App_Code/BarTenderApiHelper.cs and api/BarTenderHandler.ashx. This method directly utilizes the Seagull.BarTender.Print.dll SDK in memory, completely bypassing the legacy Print Server limitation. It sets doc.PrintSetup.UseDatabase = false; and injects data directly into Named Data Sources (SubStrings): 

doc.SubStrings.SetSubString("lblname", asset.item_desc);
doc.SubStrings.SetSubString("lblsn", asset.serial_number);
doc.SubStrings.SetSubString("lbleil", asset.eil_number);
doc.SubStrings.SetSubString("lblrfidtag", asset.rfid_tag);
doc.ExportPrintToFileToImage(...); // Generates instant 200 DPI PNG preview
doc.Print("Std_Small");           // Spools directly to Zebra printer
✅ Recommended for VA Sites: 100% stateless, zero SQL database footprint in BarTender, and supports interactive visual previews before printing.

❌ Method 2: SubStrings with Legacy iDash Print Server (Does NOT Work)

In theory, the legacy Windows service (iDash.PrintServer.exe) could open the .btw template and call format.SubStrings.SetSubString(). In practice, the legacy iDash Print Server does NOT inject SubStrings. It opens the template and prints it, but the SubString values remain as whatever "Embedded Data" was saved in the template.

⚠ Confirmed 08/25/2026: When using the legacy MQTT Print Server with Embedded Data fields (any name — lblsn, Serial Number, etc.), every label prints with the same static sample data baked into the template. The legacy Print Server does not call SetSubString().

⚙️ Method 3: Database Field Connection (Legacy Working Solution)

For environments still operating the legacy MQTT Print Server, the BarTender template must be configured with a direct SQL Server database connection querying dbo.printjob and dbo.asset. When the Print Server triggers a print, BarTender executes the query and populates each label with real asset data from the database.

Legacy Operational Note: Requires maintaining SQL credentials inside the .btw template and careful coordination via SubmitPrintJobsBatch() to prevent N×N duplicate labels.

🐛 3. The N×N Duplicate Label Bug

The Problem

When a user selected N assets to print, the system created N print jobs via the API. Each API call to /printjob/print does two things:

  1. Inserts a row into dbo.printjob with completed=0
  2. Publishes an MQTT message that triggers the Print Server

With BarTender's database query set to WHERE completed = 0 and "All Records" enabled:

Select 3 assets → 3 API calls → 3 MQTT triggers

Trigger 1: BarTender queries DB → finds 1 pending record → prints 1 label
Trigger 2: BarTender queries DB → finds 2 pending records → prints 2 labels
Trigger 3: BarTender queries DB → finds 3 pending records → prints 3 labels

Total: 6 labels (should be 3). Each label printed 1–3 times depending on timing. With rapid-fire triggers, it was closer to N × N = 9 labels.

Root Cause

The /printjob/print API endpoint performs two actions atomically (DB insert + MQTT publish) and there is no way to separate them. Calling it N times triggers N prints. Combined with BarTender's "All Records" query, each trigger prints ALL pending records, causing exponential duplication.

✅ 4. The Fix: Native API Sequential Batch Trigger

Solution: SubmitPrintJobsBatch() — Submits each print job via the native /api/printjob/print endpoint using OAuth credentials, waiting for BarTender to complete each job (polling completed = 1) before sending the next. This ensures 100% independent server execution with zero duplicate labels.

How It Works

  1. User selects N assets and clicks "Send to Printer" in Asset Master or Excel Print
  2. iDash calls IdashApiHelper.SubmitPrintJobsBatch()
  3. The helper requests a site-scoped OAuth token and calls POST /api/printjob/print for the first asset
  4. The API inserts the job, generates the RFID hex tag, and publishes the MQTT trigger to iDash.PrintServer on port 8883
  5. The Print Server executes BarTender, prints the physical label, and marks completed = 1 in SQL
  6. WaitForPendingJobsComplete() confirms the job is finished, then immediately dispatches the next asset in the queue

Result: Every selected asset prints exactly once. Zero duplicates, zero orphaned jobs, and zero external PowerShell scripts needed on production VA servers.

🛠️ 5. BarTender Template Setup

🏷️ Important for VA Installations (Zero SQL Database Mode): If your site is utilizing the Native iDash BarTender REST API & Print Engine (documented here), you do NOT need to configure a database connection inside the .btw template! Templates for the native API engine use Named Data Sources (lblname, lblsn, lbleil, lblrfidtag) with doc.PrintSetup.UseDatabase = false;, completely eliminating local SQL database requirements. The database connection setup below is strictly required only when running the legacy MQTT Print Server.
⚠️ Legacy MQTT Print Server Only: If relying on the legacy iDash.PrintServer.exe Windows service, the BarTender template must be configured with a database connection. Follow these steps exactly:

Step 1: Database Connection Setup

  1. Open the .btw template in BarTender (e.g., AW_Std_Small.btw)
  2. Go to File → Database Connection Setup
  3. Click Add...
  4. Choose "Microsoft OLE DB Provider for SQL Server" (or SQL Server Native Client)
  5. Configure the connection:
    • Server: .\sqlexpress (or localhost\sqlexpress)
    • Database: iDash
    • Authentication: SQL Server → idashadmin / idashadmin

Step 2: Set the Query

Use a custom SQL query (not a table selection). This query joins printjob to asset to retrieve the actual asset data for each pending print job:

SELECT a.name, a.description, a.text3, a.text8, a.rfidtag
FROM printjob p
INNER JOIN asset a ON p.recordid = a.id
WHERE p.completed = 0
ORDER BY p.id ASC

Step 3: Configure Record Selection

In the Database Connection Setup dialog, go to the Record Selection tab and set it to "All Records". This tells BarTender to print one label per row returned by the query.

Step 4: Map Fields to Database Columns

For each text field on the label:

  1. Double-click the field on the label to open Text Properties
  2. Change the Type from "Embedded Data" to "Database Field"
  3. Select the corresponding column from the database connection
Label Field NameTypeDatabase ColumnAsset Data
lblname (or any name)Database FieldnameAsset name / EE number
lbldescriptionDatabase FielddescriptionEquipment description
lblsnDatabase Fieldtext3Serial Number

  • Number of Identical Copies: 1

Save the template (Ctrl+S) and close BarTender. The Print Server will use this template for all future print jobs.

🔄 7. SubStrings vs Database Fields

What Are BarTender SubStrings?

SubStrings (also called "Named Data Sources") are named fields in a BarTender template that can be programmatically set via the Seagull.BarTender.Print.dll SDK:

format.SubStrings.SetSubString("lblsn", "12345");  // Set serial number
format.SubStrings.SetSubString("lbleil", "ABC-123"); // Set CMR

Why SubStrings Didn't Work with Legacy iDash Print Server

The legacy iDash Print Server does NOT call SetSubString(). Despite having the Seagull.BarTender.Print.dll in its directory, the legacy Windows service simply opens the template and prints it without injecting any SubString values. All labels print with whatever "Embedded Data" was last saved in the template.

Tested with the following SubString names: lblsn, lbleil, lblname, lbldescription, Serial Number, CMR, Name, Description — none worked with the legacy service.

✅ How SubStrings DO Work (Modern Native Engine & Spooler)

SubStrings work natively and reliably when driven through either:

  1. The Native iDash BarTender Integration Engine (App_Code/BarTenderApiHelper.cs + api/BarTenderHandler.ashx): Directly sets SubStrings in memory, supports live 200 DPI PNG visual previews to the browser, and executes physical print jobs to Zebra printers without touching local SQL. See the BarTender REST API Integration Guide for full details.
  2. The iDash Bypass Spooler (iDash\printing\Run_Bypass_Spooler.ps1): A standalone PowerShell utility that calls the Seagull SDK directly from an interactive user session.

Both methods utilize these standardized lbl-prefixed Named Data Sources:

🔍 9. Troubleshooting Guide

Symptom: All labels print the same data (embedded sample data)

Cause: BarTender template fields are set to "Embedded Data" type, and the Print Server is not injecting SubStrings.
Fix: Set up a database connection in the template with fields mapped as "Database Field" type. See Section 5.

Symptom: Duplicate labels (N selected → N×N printed)

Cause: Each print API call triggers MQTT, and BarTender's "All Records" query prints all pending records each time.
Fix: Use SubmitPrintJobsBatch() which triggers only once. See Section 4.

Symptom: Only 1 label prints (selecting multiple)

Cause: BarTender Record Selection is set to "First Record" instead of "All Records".
Fix: In BarTender Database Connection Setup → Record Selection → set to "All Records".

Symptom: "Bartender Print Result Failure" in Print Server logs

Cause: Template file not found, BarTender license expired, printer not available, or template configuration error.
Fix: Check:
  • Template path in dbo.template.filename matches the actual file location
  • BarTender is installed and licensed on the print server machine
  • The target printer is online and configured
  • Print Server log: C:\Logs\PrintServer_log*.txt

Symptom: "Print Client not currently connected" message in printjob

Cause: The iDash Print Server is not running or cannot connect to the MQTT broker.
Fix: Start the Print Server service. Check appsettings.json:
  • MqttServer: localhost
  • MqttServerPort: 8883
  • PrintClientUsername: MasterPrint

📚 11. Lessons Learned

1. The iDash Print Server does NOT inject SubStrings

Despite having the Seagull SDK, the Print Server only opens the template and prints it. It does not call SetSubString(). Do not rely on SubStrings for dynamic data when using the Print Server.

2. BarTender "Embedded Data" = Static Sample Data

Fields set to "Embedded Data" type always print whatever value was last saved in the template. They are NOT dynamically populated by the Print Server.

3. "Database Field" type is the only reliable way to get dynamic data

Configure the BarTender template with a direct SQL Server connection and map fields to database columns. This is the only approach that reliably prints correct, unique data per label.

4. /printjob/print API = DB Insert + MQTT Trigger (inseparable)

The iDash core API endpoint /printjob/print always inserts a row AND publishes an MQTT message. There is no way to insert a row without triggering the Print Server.

5. Multiple MQTT triggers + "All Records" = N×N duplicate labels

Each MQTT trigger causes BarTender to query ALL pending records. If N triggers fire while N records are pending, you get approximately N×N labels. The fix is to trigger only once.

6. Direct SQL INSERT bypasses MQTT

Inserting into dbo.printjob via SQL does not trigger the Print Server. This is the key insight that enables batch printing: insert N-1 rows via SQL, then trigger once via the API for the last row.

7. The Bypass Spooler and Native iDash Engine Inject SubStrings Correctly

While the legacy ID Integration Windows service failed to call SetSubString(), both Run_Bypass_Spooler.ps1 and the new native BarTenderApiHelper.cs directly call the BarTender SDK and inject Named Data Sources in memory. This eliminates database dependencies in label templates.

8. Always verify on the actual print system

The development server and the production print server may have different configurations, different Print Server versions, and different BarTender setups. Always test on the system where printing actually occurs.

9. BarTender DLLs Require Install Order + System Reboot

The BarTender SDK DLLs (including Seagull.BarTender.Print.dll and Seagull.Interop.dll) required by the Print Server and Bypass Spooler will not be present or operational until BarTender is installed, the iDash Print Server installer has run, and the system is rebooted. Attempting to print before a reboot causes Could not load file or assembly 'Seagull.Interop.dll'.

10. Modern Native REST API & Print Engine Resolves VA Database Constraints

In secure VA hospital networks where local SQL Database instances (such as MSSQL$BARTENDER) cannot be maintained on the web server, the native iDash BarTender Integration Engine operates 100% statelessly using in-memory SubStrings and generates 200 DPI PNG label previews for the browser.

This document is intended to be provided to VA OIT Network, Server, and Database teams as a single authoritative checklist for standing up an iDash environment. Each section maps to a specific OIT discipline.

2. SQL Server Database

The database must be hosted on an existing VA-managed SQL Server instance using the standard VA SQL image. A designated VA DBA must be engaged to provision the database and login.

🚫 Constraint
ID Integration / InfinID Technologies are prohibited from creating or hosting SQL Server instances. All database work must be performed by VA OIT Database Administration.
ItemValueNotes
Database NameidashCreated empty; iDash installer builds schema on first connection
SQL LoginidashadminSQL Server Authentication (not Windows auth)
PasswordSet to VA OIT standardMust comply with VA password policy
Server Rolessysadmin, bulkadminsysadmin required for Database Restore page (orphan fix + post-restore normalization); bulkadmin required for BCP/bulk import
Database Roledb_owner (dbo)Required for schema creation, table management, and data operations

SQL Provisioning Script (for VA DBA)

-- Run as SA or sysadmin on the target SQL Server instance
CREATE DATABASE [idash];
GO

CREATE LOGIN [idashadmin] WITH PASSWORD = N'<VA_OIT_STANDARD_PASSWORD>',
    DEFAULT_DATABASE = [idash], CHECK_POLICY = ON;
GO

USE [idash];
CREATE USER [idashadmin] FOR LOGIN [idashadmin];
ALTER ROLE [db_owner] ADD MEMBER [idashadmin];
GO

-- Server-level roles
-- sysadmin: required for Database Restore (fixes orphaned user after cross-server .bak restore)
-- bulkadmin: required for BCP/bulk data import
ALTER SERVER ROLE [sysadmin] ADD MEMBER [idashadmin];
ALTER SERVER ROLE [bulkadmin] ADD MEMBER [idashadmin];
GO

7. iDash API OAuth2 Client Credentials

iDash communicates with the iDash REST API using the OAuth 2.0 client_credentials grant. Before iDash can be configured, the OAuth client ID and secret must be known. These values are stored in the iDash database and must be copied into iDash's web.config (or entered via va_site_config.aspx) as part of Step 3b of the iDash deployment.

🚫 Critical — Frequently Missed Step
If the OAuth credentials entered in iDash do not match the values stored in the iDash database, all API-driven iDash features will silently fail: print jobs will not route, the RFID Asset Locator will not resolve assets, and the Fixed Reader Configuration page will not load readers. There is no error message visible to users — only the developer console or application log will show a 401 Unauthorized.

Step 1 — Read the Existing Credentials from the iDash database

Run this on the iDash SQL Server as idashadmin or SA:

USE [idash];
SELECT webclientid, webclientsecret FROM dbo.applicationsetting;

The result will show the webclientid and webclientsecret values. Record these — they are what you will enter into iDash's web.config.

Step 2 — Default Values (if the table has never been customized)

FieldiDash DB ColumnDefault ValueiDash web.config Key
Client ID webclientid idash.web iDash_ClientId
Client Secret webclientsecret 901564A5-E7FE-42CB-B10D-61EF6A8F3654 iDash_ClientSecret
⚠ Do not assume defaults are active. The iDash installer or a previous configuration may have changed these values. Always query the database directly. Never guess or copy from another VISN — each deployment may have unique credentials.

Step 3 — Optionally Change the Credentials (Recommended for Production)

If you want to set a custom client ID and secret (recommended for VA production environments):

USE [idash];
UPDATE dbo.applicationsetting
SET webclientid     = 'visn5_idash',
    webclientsecret = '<GENERATE_A_SECURE_GUID_HERE>';
GO

After updating the database row, also update the iDash API's appsettings.json (located in the iDash WebAPI application folder) to match: 

"ConfigSettings": {
  "WebClientId": "visn5_idash",
  "WebClientSecret": "<SAME_GUID_AS_ABOVE>",
  "AuthenticationServer": "http://localhost"
}

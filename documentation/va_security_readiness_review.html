1. Executive Summary

The independent security review conducted on September 11, 2026 identified five primary security items focused on authorization consistency across directly accessible ASPX and ASHX endpoints in the iDash web application. While the main portal operates an authenticated session and role model, certain direct request handlers did not consistently enforce application-level authorization at their dispatch points or failed to fail-closed when configuration keys were missing.

All identified items have been fully remediated in the codebase, verified through automated unauthenticated test suites, and backed by defense-in-depth architectural controls including granular role-based access control (RBAC), fail-closed configuration enforcement, HTTP method restrictions, and persistent audit logging.

2. Defense-in-Depth Architecture & Controls

iDash enforces a layered security model to protect patient privacy, equipment inventory, and administrative infrastructure:

🔒 1. Boundary & Network Protection

Protected by IIS web server bindings, optional Windows Integrated Authentication, internal VA network routing, and TLS 1.3 encryption.

👤 2. Session & Cookie Guard

Session-backed authentication verified on every page load and API handler. Unauthenticated web requests redirect immediately to index.aspx?err=auth.

🛡 3. Granular Tile RBAC

Permissions checked per tile (e.g., admin_sql, admin_site_config, admin_license_manager) preventing privilege escalation even between authenticated roles.

⛔ 4. Fail-Closed API Validation

API endpoints (such as va_remote_import.ashx) require non-empty secret keys in web.config; if omitted, the endpoint enters safe mode (HTTP 503 Disabled).

⇄ 5. HTTP Method Segregation

State-changing operations (service restarts, license deletions, database modifications) strictly enforce HTTP POST, rejecting CSRF-susceptible GET requests with HTTP 405.

📝 6. Persistent Audit Trail

Administrative and security-sensitive events are written in JSON Lines format to logs/admin_audit.jsonl with automatic size trimming and rolling 90-day retention.

3. Key Findings, Technical Remediations & Evidence

Finding 01: Remote Import Authentication Configuration
Priority: Critical ✔ Remediated
Observation
The remote import endpoint only validated RemoteImportKey when a non-empty key was configured in web.config. If RemoteImportKey was omitted or left blank, the handler processed requests without validating the intended API key.
File & Location
api/va_remote_import.ashx — Lines 38–51
Implemented Remediation
Replaced the optional key check with a fail-closed enforcement policy. If RemoteImportKey is missing or whitespace, the endpoint returns HTTP 503 Service Unavailable with an explicit message that the endpoint is disabled. If configured, requests require an exact match in the X-Api-Key header or receive HTTP 401 Unauthorized.

Finding 02: SQL Upload Page Authorization
Priority: Critical ✔ Remediated
Observation
The SQL upload page did not perform its own session, role, or administrator authorization check before presenting or processing SQL upload functionality, allowing anyone knowing the direct URL to reach SQL execution.

Finding 03: Service-Control and RabbitMQ API Authorization
Priority: Critical ✔ Remediated
Observation
The service-control (api=svc) and RabbitMQ proxy (api=rmq) branches were evaluated in Page_Load before any authentication check. In addition, the RabbitMQ proxy contained embedded guest:guest credentials.
File & Location
va_site_config.aspx.cs — Lines 65–129
Implemented Remediation
  1. Moved authorization verification to the very top of Page_Load before any API branches.

5. Environmental Security Context & Scope

In enterprise and VA production deployments, the application controls documented above operate in tandem with robust infrastructure and operational security controls:

  • Network Isolation: The iDash application server is hosted within private, VLAN-segmented hospital intranet enclaves, with external access governed by VA Site-to-Site VPN or Citrix Access Gateway.
  • IIS Application Pool Identity: The application runs under a dedicated, least-privilege Windows service account with strict file ACLs on the webroot and database.
  • Database Isolation: SQL Server connections utilize encrypted channels (Encrypt=False;TrustServerCertificate=True or enterprise PKI) with parameterized queries mitigating SQL injection risks.
  • Continuous Logging: Audit logs (logs/admin_audit.jsonl and logs/login_audit.jsonl) capture IP, user, and action telemetry suitable for ingestion by enterprise SIEMs (Splunk, Microsoft Sentinel).

6. Continuous Security Hardening & Post-Certification Addendum (September 17, 2026)

Following the initial September 11, 2026 certification, subsequent feature additions (such as interactive location printing, dynamic column selection, and label preview services) were subjected to continuous security verification under the same fail-closed, defense-in-depth principles:

🔒 AJAX WebMethod RBAC & Site Scoping

All page-level [WebMethod] endpoints (including GetPrintTemplates and SubmitPrintJobs in va_location_list.aspx) enforce EnableSession = true, validate session state, and verify user site permissions via UserManager.GetAllowedCompanyIds() to block cross-facility data access or injection.

💻 Microservice Loopback Boundary

The BarTender REST preview microservice (port 5180) is bound exclusively to local host loopback (127.0.0.1), accessible solely via server-side controller delegates (BarTenderApiHelper.cs) and unexposed to external network interfaces.

📝 Digital Agreement Audit Gate

Enforced mandatory user agreement acceptance gating on all accounts with exact timestamp persistence (AgreementAcceptedDate in idash_users.json), ensuring non-repudiation across all audit actions.

⚡ DoS & SQL Lock Exhaustion Shield

Universal application of SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; across all heavy reporting and analytics queries, ensuring complex customer reports never lock production tables or disrupt line-of-business transactions.

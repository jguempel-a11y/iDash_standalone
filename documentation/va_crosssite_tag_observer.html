📡 Cross-Site Tag Observer

Architecture, implementation, and deployment guide for detecting RFID tags from other VA sites at your fixed reader location.

1. Problem Statement

VA sites (512 Baltimore, 517 Beckley, 540 Clarksburg, 581 Huntington, 613 Martinsburg) each have their own RFID-tagged assets. When a fixed reader at one site (e.g., 613 Martinsburg) detects a tag from another site (e.g., 512 Baltimore), the system needs to:

  1. Record the observation (when and where the tag was seen)
  2. Alert operations that cross-site equipment has been detected
  3. Enable reporting on cross-site asset movements
⚠ The Core Challenge The iDash API fundamentally scopes all RFID tag matching to the reader's assigned company. A reader assigned to company 7 (613 Martinsburg) will ONLY match tags belonging to company 7. Tags from company 6 (512 Baltimore) are silently discarded by the API even though the reader hardware physically reads them.

Business value: Detecting cross-site assets is where the money is. Equipment that moves between sites without documentation creates inventory discrepancies, audit failures, and lost revenue. This system catches those anomalies automatically.

2. Why the iDash API Can't Do This

The Tag Matching Pipeline

📡 FX9600 Reader
Reads ALL RFID tags
→
📩 MQTT Broker
gateway/data/FX9600_F78C85
→
⚙ iDash API
WHERE rfidtag=@tag AND companyid=7

The API lookup chain:

  1. Reader sends tag hex (e.g., 512EE575293FF) via MQTT
  2. API receives message, identifies reader as FX9600_F78C85 (companyid=7)
  3. API queries: SELECT * FROM asset WHERE rfidtag = '512EE575293FF' AND companyid = 7
  4. NO MATCH — the asset belongs to companyid=6 (512 Baltimore)
  5. Tag read is silently discarded

What We Tried (and Why It Failed)

ApproachResultWhy
Duplicate reader entries per company Failed API matches MQTT messages to ONE reader entry by physicalid. Additional entries are ignored.
Modify iDash appsettings.json N/A No cross-company configuration option exists in the compiled API binary.
Change reader's companyid Breaks 613 Would stop matching the reader's own site's tags.
💡 Key Insight The API is a compiled binary we cannot modify. The solution must work alongside the API, not replace it. The API continues handling same-site tags normally; our listener handles cross-site tags that the API ignores.

3. Solution: Cross-Site Tag Observer

A lightweight Windows Service that subscribes to the same MQTT topic as the iDash API and performs its own cross-company tag matching directly against the SQL database.

Design Principles

  • Passive listener — reads MQTT messages but never publishes. Zero impact on existing message flow.
  • Complementary, not competing — only processes tags the API already ignores. Never touches same-site tags.
  • Minimal SQL footprint — one indexed lookup + conditional update per tag read.
  • Same proven pattern — identical architecture to the iDash Print Server (MQTT ? SQL ? Action).

💡 Our Observer subscribes to gateway/data/# The wildcard # means it receives tag data from ALL readers. If you add more fixed readers in the future, the Observer automatically covers them — no config changes needed.

Message Payload Format

The FX9600 reader sends tag data as JSON. The Observer parses the tag EPC (hex) from each message:

5. Implementation Details

Core Logic (Pseudocode)

ON MQTT MESSAGE RECEIVED (topic = "gateway/data/{readerName}"):

  1. Parse readerName from topic
  2. Look up reader's HOME company from DB:
     SELECT companyid FROM reader WHERE physicalid = @readerName
     ? readerCompanyId = 7 (613 Martinsburg)

  3. Parse tag list from JSON payload

  4. FOR EACH tag in tagList:
     a. Look up asset EXCLUDING reader's own company:
        SELECT id, companyid, name
        FROM asset
        WHERE rfidtag = @tagHex
          AND companyid != @readerCompanyId

     b. IF match found (cross-site tag!):
        UPDATE asset
        SET lastobservedtime = GETDATE(),
            lastobservedlocation = @readerLocationName
        WHERE id = @assetId

        LOG: "Cross-site tag detected: {assetName} (company {companyId})
              seen at {readerLocation} (company {readerCompanyId})"

     c. IF no match:
        SKIP (either it's a same-site tag handled by the API,
              or it's an unknown tag not in any company)

Key Design Decisions

DecisionRationale
Only update lastobservedtime + lastobservedlocation These are observation fields. We do NOT update locationname (the asset's assigned location) — that's a business decision for humans.
Exclude reader's own companyid from matching The iDash API already handles same-site tags. We only fill the gap it leaves.
Use gateway/data/# wildcard subscription Auto-covers new readers without config changes. One subscription, all readers.
Cache reader?company mapping Avoid querying the reader table on every message. Refresh cache every 5 minutes.
Debounce: skip update if lastobservedtime < 60 seconds old Readers send tag data every few seconds. No need to UPDATE every time — once per minute is sufficient.

SQL Queries Used

-- 1. Get reader's home company (cached, refreshed every 5 min)
SELECT r.physicalid, r.companyid, l.name AS locationName
FROM dbo.reader r
INNER JOIN dbo.location l ON r.locationid = l.id
WHERE r.physicalid IS NOT NULL;

-- 2. Cross-company tag lookup (per tag, per message)
SELECT id, name, companyid, lastobservedtime
FROM dbo.asset
WHERE rfidtag = @tagHex
  AND companyid != @readerCompanyId;

-- 3. Update observation (only if debounce threshold passed)
UPDATE dbo.asset
SET lastobservedtime = GETDATE(),
    lastobservedlocation = @readerLocation
WHERE id = @assetId
  AND (lastobservedtime IS NULL
       OR DATEDIFF(SECOND, lastobservedtime, GETDATE()) > 60);

7. Deployment Steps

Prerequisites

  • .NET 6.0+ Runtime installed on the server
  • Access to the iDash SQL Server database
  • MQTT broker (Mosquitto) running on port 8883
  • Same server as iDash (recommended) or network access to MQTT + SQL

Step-by-Step Installation

  1. Register MQTT user — Add CrossSiteObserver to the Mosquitto password file: 
    cd C:\mosquitto
mosquitto_passwd -b passwordfile CrossSiteObserver V5MqttCrossSite2026!
  2. Copy service files — Deploy to: 
    C:\Program Files (x86)\ID Integration Inc.\CrossSite Tag Observer\
  3. Edit appsettings.json — Update connection string and MQTT credentials for the target server.
  4. Install as Windows Service: 
    sc create "CrossSiteTagObserver" binPath="C:\Program Files (x86)\ID Integration Inc.\CrossSite Tag Observer\CrossSiteTagObserver.exe" start=auto
sc description "CrossSiteTagObserver" "Detects RFID tags from other VA sites at fixed reader locations"
sc start CrossSiteTagObserver
  5. Verify — Check the log file: 
    type C:\Logs\CrossSiteObserver_log.txt
    You should see: 
    [INF] Cross-Site Tag Observer starting...
[INF] MQTT connected to localhost:8883
[INF] Subscribed to gateway/data/#
[INF] Loaded 1 reader(s): FX9600_F78C85 ? company 7 (SP1-117)
[INF] Ready. Listening for cross-site tag reads...

9. Performance Impact Assessment

ResourceImpactDetails
MQTT BrokerNONEPub/sub copies are free. Adding a subscriber doesn't increase message volume. The reader publishes once; broker copies to all subscribers.
NetworkNONEMQTT messages are already on the wire. Our subscriber is on localhost — no external traffic added.
SQL ServerNEGLIGIBLEOne indexed SELECT per tag per read cycle (~20 tags × every 5s = ~240 queries/min). Each query is sub-millisecond on an indexed rfidtag column. UPDATE only fires for cross-site tags (rare) with 60s debounce.
CPUNEGLIGIBLEJSON parsing + string comparison. No computation-heavy operations.
Memory~20 MBReader cache (handful of entries) + MQTT client buffer. Tiny footprint.
DiskMINIMALLog file only. Rolling daily, old logs can be purged.
✅ Bottom Line This service is a passive MQTT listener doing indexed SQL lookups. It adds effectively zero load to the system. The iDash Print Server — which does more work (MQTT ? BarTender ? printer) — has been running on this same server without issues. The Observer does less work than the Print Server.

Conflict Analysis

ScenarioRiskExplanation
Observer and API update same asset IMPOSSIBLE API only updates WHERE companyid = reader's company.
Observer only updates WHERE companyid != reader's company.
They are mutually exclusive by design.
Observer slows down API IMPOSSIBLE They share the MQTT broker (which handles pub/sub natively) and SQL Server (indexed queries). No locks, no contention.
Observer breaks existing data IMPOSSIBLE Observer only writes to lastobservedtime and lastobservedlocation. These are observation fields, not assignment fields. locationname (assigned location) is never modified.

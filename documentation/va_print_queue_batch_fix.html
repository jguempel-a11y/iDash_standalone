🖨 Print Queue & Batch Print Fix

Categories:
Database Connected MQTT Print Server BarTender Bug Fix — Aug 2026

⚠️ The Problem

When printing multiple labels in a single batch (from Excel Import or Asset Master), the system produced duplicate labels and stuck/orphaned print jobs. Symptoms:

SymptomWhat HappenedFrequency
Duplicate labelsSelecting 3 assets to print produced 7 labels (1 + 3 + 3)Every batch > 1
Stuck jobsJobs stuck at completed=0 with empty generatedrfid and message~75% of batch jobs
Queue bloatdbo.printjob accumulating hundreds of orphaned rowsCumulative

🔍 Root Cause: BarTender's "All Records" Database Query

BarTender label templates are configured with a database connection that uses the "All Records" query mode. This means:

⚠ Critical: Every time BarTender is triggered, it queries the printjob table for ALL rows where completed = 0 and prints every single one — not just the job it was triggered for.

The BarTender SQL Query (inside .btw templates)

Each BarTender template (.btw file) contains an embedded database connection that runs a SQL query against the iDash database. The query BarTender executes when triggered:

🗃 BarTender Template Database Query

-- This query is embedded INSIDE each BarTender .btw template file
-- (Edit via BarTender Designer → Database Setup → Database Connection)
-- Connection: OLEDB to iDash SQL Server
-- Query Mode: "All Records"

SELECT pj.id, pj.recordid, pj.templateid, pj.generatedrfid, 
       pj.completed, pj.created, pj.companyid, pj.message,
       a.name AS assetname, a.description, a.rfidtag,
       a.text1, a.text2, a.text3, a.text4, a.text5, a.text6,
       a.text7, a.text8, a.text9, a.text10,
       l.name AS locationname
FROM dbo.printjob pj
INNER JOIN dbo.asset a ON a.id = pj.recordid
LEFT JOIN dbo.location l ON l.id = a.locationid
WHERE pj.completed = 0
  AND pj.templateid = <TemplateID>
  AND pj.companyid  = <CompanyID>
ORDER BY pj.created ASC

Note: The <TemplateID> and <CompanyID> values are passed by the Print Server via MQTT message payload. The exact query may vary by template version — check your .btw file in BarTender Designer under Database Setup → Tables/Queries.

The v_printjob View

iDash also provides a convenience view for the Print Administration page:

-- dbo.v_printjob (used by iDash Print Administration UI)
CREATE VIEW [dbo].[v_printjob] AS
SELECT a.name  AS assetname,
       l.name  AS locationname,

LEFT JOIN location l ON l.id = pj.recordid

Job 1 hadn't been marked completed=1 yet when BarTender was triggered for job 2, so BarTender's "All Records" query picked up both pending jobs and printed both.

✅ The Fix: Poll-for-Completion

Instead of submitting all jobs rapidly, iDash now waits for each job to be marked completed=1 before submitting the next one. This guarantees zero pending jobs when BarTender is triggered for the next label.

Submit Job 1
→
Print & Complete
→
Poll: pending=0?
→
Submit Job 2
→
Print & Complete
→
Poll: pending=0?
→
Submit Job 3
✓ Result: Every label prints exactly once. No duplicates. No orphaned jobs.

Polling Query

Between each job submission, iDash runs this query every 500ms (up to 15-second timeout):

SELECT COUNT(*) FROM dbo.printjob 
WHERE completed = 0 
  AND companyid  = @companyId 
  AND templateid = @templateId

When the count reaches 0, the next job is submitted. If 15 seconds pass without completion, the next job is submitted anyway (fail-safe to prevent infinite hangs).

// Assumption: BarTender "All Records" picks up all pending jobs
// Reality: Only last job processed, rest orphaned at completed=0

  SubmitPrintJob(assetId, templateId, companyId);
  if (submitted < assetIds.Count)
    WaitForPendingJobsComplete(connStr, companyId, templateId, 15000);

WaitForPendingJobsComplete() — New Shared Helper

private static void WaitForPendingJobsComplete(
    string connStr, int companyId, long templateId, int maxWaitMs)
{
    int elapsed = 0;
    const int pollInterval = 500; // Check every 500ms

    while (elapsed < maxWaitMs)
    {
        Thread.Sleep(pollInterval);
        elapsed += pollInterval;

        using (var cn = new SqlConnection(connStr))
        {
            cn.Open();
            using (var cmd = new SqlCommand(
                @"SELECT COUNT(*) FROM dbo.printjob 
                  WHERE completed = 0 AND companyid = @cid 
                  AND templateid = @tid", cn))
            {
                cmd.Parameters.AddWithValue("@cid", companyId);
                cmd.Parameters.AddWithValue("@tid", templateId);
                int pending = (int)cmd.ExecuteScalar();
                if (pending == 0) return; // Safe to submit next
            }
        }
    }
    // Timeout: submit next anyway (fail-safe)
}

🗃 Print Queue Maintenance SQL

Use these queries to view and manage the print queue. Run via SSMS or the iDash DB Update Workbench.

View Queue

-- All jobs (newest first) with asset and template names
SELECT * FROM dbo.v_printjob ORDER BY created DESC;

-- Just pending/stuck jobs
SELECT id, recordid, templateid, generatedrfid, completed, created, message
FROM dbo.printjob WHERE completed = 0 ORDER BY created;

-- Job counts by status
SELECT 
    CASE WHEN completed = 1 AND message LIKE '%Successful%' THEN 'Success'
         WHEN completed = 1 AND message LIKE '%error%'      THEN 'Error'
         WHEN completed = 1 AND message LIKE '%not currently connected%' THEN 'Disconnected'
         WHEN completed = 0 THEN 'Stuck/Pending'
         ELSE 'Other' END AS Status,
    COUNT(*) AS Total
FROM dbo.printjob
GROUP BY 
    CASE WHEN completed = 1 AND message LIKE '%Successful%' THEN 'Success'
         WHEN completed = 1 AND message LIKE '%error%'      THEN 'Error'
         WHEN completed = 1 AND message LIKE '%not currently connected%' THEN 'Disconnected'
         WHEN completed = 0 THEN 'Stuck/Pending'
         ELSE 'Other' END
ORDER BY Total DESC;

Clear Queue

-- Delete all completed jobs (safe — already processed)
DELETE FROM dbo.printjob WHERE completed = 1;

-- Delete stuck/orphaned jobs (completed=0, empty generatedrfid)
-- These will never complete on their own
DELETE FROM dbo.printjob WHERE completed = 0;

-- Delete jobs older than 30 days
DELETE FROM dbo.printjob 
WHERE created < DATEADD(DAY, -30, GETDATE());

-- Nuclear: clear entire queue
TRUNCATE TABLE dbo.printjob;
💡 Tip: On production, clear the queue periodically. There's no auto-purge — completed jobs accumulate indefinitely. A monthly DELETE WHERE completed = 1 keeps it clean.

🛠️ Complete Print Flow Architecture

1. User Action

User selects assets in Excel Import or Asset Master and clicks Print.

2. iDash Server (IdashApiHelper.cs)

Calls SubmitPrintJob() which POSTs to the iDash API:
POST /api/printjob with recordId, templateId, companyId
The API inserts a row into dbo.printjob with completed=0.

3. iDash API → MQTT Trigger

The API publishes an MQTT message to the Print Server topic, notifying it that a new job is ready.

4. Print Server (Windows Service)

Receives the MQTT message, looks up the template's .btw file path, and invokes BarTender.

5. BarTender Prints

BarTender opens the template, runs its embedded SQL query (WHERE completed = 0), generates RFID data, encodes the tag, and prints the label.

6. Print Server Marks Complete

After BarTender returns, the Print Server updates the printjob row: sets completed=1, populates generatedrfid and message.

7. iDash Polls & Submits Next (NEW)

WaitForPendingJobsComplete() checks COUNT(*) WHERE completed=0 every 500ms. When it hits zero, the next job is submitted. Max wait: 15 seconds per job.

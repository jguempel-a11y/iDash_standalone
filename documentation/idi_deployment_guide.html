IDI Tagging Team Toolkit Site Deployment Guide

Documentation Type:
System Admin / Infrastructure

Applies To: iDash Web Portal (ASP.NET WebForms, .NET Framework 4.8, IIS)

1. Overview

This document describes the steps required to deploy the Tagging Team iDash Web Portal application to a new Windows machine (server or workstation) using IIS and SQL Server. It is designed to prevent common configuration errors such as HTTP Error 500.19 (0x80070021) caused by missing IIS/ASP.NET features.

  • Framework: ASP.NET WebForms
  • Runtime: .NET Framework 4.8
  • Pipeline: Uses Classic pipeline with an ISAPI handler
  • Database: Connects to a SQL Server (typically SQL Express) database named idash

2. Prerequisites

2.1 Operating System

Windows 10, Windows 11, or Windows Server with IIS support.

2.2 Software

  • Internet Information Services (IIS)
  • .NET Framework 4.8 (included with modern Windows versions)
  • SQL Server or SQL Server Express
  • iDash Web Portal files (site folder)
  • iDash database backup or copy

3. Enable Required Windows Features

Open Control Panel ←’ Programs and Features ←’ Turn Windows features on or off. Enable the following features:

Internet Information Services ←’ World Wide Web Services ←’ Application Development Features
  • ASP.NET 4.8
  • .NET Extensibility 4.8
  • ISAPI Extensions
  • ISAPI Filters
Internet Information Services ←’ Web Management Tools
  • IIS Management Console
  • IIS 6 Metabase Compatibility (recommended for classic mode)
Optional but recommended
  • Static Content
  • Default Document
  • Request Filtering

Click OK and allow Windows to install the features. After installation, restart IIS using an elevated command prompt:

iisreset

4. Deploy the Web Application

Copy the iDash Web Portal folder to:

C:\inetpub\wwwroot\iDash.WebClient

Ensure the iDash subfolder and web.config are present at:

C:\inetpub\wwwroot\iDash\web.config

5. Configure IIS Site and Application

  1. Open IIS Manager.
  2. Expand the server node and Sites.
  3. Either use Default Web Site, or create a new site pointing to C:\inetpub\wwwroot\iDash.WebClient.
  4. Right-click the iDash folder under the site and select Convert to Application.
  5. Assign an Application Pool (see next section).

6. Configure the Application Pool

The application uses a classic ISAPI handler and .NET Framework 4.x.

  1. In IIS Manager, go to Application Pools.
  2. Create a new Application Pool, for example: idashapppool.
  3. Set:
    • .NET CLR Version: v4.0
    • Managed Pipeline Mode: Classic
    • Start Mode: AlwaysRunning (optional)
  4. Right-click the App Pool → Advanced Settings:
    • Enable 32-bit Applications: False (because the handler uses Framework64)
  5. Assign this App Pool to the iDash application.

7. Verify Handler Mappings

  1. In IIS Manager, select the iDash application.
  2. Open Handler Mappings.
  3. Confirm that ASP.NET 4.x handlers exist and are enabled, such as:
    • PageHandlerFactory-ISAPI-4.0_64bit
    • ASP.NET v4.0.30319
    • ISAPI-dll

If these are missing, ASP.NET 4.8 or ISAPI features are not installed correctly.

8. Database Configuration

The web.config connection string expects default routing configurations mappings like this:

Server=localhost\sqlexpress; Database=iDash; User ID=idashadmin; Password=idashadmin;
Encrypt=True; TrustServerCertificate=True; Connect Timeout=10;

Note: SQL Server Express is the most common installation. The instance name is typically localhost\sqlexpress. On a full SQL Server installation it is just localhost. Always verify with sqlcmd -S localhost\sqlexpress -E -Q "SELECT @@VERSION".

  1. Install SQL Server or SQL Server Express.
  2. Create or restore the idash database.
  3. Create a SQL login with:
    • Login name: idashadmin
    • Password: idashadmin
  4. Map the login to the idash database and grant appropriate permissions (e.g., db_owner).

9. Application Settings (API and OAuth)

In web.config, verify and adjust the following configurations as needed for the environment:

  • iDash_ApiBase (e.g., http://localhost/api)
  • iDash_TokenUrl (e.g., http://localhost/connect/token)
  • iDash_ClientId and iDash_ClientSecret
  • EmailRecipients list

10. Print Spooler Deployment

The iDash print pipeline uses a PowerShell-based spooler (Run_Bypass_Spooler.ps1) instead of the iDash .NET Print Server service. This section is required on every server that will physically print labels.

10.1 Install BarTender

BarTender must be installed on the print server. The spooler uses the BarTender .NET SDK (Seagull.BarTender.Print.dll) which is placed in C:\Program Files (x86)\ID Integration Inc.\iDash Print Server\ by the iDash Print Server installer.

⚠ Note — BarTender DLLs & Reboot Requirement:

The BarTender SDK DLLs (Seagull.BarTender.Print.dll, Seagull.Interop.dll, etc.) required for printing from iDash will not be present or accessible until:

  1. BarTender is installed (use 64-bit edition).
  2. iDash Print Server is installed (places the Seagull DLLs into C:\Program Files (x86)\ID Integration Inc.\iDash Print Server\).
  3. The system is restarted (rebooted) to initialize BarTender system services, register native COM objects, and update system environment variables.
  • Run the iDash Print Server installer — even if you will not use the .NET service, the installer registers the BarTender SDK DLL the PS spooler depends on.
  • Verify BarTender can open the .btw template files manually before running the spooler.

10.2 Create the Print Directory and Copy Template Files

C:\idash_prints\

Copy the following into that directory:

  • All *.btw BarTender label template files
  • Run_Bypass_Spooler.ps1
  • Run_Bypass_Print_Once.ps1
  • printer_routing.json (see section 10.4)
⚠ Critical — printer_routing.json Location

The spooler reads printer_routing.json from $PSScriptRoot — the folder where the running script lives. Some installations also have a copy under C:\VA_RFID\iDash v2.2.2\iDash\printing\. If there are multiple copies on the system, editing the wrong one has no effect.

Always find the active copy before editing:

Get-ChildItem C:\ -Filter "printer_routing.json" -Recurse -ErrorAction SilentlyContinue | Select-Object FullName

Edit the copy in the same folder as the script that is actually running.

10.3 Configure Windows Printers

  • Install the BarTender-compatible printer drivers for all physical label printers.
  • Note the exact Windows printer names (including capitalization and spacing) using: 
    Get-Printer | Select-Object Name | Sort-Object Name
  • These names are used as values in printer_routing.json — they must be character-for-character identical.

10.4 Configure printer_routing.json

This file maps the .btw filename (key) to the Windows printer name (value). Create or update it in the same folder as the running script:

{
  "AW_IQ350.btw":       "Metal_Small",
  "AW_Metal_Large.btw": "Metal_Large",
  "AW_Std_Small.btw":   "Std_Small"
}

The file is read fresh on every print job — no restart is required after changes.

10.5 Configure the Template Table (SQL)

After restoring the database, verify the template table is correctly configured. The name column must exactly match the RFID tag type strings used in the iDash mobile app. This is what enables the mobile app’s “auto-map” feature to select the correct template for each tag type.

SELECT id, name, templatetype, filename, printclientid FROM template ORDER BY id;

Expected configuration:

  • name — must match the mobile app tag type exactly (e.g., IQ350, Small_Standard, Large_Metal). If this doesn’t match, auto-map always falls back to template id=1.
  • templatetype — set to match name for future compatibility.
  • filename — full path including .btw extension (e.g., C:\idash_prints\AW_IQ350.btw).
  • printclientid — set to NULL to allow all clients, or to a specific print client ID to restrict.

Fix the default template (id=1) broken filename if needed:

UPDATE template SET filename = 'C:\idash_prints\AW_IQ350.btw' WHERE id = 1;

Rename templates to match tag types for auto-map:

UPDATE template SET name = 'IQ350',          templatetype = 'IQ350'          WHERE id = 3;
UPDATE template SET name = 'Small_Standard',  templatetype = 'Small_Standard'  WHERE id = 4;
UPDATE template SET name = 'Large_Metal',     templatetype = 'Large_Metal'     WHERE id = 5;

10.6 Per-Server Printer Naming Differences

Each physical server has its own Windows printer names. Do not copy printer_routing.json between servers without updating the values.

Server AW_IQ350.btw AW_Metal_Large.btw AW_Std_Small.btw
613 (Primary) AW_Metal_IQ350 AW_Metal_Large AW_Std_Small
Field Server Metal_Small Metal_Large Std_Small

10.7 Run / Schedule the Spooler

  • Open an elevated PowerShell window and run: C:\idash_prints\Run_Bypass_Spooler.ps1
  • Or configure as a Windows Task Scheduler task set to run at startup under a local admin account.
  • The spooler polls the printjob SQL table every 3 seconds for completed=0 rows and processes them automatically.
  • Editing printer_routing.json takes effect immediately on the next job — no restart required.
  • Editing the .ps1 script requires restarting the PowerShell window or Task Scheduler task.

11. Common Errors and Resolutions

HTTP Error 500.19 – Error Code 0x80070021

Cause: Sections are locked because ASP.NET / ISAPI features are not installed.

Fix: Enable ASP.NET 4.8, .NET Extensibility 4.8, ISAPI Extensions, and ISAPI Filters locally in Windows Features.

HTTP Error 500.19 – 32-bit/64-bit mismatch

Cause: App Pool set to 32-bit while handler uses Framework64.

Fix: Set Enable 32-bit Applications = False in App Pool settings.

Raw XML of web.config shown in browser

Cause: Folder not configured as an IIS Application or not served by IIS natively.

Fix: Convert folder to Application and browse via http://localhost/...

All print jobs go to the same printer

Cause A: printer_routing.json is being read from a different path than the one you edited. Multiple copies may exist on the server.

Fix: Run Get-ChildItem C:\ -Filter "printer_routing.json" -Recurse to find all copies. Edit the one in the same folder as the running script.

Cause B: The printer name value in the JSON doesn’t exactly match the Windows printer name.

Fix: Run Get-Printer | Select-Object Name and copy/paste the exact name into the JSON.

Auto-map always selects the same template (all same .btw)

Cause: The template.name field in SQL does not match the tag type string the mobile app sends.

Fix: Run SELECT TOP 10 id, recordid, templateid FROM printjob ORDER BY id DESC — if all rows show the same templateid, fix with UPDATE template SET name = 'IQ350' WHERE id = 3 etc., matching mobile app tag type strings exactly.

BarTender document could not be opened

Cause: The template.filename column stores a bare name without extension or path (e.g., asset instead of C:\idash_prints\AW_IQ350.btw).

Fix: UPDATE template SET filename = 'C:\idash_prints\AW_IQ350.btw' WHERE id = 1;

12. Final Verification

To verify the application deployed and configured itself correctly:

  1. Restart IIS via Admin Powershell: iisreset
  2. Browse to: http://localhost/iDash/index.aspx
  3. Confirm the application loads without HTTP 500.19 errors.
  4. Verify print pipeline:
    • Confirm C:\idash_prints\ exists and contains *.btw files.
    • Confirm printer_routing.json is in the same folder as the running spooler script.
    • Submit a test print from the iDash mobile app using each tag type and confirm correct printer routing in the PS console output.
    • Verify routing messages: -> Dynamically Re-Routing Label to Hardware Printer: [PrinterName]
    • Confirm template.name matches tag type strings by checking recent print jobs: SELECT TOP 5 id, recordid, templateid FROM printjob ORDER BY id DESC — different tag types should produce different templateid values.

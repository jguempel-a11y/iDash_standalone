📡 Fixed Reader Setup & Configuration Guide

Complete end-to-end guide for deploying a Zebra FX9600 (or compatible) fixed RFID reader with iDash and iDash. Covers hardware setup, MQTT broker configuration, antenna registration, database alignment, and the Asset Master "Fixed Reader Report" feature.

✅ Deployment Validated
This guide was written during a live production deployment of a Zebra FX9600 (FX9600_F78C85) on 2026-08-25. All steps have been tested and verified.

1. Prerequisites & Architecture

System Architecture

The fixed reader data flow follows this pipeline:

FX9600 Reader → MQTT (port 1883 TCP) → RabbitMQ 4.3.5 → iDash AntennaLocationService → SQL Database → iDash Dashboard
✅ Updated Aug 2026: Fixed reader tag data now routes through RabbitMQ 4.3.5 on port 1883 (TCP). The iDash embedded broker (port 8883/TLS) remains in use for label printing only. See RabbitMQ Setup Guide for installation details.

Required Components

iDash Web PortalCurrent (Kestrel-hosted)Includes built-in MQTT broker on port 8883 (used for printing only)

ⓘ No Redis Required
iDash can function without Redis. Set "UseRedis": false in appsettings.json. Tag lookups will fall back to direct SQL queries via IAssetRepository.GetByVTagId(). Redis is an optional performance cache, not a dependency.

2. Hardware Setup (Zebra FX9600)

1 Physical Installation

  • Mount the FX9600 in the target location (doorway, corridor, supply room)
  • Connect antennas to ports 1–4 (or 1–8 for 8-port models)
  • Connect Ethernet cable to your facility network
  • Power on and wait for boot (LED indicators should stabilize)

2 Access the Reader Web UI

Navigate to the reader's IP address in a browser: https://192.168.x.x

Default credentials: admin / change (change on first login).

3 Configure the MQTT Endpoint

Navigate to Communication → Endpoints in the FX9600 web UI.

⚠ Critical Naming Rules
  • NO SPACES in usernames, topic names, or reader names
  • Use underscores (_) to separate words
  • The username on the FX9600 must exactly match the username stored in the iDash reader table
  • The reader name (physicalid) should match the FX9600's identity string

4 Enable Tag Reads

In the FX9600 web UI, go to Operation Mode and set the reader to Autonomous or Inventory mode. Ensure at least one antenna port is enabled and set to an appropriate power level for your deployment area.

3. MQTT Broker Configuration

iDash Built-in MQTT Broker

iDash Web Portal includes a built-in MQTT broker that starts automatically with the Kestrel process. It listens on port 8883 (TLS) using the certificate at:

c:\inetpub\wwwroot\iDash.WebClient\mycert.pfx

You can verify the broker is running by checking the log at startup:

# Look for this line in C:\Logs\WebClient_log*.txt
Starting MQTT Server with encryption on port 8883 from PFX c:\...\mycert.pfx
MQTT Server start successful? True

TLS Certificate Requirements

  • Must be in PFX format
  • The FX9600 must trust the CA that signed the certificate, OR have certificate validation disabled (for self-signed certs, the FX9600 has a "Validate Certificate" checkbox in the MQTT endpoint settings)
  • If using a self-signed cert, uncheck "Validate Server Certificate" on the FX9600

Verifying MQTT Connectivity

After configuring the reader, verify the TCP connection is established:

# PowerShell — check for MQTT connection from reader IP
netstat -ano | Select-String "8883.*192.168.4.47"

# Expected output:
TCP  192.168.4.48:8883  192.168.4.47:55030  ESTABLISHED  42428
✅ Heartbeat Verification
Once connected, the FX9600 sends periodic heartbeat messages on the management topic. The iDash reader.lastseen column updates with each heartbeat. If lastseen is more than 5 minutes stale, the reader has disconnected.

4. Reader Registration in iDash / iDash

Automatic Registration

When a reader connects to the MQTT broker for the first time, iDash automatically creates a reader record in the database. However, critical fields often need manual correction:

⚠ Warning: iDash UI May Overwrite SQL Changes
If you manually correct reader settings via SQL, do NOT subsequently edit the reader via the iDash Angular UI (http://localhost/#!/admin/editreader/21). Saving from the UI overwrites fields like username, password, and devicesettings with whatever is in the form — which may be blank.

Manual SQL Registration

If auto-registration doesn't populate fields correctly:

-- Update reader with correct MQTT credentials and settings
UPDATE reader SET
  name = 'FX9600_F78C85',
  physicalid = 'FX9600_F78C85',
  ipaddress = '192.168.4.47',
  username = 'fx9600_f78c85',
  password = 'FX9600mqtt2026!',
  mqttcontroltopic = 'gateway/cmd/FX9600_F78C85',
  devicesettings = 'UpdateLocation=Yes|TagTimeout=60',
  deviceregistered = 1,
  companyid = 7
WHERE id = 21;

iDash Reader Configuration Page

iDash provides a reader configuration UI at va_reader_config.aspx. This page can add antennas, update reader names, and toggle Update Location on/off. For full documentation see Reader Configuration Documentation.

5. Antenna Configuration

Each reader needs at least one antenna record in the antenna table. Without it, iDash may not process tag reads from the reader.

Adding via iDash Reader Config UI

Navigate to va_reader_config.aspx → click your reader → "Add Antenna".

Adding via SQL

-- Insert antenna for reader ID 21
INSERT INTO antenna (readerid, antennanumber, locationid, companyid)
VALUES (21, 1, 40912, 7);

-- Verify
SELECT * FROM antenna WHERE readerid = 21;
ⓘ Location & Company Must Match
The antenna's companyid and locationid must be consistent with the reader's company and a valid location within that company. Mismatched company IDs will prevent tag lookups from finding matching assets.

6. Database Alignment (Company, Tags, vtagid)

⚠ This is the #1 cause of "Tag Not Provisioned" errors
iDash tag lookups are scoped by company AND require the vtagid field to be populated. If either condition is not met, tags will be logged as "Tag Not Provisioned" even though they exist in the asset table.

Company Alignment

The reader's companyid must match the companyid of the assets you want it to detect. iDash queries: WHERE vtagid = @tag AND companyid = @readerCompany

If your reader is in Company 7 but your tags are in Company 6, every tag read will fail. Either move the reader to the correct company or move the test tags.

vtagid Population

iDash uses vtagid — not rfidtag — as the primary lookup key for real-time tag processing. If your assets were imported with only the rfidtag column populated, you must copy the values to vtagid:

-- Populate vtagid from rfidtag for all assets that need it
UPDATE asset
SET vtagid = rfidtag
WHERE rfidtag IS NOT NULL
  AND rfidtag != ''
  AND (vtagid IS NULL OR vtagid = '');

-- Result: Updated 536,080 assets
ⓘ Why both rfidtag and vtagid?
  • rfidtag — The physical RFID tag's EPC value. Used for mobile scanning and display.
  • vtagid — The virtual tag ID used by the real-time event processing engine (BatchBeaconWorker). This is the lookup key for fixed reader observations.
For simple deployments (no BLE/GPS V-Tags), set vtagid = rfidtag.

iDash API Client Company Scope

The iDash API client (configured in web.config as iDash_ClientId) is scoped to a specific company in the clientapp table. The API will only return readers and assets belonging to that company.

-- Check API client company scope
SELECT clientid, companyid FROM clientapp WHERE clientid = 'v512';
-- Result: companyid = 7

If the reader is moved to a different company, the API client's companyid must also be updated, or the iDash dashboard will show "No readers found."

7. Verification & Troubleshooting

Step-by-Step Verification

StepHow to CheckExpected Result
1. MQTT Connection netstat -ano | Select-String "8883" ESTABLISHED connection from reader IP
2. Heartbeat SELECT lastseen FROM reader WHERE id = 21 Timestamp within last 2 minutes
3. Tag Reads Arriving Check C:\Logs\WebClient_log*.txt Lines with "Tag with ID" or successful processing
4. Asset Matching SELECT lastobservedtime FROM asset WHERE vtagid = 'your-tag-epc' Recent timestamp (not NULL)
5. iDash Dashboard Navigate to va_fixed_reader.aspx Reader shows Online, tag observation counts > 0

Common Errors & Fixes

❌ "Tag with ID xxxxxx is not in the database"

CauseFix
vtagid is emptyRun UPDATE asset SET vtagid = rfidtag WHERE ...
Company mismatchEnsure reader and asset have the same companyid
Tag genuinely not in DBAsset needs to be imported first. Tags like E280117... are factory EPCs that may not be provisioned.

❌ "Tag Not Provisioned" events in the event table

Same root causes as above. Check the rfidtag column in the event record, then query:

SELECT id, companyid, vtagid, rfidtag FROM asset
WHERE vtagid = 'THE_TAG_EPC' OR rfidtag = 'THE_TAG_EPC';

❌ Reader shows as "Offline" in iDash

  1. Verify MQTT TCP connection: netstat -ano | Select-String "8883"
  2. Check reader lastseen timestamp — if stale, the reader disconnected
  3. Check connectionstatus in the reader table
  4. After an IIS restart, the MQTT broker restarts and the reader must reconnect (may take 1–2 minutes)

❌ Duplicate readers appearing

iDash auto-registers a new reader record each time an unrecognized device connects via MQTT. After an IIS restart, if credentials/physicalid don't match the existing record, a duplicate is created. Delete the duplicate via the API:

# Delete duplicate reader via iDash REST API
DELETE /api/readers/?ids=23&madeBy=iDash

❌ LICENSE KEY ERROR

"License only allows for 5 companies but 7 companies are found" — this does not block tag processing but will appear in logs. Contact InfiniDTech support for a license key update.

❌ After IIS Restart, no tags are being processed

  1. Wait 60–90 seconds for the MQTT broker to restart and the reader to reconnect
  2. Verify the MQTT TCP connection re-established
  3. If the in-memory tag cache was invalidated, an IIS restart rebuilds it at startup

8. Asset Master — Fixed Reader Report

The Asset Master page (va_asset_master.aspx) includes a 📡 Fixed Reader Report button that instantly filters the grid to show only assets observed by a fixed reader.

New Columns

ColumnDB FieldDescription
Last Observed lastobservedtime Date/time the fixed reader last detected this asset's RFID tag. Displays with full time (e.g., 08/25/2026 9:55 AM).
Observed Location lastobservedlocation The location name where the reader observed the asset (from the antenna's assigned location).

Both columns are hidden by default. Enable them via the COLUMNS bar or click the Fixed Reader Report button (which auto-enables them).

Fixed Reader Report Toggle

The green 📡 Fixed Reader Report button in the page header acts as a toggle:

  • Click once → Activates the filter. Button turns amber with a checkmark. A time range dropdown appears.
  • Click again → Deactivates the filter. Button returns to green. All assets shown.

Time Range Options

OptionSQL FilterUse Case
Todaylastobservedtime >= CAST(GETDATE() AS DATE)Current shift validation
This Weeklastobservedtime >= DATEADD(DAY, -7, GETDATE())Weekly activity review
This Monthlastobservedtime >= DATEADD(MONTH, -1, GETDATE())Monthly inventory report (default)
All Timelastobservedtime IS NOT NULLComplete history of all reader-observed assets

Export & Reporting

The Fixed Reader Report filter is fully integrated with Export Excel. When the filter is active:

  • Click 💾 Export Excel → downloads an XLSX with only the filtered assets
  • The export respects all active filters (site, status, CMR, location) plus the fixed reader time range
  • The Last Observed and Observed Location columns are included in the export
✅ Inventory Tool Use Case
Clients can use the Fixed Reader Report as a passive inventory tool:
  1. Select a site from the company dropdown
  2. Click 📡 Fixed Reader Report
  3. Select "This Month" (or preferred range)
  4. Export to Excel for the ENNX inventory report
This creates an inventory report of all assets the fixed readers have observed, without requiring manual scanning. Sort by "Last Observed" descending to see the most recently detected assets first.

Detail Panel Enhancement

When clicking on an asset row, the detail panel now includes a "Fixed Reader Observation" section showing:

  • Last Observed: Full date/time of the last reader detection
  • Observed Location: The location where it was seen

Assets never observed by a reader will show "Not observed" in gray.

10. Developer Notes

Tag Processing Pipeline (BatchBeaconWorker)

The tag processing pipeline in iDash works as follows:

  1. FX9600 publishes a tag read message on the data topic via MQTT
  2. iDash MessageInterceptor receives the message and queues it for processing
  3. BatchBeaconWorker dequeues the tag and calls dataCache.GetAssetByVTag(tagId)
  4. If UseRedis: false, the cache falls through to IAssetRepository.GetByVTagId(companyId, vtagId)
  5. If a matching asset is found:
    • Updates lastobservedtime, lastobservedlocation, readerid
    • If UpdateLocation=Yes in reader settings, also updates locationid
  6. If no match: calls InsertTagNotProvisioned(vTagID, rfidTag) → creates an event record

11. Lessons Learned

Key insights from the 2026-08-25 deployment:

#LessonImpact
1 vtagid must be populated. The BatchBeaconWorker looks up assets by vtagid, not rfidtag. Empty vtagid = "Tag Not Provisioned" for every read. 536K assets had empty vtagid. Required bulk SQL update.
2 Company IDs must match. Reader company must equal asset company. API client company must equal reader company. Mismatched company caused zero tag matches and "No readers found" in iDash.
3 NO SPACES in MQTT fields. Usernames, topic names, and reader names must not contain spaces. Use underscores. Spaces in username/topic caused MQTT auth failures.
4 iDash UI can overwrite SQL changes. Editing a reader via the iDash Angular UI resets manually configured SQL fields. Lost credentials and device settings twice.
5 Duplicate readers on IIS restart. After an IIS restart, the MQTT broker restarts. If the reader reconnects before the old record is updated, iDash may auto-register a duplicate. Required deleting duplicate reader records.
6 Redis is optional. UseRedis: false in appsettings.json is a valid production configuration. No need to install Redis. Simplified deployment — no third-party dependencies.
7 LLRP conflicts. If another LLRP client is connected to the FX9600, new connections will fail with "There is already a connected LLRP client." Use MQTT mode instead of LLRP. Resolved by using MQTT endpoint exclusively.
8 IP address can be 0.0.0.0 for MQTT. Since the reader connects to the server (not the other way around), the reader's IP in iDash is for display only when using MQTT. Simplifies config for DHCP-assigned readers.

📧 Email Recipient Storage — JSON File Migration

Technical reference documenting the architectural change that moved email recipient storage from web.config appSettings to a standalone JSON file. This change was made on June 29, 2026 to fix a critical session-loss bug that forced users to re-authenticate every time an email address was added or removed.

Status: DEPLOYED
Email recipients are now stored in config/email_recipients.json. Existing recipients from web.config are auto-migrated on first access — no manual steps required.

The Problem

When a user navigated to Report Automation Setup (va_report_automation.aspx) and added or removed an email recipient, the system would immediately force them back to the login screen, requiring re-authentication as idashadmin or their current user account.

This happened every single time a recipient was added or removed, making the email configuration workflow effectively unusable without repeatedly signing in.

Root Cause: IIS Application Pool Recycle

The email recipient list was previously stored in web.config as a semicolon-delimited string in the EmailRecipients appSetting key: 

<add key="EmailRecipients" value="JGUEMPEL@ID-INTEGRATION.COM" />

The EmailHelper.SaveRecipients() method in App_Code/EmailHelper.cs would call WebConfigurationManager.OpenWebConfiguration("~") followed by config.Save() to persist changes. This wrote directly to the physical web.config file on disk.

IIS monitors web.config for any file system changes. When the file is modified, IIS automatically triggers a full application pool recycle. This destroys all in-memory session state, including Session["IdashUserRole"] and Session["IsAdminAuthenticated"].

After the recycle completes, the postback response arrives at the browser, but the server-side session is gone. On the next page load, the session check in va_report_automation.aspx.cs (line 53) sees a null role and redirects back to index.aspx (the login page): 

if (Session["IdashUserRole"] == null || 
    (Session["IdashUserRole"].ToString() != "admin" && !hasTileAccess))
{
    Response.Redirect("index.aspx");
    return;
}
⚠ Key Insight: This is not a bug in the authentication system. The authentication works correctly. The problem is that saving recipients to web.config is a destructive operation that nukes the entire application state. Any data stored in web.config that is frequently modified by users will exhibit this same behavior.

The Fix: JSON File Storage

Email recipients are now stored in a standalone JSON file at: 

~/config/email_recipients.json

This file is a simple JSON array of email address strings: 

["JGUEMPEL@ID-INTEGRATION.COM","user2@example.com","user3@example.com"]

Writing to this file does not trigger an IIS application pool recycle. Sessions remain intact, and users stay logged in.

Automatic Migration

On first access after deployment, the GetRecipients() method checks for the JSON file. If it doesn't exist, it falls back to reading the legacy EmailRecipients key from web.config and automatically writes those values to the new JSON file. After this one-time migration, all subsequent reads and writes use the JSON file exclusively.

Files Changed

File Change
App_Code/EmailHelper.cs Rewrote GetRecipients(), AddRecipient(), RemoveRecipient(), and SaveRecipients() to use config/email_recipients.json instead of web.config. Added auto-migration fallback. Simplified read-only helper methods (GetFromName(), GetFromEmailAddress(), GetDefaultSubject()) to use the lightweight AppSettings indexer instead of opening the full configuration object.
va_ennx_mobile.aspx.cs Replaced the inline GetEmailRecipients() method (which duplicated the old web.config read logic) with a delegate to the shared EmailHelper.GetRecipients() method for consistency.
config/email_recipients.json [NEW] Auto-created on first access. Stores the email recipient list as a JSON array.

What Still Uses web.config

Only SMTP connection settings (host, port, username, password, from address) remain in web.config. These are rarely changed and are typically only set once per site deployment via the Site Configuration page (va_site_config.aspx). The session loss on that page is acceptable because site config is a one-time setup operation, not a frequent workflow.

The following keys remain in web.config appSettings (read-only during normal operation):

  • SMTP_Host — SMTP server hostname
  • SMTP_Port — SMTP port (typically 587)
  • SMTP_User — SMTP authentication username
  • SMTP_Password — SMTP authentication password
  • SMTP_FromEmail — sender email address
  • SMTP_FromName — sender display name
  • Default_EmailSubject — default subject line override

Developer Notes

Adding Recipients Programmatically

// Add a recipient (no session impact, no app pool recycle)
EmailHelper.AddRecipient("newuser@example.com");

// Remove a recipient
EmailHelper.RemoveRecipient("olduser@example.com");

// Get the full list
List<string> recipients = EmailHelper.GetRecipients();

Rule of Thumb

Never write frequently-changed data to web.config. Use JSON files in the config/ directory for any settings that users may update during normal operation. Reserve web.config for infrastructure settings that change only during initial deployment or major reconfiguration.

Database Recovery Data Loss Fix New 08/26

Background: What Happened

⚠ Root Cause

The System Diagnostics page (va_system_diagnostics.aspx) previously included a "Batch Update Simulation" test that used PUT /api/asset to simulate mobile scanner syncs. However, the PUT payload only included 6 fields (id, name, companyid, description, text1, text3). The iDash API interpreted all omitted fields as NULL, wiping out rfidtag, serial numbers, text fields, location data, and other asset information on every record the test touched.

✅ Fix Applied

The diagnostics test has been converted to a read-only GET /api/asset/{id} call. It still validates API auth, license limits, and connectivity but no longer modifies any data. This fix must be deployed to all systems running iDash diagnostics.

How to Identify Damaged Records

All records modified by the old test are stamped with a unique marker:

SELECT id, name, rfidtag, lastmodified, lastmodifiedby
FROM dbo.asset
WHERE lastmodifiedby = 'iDashDiag'
ORDER BY id;

The lastmodified timestamp shows exactly when the damage occurred. Records created before that timestamp are the ones to recover.

What Was Preserved vs. Lost

Status Fields
✅ Preserved id, name, companyid, description, text1, text3, created, disposalstatus, maintenancemethod
❌ Wiped to NULL rfidtag, assettype, departmentcode, text2, text4–text20, listvalue1–listvalue5, date1–date5, locationid, checkinstatus, checkedoutto, lastobservedlocation, lastobservedtime, lastmodified, lastmodifiedby, and all maintenance/disposal fields

Recovery Tool: Cross-System Restore

This script restores a .bak backup file on a separate machine, extracts the clean data for the damaged asset IDs, and generates portable UPDATE statements you can paste into SSMS on the damaged system.

Prerequisites

  • A .bak file from the damaged system taken before the diagnostics test ran
  • A SQL Server instance to restore the backup on (can be any machine, doesn't need to be the damaged one)
  • Enough disk space for the temporary restore (auto-cleaned after)

Step-by-Step

Step Action
1 Copy the .bak from the damaged system to the recovery machine
2 Open va_idashdiag_recovery.sql in SSMS on the recovery machine
3 Edit the 5 configuration variables at the top (backup path, temp DB name, file paths, target DB name)
4 In SSMS: Query > Results To > Results to Text (Ctrl+T), then set Tools > Options > Query Results > Max Characters = 8000
5 Run the script — it restores the backup, generates UPDATE statements, and prints them
6 Copy the generated UPDATE output (everything between BEGIN TRANSACTION and COMMIT)
7 Paste and run in SSMS on the damaged system
8 Run the cleanup section at the bottom to drop the temp database

Customizing the Asset ID List

The script includes a hardcoded list of asset IDs (177324–177367) from the original incident. To recover different assets, update the WHERE id IN (...) clause on line ~110. You can get the full list from the damaged system:

-- Run on the DAMAGED system to get the ID list:
SELECT id FROM dbo.asset WHERE lastmodifiedby = 'iDashDiag' ORDER BY id;

FAQ: Why Do Values Have N’ Prefix?

The generated UPDATE statements use N'value' syntax (e.g., N'613EE10047FF'). This is standard SQL Server syntax for Unicode (NVARCHAR) string literals. The N is not stored in the data — it tells SQL Server to treat the string as Unicode. The actual stored value is just 613EE10047FF.

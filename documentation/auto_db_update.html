Auto Database Update & Cross-Site Merge SOP

This document completely outlines the architecture and proper operating procedures for merging remote AssetWorx database backups and flat-files into the master local system using the automated va_autodbupdate.aspx and corresponding SQL merging engine.

Intelligent Data Sync Active: The current synchronization framework natively protects all core master data variables (last known locations, last inventoried dates, structural records) during the merge process.

1. Accepted File Formats & Loading Areas

The Auto DB update module polls the designated watch folder continuously (Default: C:\VA_RFID\va_dbupdate\autoload).

  • cart1.assetworx_daily_full.bak - Represents a full SQL Backup file exported directly from an off-site master server.
  • data.txt / data.xlsx - Represents flat data output files exported via ENNX/legacy table reports into the root.

2. Advanced Cross-Site Backup (.BAK) Merging

When the engine detects a remote SQL backup (.bak), it routes the workload away from the default blind insertion routine to an incredibly secure database reconciliation pipeline (va_bak_merge.sql).

  1. Temp DB Spin-up: The backup file is restored strictly to an isolated temporary sandbox database (assetworx_merge_temp) so no direct interactions occur until verified.
  2. Upsert Normalization: Data flows natively bridging the temp server and the actual AssetWorx system checking explicitly for duplicate RFIDs and Names.
  3. Master Field Protections:
    • lastinventoried is updated ONLY if the imported record has a newer/fresher ping.
    • lastobservedlocation relies strictly on the most recently parsed area scans.
    • disposalstatus (listvalue1) mapping handles "TURNED IN", "MISSING", preventing null-overwrites affecting deployment analytics.

3. The Intelligent CMR Filter

CRITICAL SAFETY PROTOCOL: Past database migrations uncovered massive corruption vectors where remote sites shoved extended nomenclature tags (e.g. HOIST PATIENT CEILING) into their CMR database column (text8).

To safely pull CMR IDs from remote databases without poisoning the master dataset:

  • The script imports text8 from incoming backups through an intelligent firewall.
  • If an incoming CMR string contains multiple spaces, exceeds 10 characters, lacks any dashes (-), or doesn't start with "CMR", the script identifies it as an invalid nomenclature hazard.
  • Invalid payloads are immediately nulled out before insertion, protecting your CMR dashboard filters.
  • Validly formatted CMRs (e.g. 512-A00400) easily slip through to map to the new database nodes intact.

4. Executing an Update

To run an update manually:

  1. Drop the properly named .bak file or .txt file directly into C:\VA_RFID\va_dbupdate\autoload.
  2. Open the Database Automation Panel (va_autodbupdate.aspx) in your browser.
  3. Click Run Database Automation.
  4. Once processed, the payload file will be cleanly sorted into the /loaded archive folder timestamped for reference.

1. Overview & Purpose

va_system_diagnostics.aspx is a one-click health-check dashboard for the iDash platform. It was created to solve a recurring problem: after a database restore, a server migration, or a reboot, the system can appear to work for web users but silently fail for the mobile app in batch mode.

Batch mode failures are hard to reproduce without real RFID hardware. This page simulates the exact same API path that the mobile app takes when syncing offline scans — calling PUT /api/asset?madeBy=iDashDiag for each asset — which triggers AssetController.Update and its license check, just as the mobile app does.

Background: The original batch-mode error was “License limits exceeded for companies or servers” appearing in the API log at C:\Logs\WebClient_log.txt. The root causes were:
  • A DB restore that left the old server’s license key (MAC E41FD59D1DEF) in dbo.applicationsetting instead of the new server’s MAC.
  • superadmin.companyid was set to a specific company instead of NULL (global access), which caused tenant-count mismatches in the license check.
  • Stale entries in dbo.serverstatus from the old server.

4. Test Suite — What Each Test Does

🔑 Test 1: API Authentication

Sends a POST to /connect/token with grant_type=client_credentials using the credentials from web.config keys iDash_ClientId / iDash_ClientSecret.

Pass: receives an access_token and caches it for subsequent tests.
Fail: API is down, IIS not running, wrong client credentials, or network issue.

The client credentials live in dbo.clientapp. Query: SELECT clientid, secret FROM dbo.clientapp. The default fallback uses iDash_ClientId=v512 from web.config.

🗃 Test 2: Database & License

Connects directly to the iDash SQL database and checks:

  • Number of companies in dbo.company
  • Total asset count in dbo.asset
  • Whether dbo.applicationsetting.licensekey is present (not null/empty)
  • The company name and schema version stored in settings
If the license key is shown as “MISSING”, batch mode will always fail. The license must be applied via the iDash Settings UI or by directly updating dbo.applicationsetting SET licensekey = '...'.

🔌 Test 3: Server Registrations

Queries dbo.serverstatus and lists every registered service (name, type, version, last-seen time). A healthy system typically has:

  • Alarm Monitoring Service — always present
  • Print Server - Batch — present when BarTender/print server is running
After a DB restore from another server, stale rows from the old server may remain here. If the license limits “Servers” count (e.g. 1 server allowed), extra rows can trigger the batch-mode license error. Fix: DELETE FROM dbo.serverstatus WHERE name != 'YOUR_SERVER_NAME'

📥 Test 4: Batch Update Simulation

This is the critical test. It mimics exactly what the mobile app does in offline batch sync mode:

  1. Queries N assets from dbo.asset (configurable, default 5)
  2. For each asset, sends PUT /api/asset?madeBy=iDashDiag with the asset JSON in the body
  3. Records per-asset timing and catches any errors
  4. Specifically detects the string “License limits exceeded” in the response body

Why PUT without ID in the URL? The iDash API route is [HttpPut] api/[controller] — the asset ID is in the JSON body, not the URL path. PUT /api/asset/{id} returns 405 Method Not Allowed.

Expected performance: ~300–400ms per asset on a local server. Times above 1 second suggest SQL or API performance issues. This number is useful as a regression baseline when upgrading iDash.

5. How to Run Diagnostics

  1. Log in to iDash at http://[server]/iDash/
  2. Click the 📊 System Diagnostics tile on the home page
  3. Select the Company / Site to filter the batch test assets (or leave as “All Companies”)
  4. Set Batch Size (1–50). Default of 5 is sufficient for a health check; use 20+ for load testing
  5. Click ▶ Run Diagnostics
  6. A loading overlay appears while the 4 tests run (typically 3–10 seconds total)
  7. Results display as animated cards with green PASS / red FAIL indicators
To run without a browser (e.g. on a remote server via RDP), use the PowerShell script: C:\va_rfid\V5Data\tools\Invoke-BatchModeTest.ps1 -BatchSize 10 -CompanyId 3

6. Reading the Results

The summary bar shows four counters:

Stat Meaning
Tests Passed X / Y live tests (excludes “Coming Soon” placeholders)
Total Runtime End-to-end wall-clock time for all tests in milliseconds
Tests Run Number of active (non-placeholder) tests executed
Coming Soon Placeholder tests not yet implemented (MQTT, RabbitMQ, Readers)

Each test card shows:

  • Top color bar: green = pass, red = fail, dashed = coming soon
  • Duration (top-right): milliseconds for that specific test
  • Message: human-readable result summary
  • Details: technical context (endpoint URL, client ID, error body snippet)

Common Failure Patterns

Test Fails Likely Cause Fix
API Authentication IIS app pool recycled; API not running; wrong client ID/secret Check IIS; verify dbo.clientapp; restart app pool
Database & License — “MISSING” License key cleared by DB restore or Settings page Re-apply license via iDash Settings → License tab
Batch Update — LICENSE LIMITS EXCEEDED License MAC doesn’t match server; too many tenants/servers Check applicationsetting.licensekey; clean serverstatus; fix superadmin.companyid = NULL
Batch Update — 500 error Asset payload missing required fields; API validation failed Check API log at C:\Logs\WebClient_log.txt

7. Email Report

After running tests, click 📧 Email Report to send a full HTML diagnostic report to all addresses configured in iDash/config/email_recipients.json.

The email includes:

  • Server hostname and run timestamp
  • Health summary (X/Y passed)
  • Table of all tests with status, duration, and details
  • Total runtime footer
Email settings (SMTP host, from address, etc.) are configured in web.config under SMTP_Host, SMTP_Port, SMTP_User, SMTP_Password. See Support Request documentation for SMTP setup details.

8. Deploying to WV / Remote Sites

The diagnostics page is designed to self-configure from the local web.config. To deploy to the West Virginia site (VISN5-8) or any other remote site:

  1. Copy va_system_diagnostics.aspx and va_system_diagnostics.aspx.cs to C:\inetpub\wwwroot\iDash\ on the target server
  2. No config changes needed — it reads iDash_TokenUrl, iDash_ClientId, iDash_ClientSecret, and iDash_ApiBase from that server’s web.config
  3. First check what client credentials exist on that server: SELECT clientid, secret FROM dbo.clientapp
  4. Update web.config if the iDash_ClientId key is missing
WV-specific check: The WV system (VISN5-8) had its DB restored from the BURBOT reference system. Verify the license reflects the VISN5-8 MAC address by checking: SELECT company, LEFT(licensekey,60) FROM dbo.applicationsetting. The preview should start with VA West Virginia.

10. Developer Notes

Authentication Flow

The diagnostics page authenticates using OAuth2 client_credentials grant (same flow as IdashApiHelper.cs). Token endpoint: 

POST /connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=v512
&client_secret=[from web.config iDash_ClientSecret]

Response contains access_token used as Bearer on all subsequent calls.

Batch Update Endpoint

The confirmed working update endpoint is: 

PUT /api/asset?madeBy=iDashDiag
Authorization: Bearer {token}
Content-Type: application/json

{"id":3,"name":"512 EE10001","companyid":6}
NOT PUT /api/asset/{id} — this returns 405.
NOT GET /api/asset/{id} for reading — this returns an empty body.
The route is [HttpPut] api/[controller] with the ID in the request body.

C# Compatibility

The IIS ASPX compiler on this system uses C# 5. The following C# 6+ features must be avoided:

  • Expression-bodied members (=> expr on methods) — use full { return ...; }
  • Index initializers ({ ["key"] = value }) — use .Add("key", value)
  • String interpolation ($"...") — use string.Format(...)
  • Null-conditional operators (?.) — use explicit null checks

Adding Tests

// In va_system_diagnostics.aspx.cs
private DiagnosticResult TestMyNewCheck()
{
    var sw = Stopwatch.StartNew();
    try
    {
        // ... your test logic ...
        sw.Stop();
        return new DiagnosticResult {
            TestName = "My New Check",
            Category = "mqtt",        // used to group cards in the ASPX
            Icon     = "&#128225;",
            Passed   = true,
            Message  = "Connected OK",
            DurationMs = sw.ElapsedMilliseconds,
            Details  = "Host: localhost:8883"
        };
    }
    catch (Exception ex)
    {
        sw.Stop();
        return new DiagnosticResult {
            TestName="My New Check", Category="mqtt", Icon="&#128225;",
            Passed=false, Message=ex.Message, DurationMs=sw.ElapsedMilliseconds
        };
    }
}

// Then call it in RunAllTests():
TestResults.Add(TestMyNewCheck());

PowerShell Equivalent

The PowerShell script Invoke-BatchModeTest.ps1 does the same batch update test and is useful for running on remote servers without browser access: 

# Run on VISN5-8 via RDP
.\Invoke-BatchModeTest.ps1 `
    -BaseUrl http://localhost `
    -ClientId "v512" `
    -ClientSecret "YOUR_SECRET" `
    -BatchSize 10 `
    -CompanyId 3

11. Troubleshooting

Symptom Cause Resolution
Page redirects to ../index.aspx immediately Not logged in to iDash, or insufficient tile access Log in to iDash first; add admin_diagnostics tile to user’s tile list
Company dropdown is empty DB connection string misconfigured; dbo.company is empty Check web.config connection string; verify at least 1 company in DB
Tests hang for >30 seconds API is not responding (IIS recycled, app pool stopped) Open IIS Manager → restart iDash app pool; check C:\Logs\WebClient_log.txt
Email button does nothing No recipients configured, or SMTP not set up Add recipients via iDash Admin → Email Settings; verify SMTP in web.config
Batch test 500 errors Asset payload missing required fields for API validation Check C:\Logs\WebClient_log.txt for the full exception. May indicate schema changes in iDash update.

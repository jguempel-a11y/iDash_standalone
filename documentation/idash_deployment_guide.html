🚀 iDash Complete Deployment Guide

This is the step-by-step technical playbook for recreating the iDash portal on a new Windows Server. It assumes the engineer has basic experience with IIS, SQL Server Management Studio (SSMS), and Windows Task Scheduler.

Prerequisites: Windows Server (2016+), IIS with ASP.NET 4.8 enabled, and SQL Server (or Express) with the iDash database. The database can be either restored from an existing .mdf / .bak, or a completely fresh installation (new DB) which can be seeded using iDash's built-in ingestion tools.
⚡ Shortcut: After completing Steps 1–2 (file copy and IIS setup), the Site Configuration page (va_site_config.aspx) provides a graphical form to complete Steps 3–4 without manually editing web.config. It writes changes directly and includes a built-in deployment checklist. Navigate to http://localhost/iDash/va_site_config.aspx after first boot.
1

File System Placement & Directory Scaffolding

iDash operates out of the web root, but relies on several external directories for logging, print spooling, and file drop-offs.

  1. Copy the entire iDash folder into your web root: C:\inetpub\wwwroot\iDash\iDash.
  2. Ensure the IIS_IUSRS group has Read & Execute permissions on this folder, and Write permissions on the following subdirectories:
    • iDash/App_Data/ — user account storage (idash_users.json)
    • iDash/config/ — email recipients and report automation settings (JSON files)
    • iDash/logs/ — login audit trail (login_audit.jsonl) and application-level log output
    • iDash/uploads/incoming/ — customer/employee file uploads via the Downloads & Uploads page
  3. Create the following essential external folders on the server:
    • C:\VA_RFID\ennx_live\saved\auto\ (For automated and manual ENNX exports)
    • C:\inetpub\wwwroot\iDash\autoload\ (The drop folder for .bak or .sql sync files)
    • C:\Logs\ (For Serilog diagnostic output)
2

IIS Application Configuration

iDash requires a specific IIS configuration. Each item below corresponds to a real requirement in web.config or in the IIS server setup. Missing any of these is the most common cause of deployment failures.

2a. Install Required Windows Features

Run in an elevated PowerShell (or use Server Manager → Add Roles and Features):

Install-WindowsFeature Web-Server, Web-Asp-Net45, Web-ISAPI-Ext, Web-ISAPI-Filter, Web-Default-Doc, Web-Static-Content, Web-Http-Errors, Web-Http-Logging, Web-Stat-Compression, Web-Filtering

The critical role is Web-Asp-Net45 (ASP.NET 4.8). Without it, all .aspx pages return HTTP 500.21 or HTTP 404.

2b. Create the Application Pool

  1. In IIS Manager, create a new Application Pool named iDash (or reuse an existing one).
  2. Set .NET CLR Version to v4.0.
  3. Set Managed Pipeline Mode to Integrated.
  4. Under Advanced Settings → Process Model → Identity, set to ApplicationPoolIdentity (default) or a dedicated service account. Ensure this account has write access to the subdirectories listed in Step 1.
  5. Set Start Mode to AlwaysRunning if you need background auto-update tasks to wake without a browser hit (optional but recommended).

2c. Create the Web Application

  1. Right-click Default Web Site (or your site) → Add Application.
  2. Set Alias to iDash, Physical Path to C:\inetpub\wwwroot\iDash\iDash.
  3. Assign to the pool created in 2b.
⚠ Do NOT just add a Virtual Directory. iDash must be an Application (not a virtual directory) so IIS loads its own web.config.

2d. Install the .NET Core Hosting Bundle (for the iDash REST API)

The web.config contains an aspNetCore handler that routes /api/* to iDash.Web.dll. This requires the .NET Core Hosting Bundle to be installed on the server. Without it IIS returns HTTP 500.19 or HTTP 500.0 - ANCM In-Process Handler Load Failure.

winget install Microsoft.DotNet.HostingBundle

After installing, run iisreset from an elevated command prompt.

Note: If you do not use the iDash REST API (i.e., UseRestApi is false in web.config), remove or comment out the <aspNetCore> element and the aspNetCore handler from web.config to avoid requiring the hosting bundle.

2e. Handler Registration — The Dual-Pipeline Setup

The web.config registers two handlers inside <system.webServer><handlers>:

Handler NamePathModulePurpose
ASPClassic *.aspx IsapiModule via aspnet_isapi.dll All iDash .aspx pages (ASP.NET 4.8 WebForms)
aspNetCore /api/* AspNetCoreModuleV2 iDash REST API (iDash.Web.dll)
⚠ classicMode preCondition: The ASPClassic handler has preCondition="classicMode,runtimeVersionv4.0,bitness64". Despite the name, this works in Integrated pipeline — the classicMode preCondition here refers to the ISAPI integration mode, not the IIS pipeline mode. Do not change the Application Pool to Classic mode.

2f. machineKey — Required for ViewState Stability

The web.config includes a static <machineKey>. This prevents the "Validation of ViewState MAC failed" error that occurs when the application pool recycles and regenerates a new runtime key (which invalidates all in-flight form submissions).

The key is already set in the deployed web.config. If you rebuild web.config from scratch, generate new keys using: ASP.NET MachineKey Generator or PowerShell:

(New-Object System.Security.Cryptography.RNGCryptoServiceProvider).GetBytes($b = [byte[]]::new(64)); [Convert]::ToBase64String($b)

2g. Request Size Limits

iDash handles large file uploads (database files, data CSVs). The web.config sets limits at two levels:

SettingLocationValueCovers
maxRequestLength<httpRuntime>1 GB (1048576 KB)ASP.NET request body cap
maxAllowedContentLength<requestLimits>1 GB (1073741824 bytes)IIS kernel-level cap
executionTimeout<httpRuntime>900 secondsMax time for a single request

These are global defaults. va_data_import.aspx has its own tighter override (50 MB, 600s) because it processes 47K-row data files rather than full database backups.

2h. Per-Page RequestValidation Overrides

Two pages bypass the global requestValidationMode="4.0" setting via <location> blocks:

  • va_autodbupdate.aspx — uses requestValidationMode="2.0" so that raw SQL code containing < and > characters can be saved without ASP.NET throwing a "A potentially dangerous Request.Form value was detected" error.
  • va_data_import.aspx — has an elevated maxRequestLength (50 MB) and maxAllowedContentLength for large data file uploads.

These <location> blocks are already present in the deployed web.config. If you re-create web.config manually, these must be included or those pages will error.

2i. MIME Type Addition

The web.config adds the .avif MIME type (image/avif) under <staticContent>. IIS does not include this by default. Without it, any .avif image assets return HTTP 404.

2j. JSON AJAX Payload Size

maxJsonLength is set to 2147483644 (max int) in <system.web.extensions>. Without this, ScriptManager-driven AJAX calls that return large datasets (asset tables, report data) throw a "JSON serialization exceeded maxJsonLength" exception visible only in the browser console.

3

Web.config & Environment Configuration

You must point the application to the new local database, SMTP relay, and API credentials. The recommended way is to use the Site Configuration page (va_site_config.aspx), which provides a form-based UI for all of these settings. Alternatively, you can edit web.config directly.

3a. Database Connection

Under <connectionStrings>, update the iDash connection string:

Data Source=.\sqlexpress;Database=iDash;User ID=idashadmin;Password=idashadmin;Encrypt=False;TrustServerCertificate=True;Connect Timeout=30

Change Data Source to your SQL Server instance, User ID and Password to your SQL credentials.

3b. API / OAuth Credentials

⚠ Read these values FROM iDash BEFORE you fill them in here.
The iDash_ClientId and iDash_ClientSecret are not values you choose for iDash — they are values that the iDash API server already has, stored in the dbo.applicationsetting table. iDash must be configured to match them.

To retrieve them, run this on the iDash SQL Server: 
USE [idash];
SELECT webclientid, webclientsecret FROM dbo.applicationsetting;
Copy the returned values into the fields below. If the table has never been customized, the defaults are idash.web / 901564A5-E7FE-42CB-B10D-61EF6A8F3654 — but always verify directly, never assume defaults. See Network Guidelines — Section 7 for the full credential setup guide including how to change them.

Under <appSettings>, update the following keys:

KeyExample ValuePurpose
iDash_ApiBasehttp://localhost/apiREST API base URL
iDash_TokenUrlhttp://localhost/connect/tokenOAuth 2.0 token endpoint
iDash_ClientIdidash.web (read from DB)OAuth client ID (must match webclientid in iDash DB)
iDash_ClientSecret(read from DB)OAuth client secret (must match webclientsecret in iDash DB)

3c. Email / SMTP Settings

These keys control how iDash sends automated reports and admin alerts:

KeyExample ValuePurpose
SMTP_Hostsmtp.office365.comSMTP server hostname
SMTP_Port587SMTP port (usually 587 for TLS)
SMTP_Uservisn5@id-integration.comSMTP authentication username
SMTP_Password(account password)SMTP authentication password
SMTP_FromEmailvisn5@id-integration.comSender email address
SMTP_FromNameiDash ReportsSender display name
⚠ Do NOT store email recipients in web.config. Email recipients are stored separately in config/email_recipients.json and managed through the Report Automation UI (va_report_automation.aspx). Writing to web.config at runtime triggers an IIS application pool recycle which destroys all active user sessions. See Email Recipient Storage for details.
4

Migrating External State (Users, Configs & Recipients)

iDash uses JSON files outside the SQL database to manage users, email recipients, and report settings. Moving the SQL database alone will NOT move these.

FilePurposeWhat Happens If Missing
App_Data/idash_users.json All portal user accounts, passwords (SHA-256), roles, site permissions, and tile access A default idashadmin account is auto-created. All other users are lost.
config/email_recipients.json Global email recipient list for automated reports and admin alerts Auto-migrated from web.config EmailRecipients key on first access (one-time). If neither exists, no recipients are configured.
config/report_automation.json Report automation settings: enable/disable, scheduled time, subject format, Excel field selections Defaults are used (enabled, 19:00, standard fields).
print_mapping_config.json Maps tag type strings (e.g., IQ350) to BarTender template IDs for the web UI print buttons Print buttons will have no template mapping and will fail silently.
logs/login_audit.jsonl Login audit trail — every sign-in attempt (success/failure) with timestamp, username, IP, and role Auto-created on first login. No history will be available until a user signs in. Auto-trims at 90 days or 5,000 entries.
uploads/incoming/ Customer and employee file uploads submitted through the Downloads & Uploads page Upload section still works but files will fail to save if the directory does not exist or lacks write permissions.
Important: The IIS AppPool identity (IIS_IUSRS) must have write permissions to App_Data/, config/, logs/, and uploads/incoming/, as the web portal reads and writes these files directly during normal operation.
5

One-Time Company Setup SQL

Each site needs a company record in the database so that imported assets map to the correct facility. The Site Configuration page (va_site_config.aspx) includes a built-in SQL executor for this — enter the station number and site name, then click Execute.

Alternatively, run in SSMS:

USE [iDash];
IF NOT EXISTS (SELECT 1 FROM dbo.company WHERE SUBSTRING(name,1,3) = '649')
    INSERT INTO dbo.company (name) VALUES ('649 San Diego');

Replace 649 and San Diego with the actual 3-digit station number and site name. This is safe to re-run — uses IF NOT EXISTS.

6

Print Server Bypass Spooler Setup

iDash does not use the legacy iDash Print Server Service. It uses a standalone PowerShell spooler to avoid Session 0 BarTender crashes.

📁 Spooler Location: All spooler files are stored inside the iDash deployment under iDash\printing\ — i.e., C:\inetpub\wwwroot\iDash\printing\. This keeps everything in one deployment package (no separate folder to create or migrate). Files present: Run_Bypass_Spooler.ps1, printer_routing.json, and all *.btw BarTender templates.
⚠ Web Root Security Note: Because printing\ is inside the IIS web root, IIS could serve Run_Bypass_Spooler.ps1 as a plain text download if a browser requests it directly. IIS does not execute .ps1 files — there is no code execution risk. However, to prevent the script source from being viewable, add a web.config deny rule in the printing\ folder, or ensure the VA network firewall restricts direct web access to the server. The .btw files are proprietary BarTender binaries and are not a concern.
  1. The spooler files are already in place at C:\inetpub\wwwroot\iDash\printing\ as part of the iDash deployment. No separate copy step is needed.
  2. Edit printer_routing.json in iDash\printing\. You must change the target printer names to match the exact Windows Printer names installed on this specific server (e.g., "Zebra ZD420"). The spooler reads this file from $PSScriptRoot on every print job, so it must stay co-located with the script.
  3. Open Task Scheduler and create a new task named iDash Print Spooler.
  4. Configure the task to run: "Run only when user is logged on" (Critical: Do NOT check "Run whether user is logged on or not", as this places it in Session 0 and BarTender will hang).
  5. Set the Trigger to "At log on" for a dedicated service account.
  6. Set the Action to Start a Program: powershell.exe with arguments: -WindowStyle Hidden -File "C:\inetpub\wwwroot\iDash\printing\Run_Bypass_Spooler.ps1".
  7. Start the task manually to begin polling the SQL printjob table.
Full details: See the Print Server Setup & Troubleshooting Guide for expanded BarTender SDK, template, and hardware routing configuration.
7

Background Automations (Task Scheduler)

iDash uses Windows Task Scheduler to drive background jobs without relying on IIS application pool sleep cycles.

  1. Auto Database Update: Creates a task to ingest .bak files dropped by field servers.
    Action: powershell.exe -Command "Invoke-WebRequest -Uri 'http://localhost/iDash/va_autodbupdate.aspx'"
    Trigger: Daily, repeated every 10 minutes indefinitely.
  2. Daily Report Automation: Generates and emails the daily ENNX and Excel reports to all recipients in config/email_recipients.json.
    Action: powershell.exe -Command "Invoke-WebRequest -Uri 'http://localhost/iDash/va_report_automator_runner.aspx'"
    Trigger: Daily at 19:00 (7:00 PM), or whatever time is configured in config/report_automation.json.
Note: The report automation schedule time shown in the va_report_automation.aspx UI is informational only. The actual execution is triggered by Windows Task Scheduler, so the trigger time must match what you configured above.
8

Database Seeding / Importing Initial Data

If you are deploying against a completely fresh, empty iDash database, you must seed it with initial site data before running reports. iDash provides built-in tools for this, allowing you to bypass SQL Server Management Studio.

  1. Two-Pass Import Workflow: Open va_dbupdate.aspx (Manual DB Update tile in Admin Tools). Upload the VA data file. Run the Enrichment script (Pass 1) then Standard script (Pass 2). See the DB Update documentation for the full procedure.
  2. Auto Database Update (Field Sync): The va_autodbupdate.aspx engine polls the C:\inetpub\wwwroot\iDash\autoload\ directory for large .bak backup files or SQL scripts dropped by remote field servers. It safely restores these databases into temporary SQL tables, merges the new assets, and cleans up after itself.
  3. For detailed technical specifics on the cross-database merge architecture and the background polling scripts used, read the Field Server Sync Documentation.
9

First Boot & Verification

Verify the deployment is successful through the iDash diagnostic tools.

  1. Navigate to http://localhost/iDash/index.aspx in your browser.
  2. Log in using the idashadmin account (or whichever admin account was migrated in Step 4).
  3. Verify the status bar at the top of the Hub shows ● CONNECTED and the correct server machine name. If it shows DISCONNECTED, your database connection string (Step 3a) is wrong.
  4. Open the IIS & App Log Analyzer tile (va_log_viewer.aspx) and check for SQL connection failures or authentication errors. Switch to the Login Audit tab to confirm your login was recorded.
  5. Open the User Management tile (va_user_management.aspx) and verify the Login History card at the bottom shows your sign-in entry — this confirms logs/login_audit.jsonl is writable.
  6. Open the Print Mapping tile (va_print_mapping.aspx) and confirm your print_mapping_config.json loaded successfully.
  7. Open the Report Automation tile (va_report_automation.aspx) and verify the email recipient list is populated. Try adding and removing a test recipient to confirm the JSON file storage is working (you should not be logged out).
  8. Open the Downloads & Uploads tile (va_downloads.aspx) and try uploading a small test file to confirm the uploads/incoming/ directory has write permissions.
  9. Navigate to the Site Configuration page (va_site_config.aspx) and review the built-in deployment checklist at the bottom of the page to confirm each item is complete.

config/*.json email_recipients.json, report_automation.json Frequently (users add/remove recipients, toggle reports) NO — sessions preserved
App_Data/*.json idash_users.json When users are created/edited/deleted NO — sessions preserved

logs/*.jsonl login_audit.jsonl Every login attempt (auto-trimmed at 90d / 5K entries) NO — sessions preserved

🔌 WebSerial USB Scanning — HTTPS Prerequisite

As of 07/25/2026, six iDash scanning modules support the WebSerial API for connecting USB RFID readers and serial devices directly through the browser (Chrome or Edge). This feature requires HTTPS (or localhost) to function.

ModuleFile
ENNX Live Scanva_ennx_live_scan.aspx
EIL Live Scanva_eil_live_scan.aspx
Universal ENNX Creatorva_universal_ennx.aspx
VA Site Inventoryva_inventory.aspx
RFID Asset Locator (07/24/2026)va_rfid_locator.aspx — client-side JS, continuous serial connection, tag normalization applied to serial reads identically to keyboard reads
Fixed Reader Config (API mgmt, no WebSerial)va_reader_config.aspx — manages fixed readers via REST API; WebSerial does not apply
⚠ Deployment Impact: If the IIS site is configured with HTTP only (no SSL binding), the WebSerial section on each page will display "Not Available" — but all other scanning (keyboard, DataWedge) continues to work normally. To enable WebSerial, configure an HTTPS binding with a valid SSL certificate in IIS Site Bindings.

Why: WebSerial eliminates the need for DataWedge or COM-port relay middleware by letting the browser talk directly to USB serial ports. It requires no software installation on client machines. The HTTPS requirement is a browser security policy (not an iDash requirement) — Chromium enforces it for all "powerful features" that access hardware.

🛠 IIS Troubleshooting Quick Reference

These are the most common IIS errors seen during iDash deployments and their fixes.

ErrorCauseFix
HTTP 500.21 — Handler "ASPClassic" has a bad module ASP.NET 4.8 is not registered with IIS Run: %windir%\Microsoft.NET\Framework64\v4.0.30319\aspnet_regiis.exe -ir then iisreset
HTTP 500.19 — Cannot read configuration file Missing IIS module (often AspNetCoreModuleV2 not installed) Install the .NET Core Hosting Bundle (Step 2d) then iisreset
HTTP 500.0 — ANCM In-Process Handler Load Failure Hosting Bundle installed but wrong version, or iDash.Web.dll missing Verify the .NET runtime version the DLL targets. Check stdoutLogFile in web.config (logs\stdout*.log) for the exact error.
HTTP 404 on .aspx pages iDash was added as a Virtual Directory instead of an Application, OR Web-Asp-Net45 feature not installed Convert Virtual Directory to Application in IIS Manager. Run Install-WindowsFeature Web-Asp-Net45.
Validation of ViewState MAC failed App pool recycled and regenerated machine keys mid-session, or <machineKey> is missing from web.config Ensure the static <machineKey> block is present in web.config (Step 2f).
A potentially dangerous Request.Form value was detected on va_autodbupdate.aspx The <location> override for requestValidationMode="2.0" is missing Add the <location path="va_autodbupdate.aspx"> block from the reference web.config (Step 2h).
Maximum request length exceeded on large uploads Either maxRequestLength (ASP.NET) or maxAllowedContentLength (IIS) is at default (4 MB / 30 MB) Set both in web.config as documented in Step 2g. Both must be increased — one alone is not enough.
JSON serialization exceeded maxJsonLength The <jsonSerialization maxJsonLength> element is missing from <system.web.extensions> Add the <system.web.extensions> block from the reference web.config (Step 2j).
HTTP 404 on .avif images IIS does not include .avif in its default MIME map Add <mimeMap fileExtension=".avif" mimeType="image/avif" /> under <staticContent> (Step 2i).
Access denied / 500 writing to App_Data, config, logs IIS AppPool identity lacks Write permission on those subdirectories Grant IIS_IUSRS (or the AppPool identity) Write access to App_Data\, config\, logs\, uploads\incoming\ (Step 1).
WebSerial shows "Not Available" Site is HTTP-only; WebSerial requires HTTPS (or localhost) Add an HTTPS binding with a valid SSL certificate in IIS Site Bindings (Step WebSerial section above).

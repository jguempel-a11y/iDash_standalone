RFID Mode Behaviour & Input Handling

How RFID input works: The page does not use a hardware RFID SDK. The TC53 / RFD40 RFID scanner is configured in keyboard-wedge mode — it emulates a keyboard and fires the decoded EPC/barcode string directly into whichever text field currently has focus, terminated by a carriage return (Enter). ASP.NET's AutoPostBack="true" on both scan fields intercepts that Enter and immediately submits the form — no button click required.

The Two Scan Fields

FieldIDAcceptsTrigger
Location Scan TxtLocationScan Room/space barcodes only (e.g. SP1234) OnTextChanged ←’ BtnSetLocation_Click — fires on every Enter/tab-out
Asset Scan TxtAssetScan Asset/equipment barcodes (e.g. EE123456) OnTextChanged ←’ BtnAddAsset_Click — fires on every Enter/tab-out

Prefix / Postfix Stripping — Does It Happen?

No prefix or postfix is stripped by the application code. The raw string delivered by the scanner is used as-is after a single .Trim().ToUpper() call. There is no GS1, AIM, or custom symbology prefix-removal logic at the application layer.

Scanner-level stripping only. If your TC53 / RFD40 profile is configured with a prefix or suffix in the DataWedge or RFID config, those characters will be stripped by the device firmware before the string reaches the browser. The application itself never sees them. If barcodes arrive with unexpected leading characters, the fix is in the DataWedge profile on the device — not in this application.

What the Application Does to Each Scanned String

StepCodeEffect
Upper-case .ToUpper() All comparisons are case-insensitive. ee123456 and EE123456 are identical.
Trim whitespace .Trim() Leading/trailing spaces and newlines from the scanner Enter key are removed.
Empty guard if (string.IsNullOrWhiteSpace(barcode)) return; A blank scan (e.g. double-trigger with nothing in the field) is silently ignored — no error, no postback effect.
DB lookup exact match WHERE name = @Name The processed string is matched exactly against asset.name. No LIKE or fuzzy matching.

What Is Silently Ignored

  • Empty / whitespace-only scans — the field guard returns immediately with no error.
  • Duplicate asset scans — if the asset is already in the grid and already has a non-pending final status (Found, Moved Here), it is re-promoted to the top and its status is updated to Found (Pending) again — it does not create a second row.

What Is Actively Rejected (Errors Shown)

  • Location scanned into Asset field (detected by pattern — see Filter 3 below)
  • Asset scanned into Location field (the EE substring check)
  • Barcode not found in dbo.asset
  • Asset belonging to a different companyid (different VA site)
  • Location not found in dbo.location for the selected site
  • Scan attempted without Operator or Site selected

Batch Scanning Mode (RFID Sweeps)

The 📡 Batch Mode button toggles high-speed RFID burst mode. In standard Web Forms, every barcode or tag scan immediately initiates an HTTP POST reload (AutoPostBack). When using handheld RFID readers (such as a Zebra RFD40 or TC53 sled) that detect multiple tags per second, single-item postbacks can overwhelm the browser and drop scans.

FeatureNormal Mode (Default)📡 Batch Mode ON
Trigger & Postback Fires immediate HTTP POST page reload on every single scan. Suppresses all postbacks. Scans are held in an in-memory client queue (_batchQueue).
RFID Sweep Speed 1 tag at a time (wait for page reload before next scan). Continuous trigger hold. Sweep shelves, carts, or cabinets at 20+ tags per second with zero UI latency.
Deduplication Deduplicated on the server during postback. Instant client deduplication — identical tags repeatedly read by the RFID field are filtered immediately.
Audio & Visual Feedback Page refresh chime / visual reload. Audio beep on each new unique tag + live counter (e.g. 24 tags queued) with preview chips.
Commit to Server Automatic per tag. Click Submit Batch to send all queued tags in a single JSON payload for server reconciliation.

Batch Submission Results

When Submit Batch is clicked, the server processes all tags sequentially via ProcessBarcode() and outputs an aggregated summary:

Batch complete: 28 processed (24 found in-place, 4 new/moved, 0 not in DB, 0 wrong site).

All found and moved assets appear in the grid as Found (Pending) or Moved Here (Pending) ready for the final Commit Scans.

RFID Scan Filters — All 8 Explained

Every scan passes through a layered filter chain. Filters 1–6 are hard-rejects (nothing enters session). Filter 7 is a soft display filter only.

Filter Order: Operator guard ←’ Site guard ←’ Location format ←’ Location cross-site DB check ←’ Asset existence ←’ Asset cross-site ←’ CMR display filter.

Filter 1 — Operator Required

Applies toBoth Location and Asset scans
SourceBtnSetLocation_Click & BtnAddAsset_Click
LogicDdlEmpl.SelectedValue must not be empty
On BlockRejected — Error shown, field cleared, focus forced to Operator dropdown. No DB call made.
WhyEvery committed update writes lastmodifiedby = @Emp. Without an operator the audit trail is broken.

Filter 2 — Site Required

Applies toLocation scan only
SourceBtnSetLocation_Click
LogicDdlCompany.SelectedValue must not be empty
On BlockRejected — Error shown, field cleared, focus forced to Site dropdown.
WhyThe companyid is required for Filter 4's cross-site validation.

Filter 3 — Location Format Check

Applies toLocation scan
Sourceif (!loc.StartsWith("SP") || loc.Contains("EE"))
Logic
  • Must start with SP — VA room/space barcodes always begin with this prefix.
  • Must not contain EE — this substring identifies equipment/asset barcodes. If an operator accidentally scans an asset tag into the Location field, this catches it.
On BlockRejected — "Invalid Location. You MUST barcode scan a valid Location (starts with SP) before scanning!" Field cleared.
WhyPrevents the room context from being set to an asset barcode, which would cause the DB query to return zero expected assets and break the entire sweep session.

Filter 4 — Location Cross-Site DB Validation

Applies toLocation scan — after format check passes
SourceSQL against dbo.location
Logic Two queries run in sequence: 
-- Query 1: Does this location exist for our site?
SELECT COUNT(*) FROM dbo.location
WHERE UPPER(LTRIM(RTRIM(name))) = @Loc
  AND companyid = @CompanyId

-- Query 2 (only if query 1 = 0): Does it exist on ANY site?
SELECT COUNT(*) FROM dbo.location
WHERE UPPER(LTRIM(RTRIM(name))) = @Loc
On Block Two distinct messages:
  • Found on another site ←’ Wrong Site — "Location X exists in the database but belongs to a different site — not Y."
  • Not found anywhere ←’ Not Found — "Location X was not found in the database at all."
WhyPrevents an operator at one VA medical center from accidentally loading room lists from another facility's database records. Hard data isolation per site.

Filter 5 — Barcode Format Validation (3-Digit Station Prefix)

Applies toAsset scan — before database lookup
SourceRegex.IsMatch(barcode, @"^\d{3} EE\w+$")
LogicEnforces that every scanned physical barcode starts with a 3-digit station code, followed by a space, EE, and alphanumeric asset identifier (e.g. 512 EE123456). Substation division codes (e.g. 512A4, 512A5) are never on physical tags and are resolved via system DB lookups.
On BlockRejected — "Invalid Barcode Format: XXX. Barcodes must match the 3-digit station pattern (e.g. '512 EE12345')." Field cleared.
Prefix MismatchWarning — If the scanned 3-digit prefix does not match the active site selection (e.g. scanning 613 EE... while site 512 is selected), an orange alert warns the operator of the facility mismatch.
WhyPrevents malformed barcode reads from polluting the database and alerts operators immediately if they sweep assets from an unexpected facility.

Filter 6 — Asset Existence Check

Applies toAsset scan — for barcodes NOT already in the active location checklist
SourceLookupAssetInventoryDetails(barcode)
Logic
SELECT TOP 1 id, companyid, description, text3, text8, text19, text6
FROM asset WHERE name = @Name
ORDER BY CASE WHEN companyid > 0 THEN 0 ELSE 1 END, id DESC
If returns no row ←’ rejected.
On BlockRejected — "Asset XXX does not exist in the database! Ignoring scan."
WhyPrevents garbage data — mis-reads, dust, typos, incorrect symbology — from entering inventory records.

Filter 7 — Cross-Site Asset Guard

Applies toAsset scan — fires just after existence check, for foreign assets
Sourceif (info.CompanyId != currCompanyId)
LogicThe companyid from the asset lookup is compared to the selected Site dropdown companyid.
On BlockRejected — "Asset XXX belongs to a different site (Site Name)! You cannot scan cross-site assets."
WhyEnsures a scanner in Building A cannot move assets belonging to Building B's inventory, which would corrupt both sites' records.

Filter 8 — CMR / EIL Grid Display Filter (Soft)

Applies toGrid display only — never blocks a scan
SourceDdlCmrFilter ←’ BindGrid()
Logic After every location load or asset scan, PopulateCmrFilter() groups the in-memory scan list by ScanItem.CMR (= asset.text8). Unique CMRs populate a dropdown: CMR-512 (14 assets), CMR-301 (8 assets), etc. Assets with no CMR are grouped as UNASSIGNED. Selecting a CMR applies an in-memory LINQ WHERE against the session list.
On SelectDisplay Only — Grid narrows to that CMR. All other scan items remain in session; no data is removed.
WhyLarge VA rooms can hold assets from multiple CMRs. This lets the operator focus on one CMR at a time without disrupting the overall sweep.

Moving Assets to a New Location — Full Workflow

Core concept: The system loads what the database thinks is in a room. When you physically find an asset that the database said was elsewhere, scanning it flags it as "Moved Here". Committing saves the new location to the DB.

Step-by-Step: Full Asset Move Procedure

1
Set Operator & Site

Select your username from the Operator dropdown and the VA medical center from the Site Filter dropdown. These are required before anything else will work. If you just provisioned a new user account, click Refresh App Data to reload the dropdowns without losing your scan session.

2
Scan the Room Location Barcode

Point the scanner at the room label (a barcode that starts with SP). The scanner fires the string into the Scan Location field and auto-submits. The system:

  • Validates the format (must start with SP, must not contain EE)
  • Verifies the location exists in dbo.location for the selected site
  • Loads all assets currently assigned to that room from the asset table
    (WHERE text6 = @Loc) and populates the grid with them all in Not Found status
  • Populates the CMR filter dropdown from that result set
  • Shows a count badge: "14 Assets Assigned"
  • Automatically moves focus to the Asset Scan field

The Current Location Mode label now shows the active room in large green text.

3
Sweep the Room — Scan Each Asset Tag

Walk the room and scan each RFID/barcode tag. For each scan one of two things happens:

Scenario A — Asset Belongs Here (Confirmation)

The scanned barcode matches an item already in the grid (the database already assigned it to this room). The system finds it in the in-memory session list and:

  • Flips its status from Not Found to Found (Pending)
  • Moves that row to the very top of the grid for immediate visual confirmation
  • No DB write happens yet — it is still "pending"
  • Focus returns immediately to the Asset Scan field — ready for the next scan

Scenario B — Asset Found Here but Belongs Elsewhere (Move)

The scanned barcode is NOT in the current room's checklist. The system does a live DB lookup:

  • Verifies the barcode exists in dbo.asset (Filter 5)
  • Verifies it belongs to the same site selected (Filter 6)
  • If both pass — the asset is loaded into the grid as a new row inserted at the top with:
    • Current Loc (DB): the room the DB says it currently lives in
    • Scanned Loc: the room you are currently sweeping
    • Status: Moved Here (Pending) — or Pending Move if Queue Mode is on
No DB change happens yet. The asset's location in the database is still the old room. Nothing is written until you click Commit Scans.
4
Commit Scans — This Is When DB Writes Happen

When you are done scanning the room (or a section), click the Commit Scans button (it only appears when there are pending items in the grid). The system iterates every item in the session scan list that has a Pending status and executes: 

UPDATE asset
SET text6            = @Loc,    -- current location field
    text16           = @Loc,    -- tagged/verified location field
    lastinventoried  = SYSDATETIMEOFFSET(),
    lastmodifiedby   = @Emp
WHERE id = @Id

Both text6 AND text16 are updated simultaneously. After commit:

  • Items that were Found (Pending) become Found
  • Items that were Moved Here (Pending) become Moved Here
  • Items that were Pending Move become Moved Here
  • Items still showing Not Found remain in the grid — they were not physically seen during the sweep

A success message shows the count: "Successfully committed N scanned assets to the database."

5
(Optional) Export / Email Results

After committing, use the bottom action bar:

  • Build ENNX: Generates a formatted ENNX text block in the preview box. Can be copied or emailed.
  • Export Excel: Downloads a CSV containing Asset Tag, Description, Serial Number, CMR, Current Loc (DB), Scanned Loc, and Status for all non-"Not Found" items.
  • Email Results: Sends both the CSV and the ENNX text as email attachments to all configured recipients.
Export/Email are blocked if:
  • There are uncommitted (Pending) scans still in the grid — you must commit first.
  • The scan list contains zero non-"Not Found" assets — nothing to send.

Moving Multiple Assets Across Multiple Rooms

Scan a new location barcode at any time. This replaces the entire session scan list with the expected assets for the new room. Any previously committed scans from the old room are already saved in the DB — the session reset only affects the in-memory working list. Process each room as an independent sweep session.

SQL Reference

Location Load Query

Fires when a valid location is scanned. Retrieves all assets the database currently assigns to that room. Serial Number = text3, CMR = text8, Tag Type = text19, Location = text6:

SELECT id, name, description, text3, text8, text19, text6
FROM asset
WHERE text6 = @Loc
ORDER BY name

Asset Global Lookup (Filters 5 & 6)

Fires for any asset barcode NOT already in the current room checklist:

SELECT TOP 1 id, companyid, description, text3, text8, text19, text6
FROM asset
WHERE name = @Name

Asset Commit Update

Fires once per pending item when Commit Scans is clicked. Updates both location fields and inventory timestamp:

UPDATE asset
SET text6            = @Loc,
    text16           = @Loc,
    lastinventoried  = SYSDATETIMEOFFSET(),
    lastmodifiedby   = @Emp
WHERE id = @Id

Location Cross-Site Validation (Filter 4)

-- Check for this site:
SELECT COUNT(*) FROM dbo.location
WHERE UPPER(LTRIM(RTRIM(name))) = @Loc
  AND companyid = @CompanyId

-- Fallback check (if count = 0):
SELECT COUNT(*) FROM dbo.location
WHERE UPPER(LTRIM(RTRIM(name))) = @Loc

Offline Mode & Local Resilience

The page provides robust offline operation designed specifically for hospital basements, lead-lined radiology suites, and RF dead zones where Wi-Fi drops frequently during room sweeps:

  • Dedicated Offline Queue: Scans are isolated in localStorage under key Inventory_OfflineQueue (preventing collision with Tag Team or ENNX scanners).
  • Active Dual-Layer Connectivity Probing: Instead of relying on passive browser flags, an active 4-second XHR HEAD probe tests real IIS server and SQL Server database reachability.
  • Enter-Key Hardware Scanner Interception: In ASP.NET Web Forms, pressing Enter or barcode scanner hardware line returns in an input field ordinarily causes the browser to submit an HTTP POST. If disconnected, this would show a browser network crash screen. Both TxtAssetScan and TxtLocationScan trap Enter events when offline, preventing form navigation and routing the barcode directly to local storage.
  • Real-Time Visual Checklist Updates: When scanning offline, if the asset is in the current room's checklist, its status badge immediately flips to Found (Pending) with row highlighting — giving the operator instant visual confirmation that the scan was registered.
  • State Auto-Persistence: Selected Site, Operator, and active Room Location are persisted in local storage so page reloads never lose location context.
  • Sync Endpoint (?action=sync): When connectivity returns, the Sync Now button becomes available. It POSTs the JSON queue to va_inventory.aspx?action=sync, validating 3-digit station format, updating text6, text16, lastinventoried, and lastmodifiedby in SQL Server, and updating the session checklist.
Substation Barcode Rule: All VA barcode tags use a standard 3-digit station prefix (e.g. 512 EE12345). Substation divisions (e.g. 512A4 Fort Howard, 512A5 Perry Point) are NEVER printed in physical barcode tags; substations are resolved through system database lookups.

Refresh App Data Feature

The Refresh App Data button in the top-right of the interface is a state-preserving resync utility.

  • What it does: Re-queries the SQL database for the latest Operator usernames (v_sysuser) and Site names (dbo.company), updating both dropdowns.
  • Preserves Workflow: Unlike a browser refresh (which wipes session variables and the scan grid), this button refreshes the dropdowns in the background without clearing the active scan list.
  • Use Case: If a new operator account is added in AssetWorx while a sweep is in progress, click this to load the new account without losing any scanned data.

WebSerial USB Input

The WebSerial section allows connecting a USB-tethered RFID reader (or any serial device) directly through the browser. When a complete line is received from the serial port, it is placed into TxtAssetScan and the standard ASP.NET postback is triggered automatically.

Serial Port Configuration

ParameterValue
Baud Rate115200
Data Bits8
ParityNone
Stop Bits1
Flow ControlHardware
Buffer Size1024 bytes

Why WebSerial?

Traditional barcode/RFID scanning in a browser requires a middleware layer (DataWedge, COM-port relay app, or a native mobile app) to translate serial data into keyboard events. WebSerial eliminates that middleware by letting the browser talk directly to the USB serial port. This means:

  • No extra software: No DataWedge profile, no COM-port relay, no native app installation.
  • Any USB serial device: Works with any reader that outputs newline-terminated data over a serial/USB-serial connection.
  • Zero configuration: The browser prompts the user to select their serial port — no driver setup, no port number guessing.
  • Same processing pipeline: Data from the serial port is placed into TxtAssetScan and triggers the same __doPostBack that a keyboard scan does, so all server-side validation, filters, and DB writes apply identically.

How WebSerial Works on This Page (Technical Flow)

  1. User clicks "Select/Open Serial Port" inside the collapsible WebSerial panel below the Asset Scan field.
  2. The browser displays its native serial port picker dialog (a security requirement — no port is accessed without explicit user interaction).
  3. Once a port is selected, JavaScript opens it with the parameters above (115200 baud, 8N1, hardware flow control) and starts an asynchronous read loop.
  4. Incoming bytes are decoded as UTF-8 and appended to a line buffer. When a newline (\n) is detected, the complete line is trimmed.
  5. The trimmed line is placed into TxtAssetScan.value and __doPostBack('TxtAssetScan', '') is called, triggering the standard ASP.NET postback.
  6. The server-side BtnAddAsset_Click handler processes the scan through all 7 filters identically to a keyboard-entered barcode.
  7. Important: Because the postback causes a full page reload, the serial connection is closed after each scan. The operator must click "Select/Open Serial Port" again to reconnect.
ℹ Prerequisite: WebSerial requires Chrome or Edge, served over HTTPS (or localhost). If the site is served over plain HTTP, the section will display "Not Available" but keyboard/DataWedge scanning continues normally.
⚠ Postback behavior: Because this page uses AutoPostBack, each scan causes a full page reload. The serial port connection is lost after every scan. To continue scanning via WebSerial, the operator must re-open the port after each postback. For high-volume continuous scanning, the ENNX Live Scan tools (which are fully client-side) provide a more seamless serial experience.

The WebSerial feature requires explicit user interaction to grant the browser permission to access a serial port. No serial ports are accessed automatically. The permission does not persist across browser sessions.

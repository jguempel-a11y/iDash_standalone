🚨 Why a Message Broker Is Required

A message broker is the central nervous system between the RFID readers and iDash. Without one, the system cannot reliably operate at the scale of 80+ readers with 360+ antennas running 24/7 across VA facilities.

What Is a Message Broker?

A message broker is a dedicated service that sits between producers (the FX9600 readers) and consumers (iDash/iDash). It receives messages, stores them temporarily, and delivers them to consumers. Think of it as a post office for RFID data — it guarantees every letter gets delivered, even if the recipient isn’t home.

1. IIS App Pool Recycling = Guaranteed Data Loss

🚫 This is the #1 reason a broker is mandatory.
Recycle TriggerDefault SettingWhat Happens
Scheduled recycleEvery 29 hoursIIS shuts down w3wp.exe and restarts. During ~3–10 sec transition, no connections accepted.
Memory limitExceeds thresholdIIS kills the worker process immediately. In-flight requests terminated.
Configuration changeAny web.config editAutomatic recycle on every deployment and config change.
Idle timeout20 minutes inactivityIIS shuts down worker process to save resources.
⚠ With RabbitMQ: Readers send data to the broker, not to IIS. RabbitMQ is a standalone Windows Service that does not recycle. When IIS recycles, the broker holds all messages. Zero data loss.

2. Deployments & Updates = Outage Windows

  • iDash updates: App pool recycle — unavailable 30 sec to several minutes
  • Windows Updates: Monthly patching — offline 5–15 minutes
  • iDash changes: web.config edits trigger instant recycle
  • SQL maintenance: Backups, index rebuilds, failovers
✅ With a broker: Readers never know the server went down. RabbitMQ queues everything. When the server returns, the service reconnects and processes the backlog. No data lost.

3. Thread Pool Exhaustion & SQL Write Contention

MetricValue
Readers80
HTTP POSTs per second (without broker)80
IIS default thread pool~100 threads
Individual SQL writes/sec (without broker)80
✅ With a broker: RabbitMQ handles all connections on Erlang’s thread pool. The service batch-writes to SQL efficiently — reducing load by 95%. IIS is not involved in data ingest.

4. Reader Health Monitoring & Remote Management

MQTT includes “Last Will and Testament” (LWT) — if a reader disconnects unexpectedly, RabbitMQ automatically publishes a notification. The pub/sub model is also bidirectional: iDash can send commands to readers via MQTT control topics.

Summary: Direct HTTP vs. Broker Architecture

🔎 iDash Built-In MQTT Infrastructure Discovery Report

Analysis of the iDash installation revealed a built-in MQTT broker — it does not use or install Mosquitto.

Key Finding: MQTTnet, Not Mosquitto

⚠ iDash does NOT use Mosquitto. The software ships with MQTTnet 3.1.2 (MQTTnet.dll, 303 KB), a .NET library with an embedded MQTT broker/server. Mosquitto is not installed anywhere on this server.

When enabled, the MQTTnet broker runs inside iDash.Web.exe — sharing memory, thread pool, and lifecycle with the web application. Fine for 1–10 readers, but cannot sustain 80+ in production.

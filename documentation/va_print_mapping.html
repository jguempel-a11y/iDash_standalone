📌 Print Mapping & Routing Guide

Covers va_print_mapping.aspx, the print_mapping_config.json it manages, and how it fits into the three-layer print routing architecture. Also explains the difference between iDash web-based print mapping and the PS Spooler hardware routing — two separate systems that are often confused.

Three-Layer Print Routing Architecture

A successful print job passes through three independent routing decisions. Each layer is controlled by a different file or database table. Misconfiguring any layer will cause jobs to go to the wrong template or printer.

LayerWhat It DoesControlled ByWho Reads It
1Mobile Auto-Map Selects which template ID gets assigned when the mobile app creates a print job SQL template.name column — must exactly match the RFID tag type string AssetWorx Mobile App
2iDash Web Mapping When printing from the Tag Team Scan web UI, resolves which template ID to use for a given tag type print_mapping_config.json — managed by va_print_mapping.aspx va_tagteam_scan.aspx via InjectPrintScript()
3Hardware Routing Maps the .btw filename to the correct Windows printer name at print time printer_routing.json — edited manually in the spooler folder Run_Bypass_Spooler.ps1
⚠ Common Confusion
print_mapping_config.json and printer_routing.json are completely separate files with different purposes. va_print_mapping.aspx manages only print_mapping_config.json. The spooler hardware routing is controlled by printer_routing.json in the spooler script folder — see the Print Server Setup guide for that.

What va_print_mapping.aspx Does

This page provides a UI for configuring Layer 2 — the iDash web print mapping. It allows you to draw explicit links between an RFID tag type and a specific BarTender template, and optionally force the print job to a specific print client or service.

What it writes

Saves to print_mapping_config.json in the iDash root directory:

C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\print_mapping_config.json

Example file content:

{
  "IQ350":         { "TemplateID": 3, "TargetType": "Default",  "TargetValue": "" },
  "Large_Metal":   { "TemplateID": 5, "TargetType": "Client",   "TargetValue": "613Print" },
  "Small_Standard":{ "TemplateID": 4, "TargetType": "Default",  "TargetValue": "" }
}
  • Key: The RFID tag type string (must match exactly what appears in the Tag Type column)
  • TemplateID: The SQL template.id value to use for this tag type
  • TargetType: Default, Client, or Service
  • TargetValue: The specific print client or service name (only when TargetType is not Default)

What reads it

On every page load of va_tagteam_scan.aspx, the C# method InjectPrintScript() reads print_mapping_config.json and injects it as a JavaScript object: 

window.awPrintConfig.templateMappings = { "IQ350": { "TemplateID": 3, ... }, ... };

The printCheckedTags() and printSingleTag() JavaScript functions then use templateMappings to resolve the correct template ID at print time. If a tag type has no entry in the config, it falls back to a name-match against the template list, then falls back to the first available template.

How to Configure Print Mappings

Option A — Name Match (Preferred, No UI Needed)

The simplest approach. In the template SQL table, set the name column to exactly match the RFID tag type string (e.g., IQ350, Large_Metal, Small_Standard). The iDash print JS automatically performs a name-match fallback against the template list, so no entry in print_mapping_config.json is needed at all. 

UPDATE template SET name = 'IQ350'         WHERE id = 3;
UPDATE template SET name = 'Small_Standard' WHERE id = 4;
UPDATE template SET name = 'Large_Metal'    WHERE id = 5;
This approach also fixes the mobile app auto-map (Layer 1) at the same time — one SQL update resolves both the web and mobile print pipeline simultaneously.

Option B — Explicit Mapping via va_print_mapping.aspx

Use this when your template is named differently from the tag type, or when you need to force a specific print client per tag type.

  1. Open iDash Hub → Configure Print Templates (or navigate directly to va_print_mapping.aspx).
  2. Select the Tag Type from the left dropdown (e.g., IQ350).
  3. Select the Template from the middle dropdown (shows template.name (Template ID: N)).
  4. Optionally set a Target Type:
    • Default — uses the routing target embedded in the template's SQL record (template.usewithservice or linked printclient)
    • Client — forces this tag type to a specific named print client (e.g., 613Print)
    • Service — forces routing to a background print service
  5. Click Add Mapping. The entry is immediately written to print_mapping_config.json.
Note: Mappings added here only affect printing from the iDash web interface (Tag Team Scan). They have no effect on the mobile app auto-map or the PS Spooler hardware routing. Those are controlled by Layer 1 (SQL) and Layer 3 (printer_routing.json) respectively.

Template Resolution Priority (Web UI)

When Server Print or Auto Print is triggered from the web, the JS resolves the template in this order:

  1. Manual Override Dropdown — if the user selected a template from the DdlPrintTemplate dropdown in the action bar, that template ID is used unconditionally.
  2. print_mapping_config.json lookup — if the tag type has an entry in the mapping config, the mapped TemplateID is used.
  3. Name match — if no config entry, finds a template whose name exactly equals the tag type string.
  4. First available template — fallback of last resort; uses printTemplates[0].

🔎 Troubleshooting

All jobs use the same template regardless of tag type

  • Check that print_mapping_config.json has entries for each tag type: open va_print_mapping.aspx and verify the mapping grid.
  • If using name-match, run SELECT id, name FROM template and confirm name exactly matches the tag type string (case-sensitive).
  • Open browser DevTools console on Tag Team Scan and check window.awPrintConfig.templateMappings — if it is {} or empty, the config file is missing or unreadable by IIS.

Print goes to the wrong physical printer despite correct template

  • The template routing in print_mapping_config.json controls which print client receives the job, not which Windows hardware printer is used.
  • The hardware printer selection is controlled by printer_routing.json in the PS Spooler folder. See the Print Server Setup guide.

Changes to mappings not taking effect

  • print_mapping_config.json is re-read on every page load of va_tagteam_scan.aspx — no IIS restart needed.
  • Hard refresh the Tag Team Scan page (Ctrl+Shift+R) after adding a mapping.
  • Verify IIS has write permission to the iDash directory so va_print_mapping.aspx can save the file.

Support Request

Lets any authenticated iDash user submit a help ticket directly to ID Integration Support from the Hub. The email is routed using the site’s SMTP settings, the subject is pre-populated with the user’s assigned site name, and a copy goes to the submitter. Requests are sent asynchronously via AJAX — no page reload required.

Source files:  index.aspx  •  support_send.ashx  •  App_Code/EmailHelper.cs

👉 How to Access

When logged in, look in the upper-right user bar for the Support Request pill (next to the theme toggle and Sign Out). Clicking it opens a modal overlay without leaving the Hub.

ℹ Visibility: The pill is only shown when a user is authenticated. It is not visible on the login screen.

🔌 SMTP Dependency

Uses EmailHelper.SendDirectEmail() — the exact same SMTP code path that sends ENNX reports and all other automated iDash emails. Managed via Site Configuration.

web.config KeyUsed For
SMTP_HostMail server hostname or IP
SMTP_Port587 for Office 365 / TLS, 25 for internal relay
SMTP_UserAuth username (blank = unauthenticated relay)
SMTP_PasswordAuth password (blank = unauthenticated relay)
SMTP_FromEmailFrom address. Must be a valid email address.
⚠ SMTP_FromEmail must be a valid email address. If the Site Configuration page previously saved a display name (e.g., “613 - Martinsburg”) into this field instead of an address, email sending will fail. Verify in Site Configuration → Email → From Email.
ℹ VA Facility Servers: VA firewalls may block outbound SMTP to external servers (e.g., smtp.office365.com:587). Configure an internal SMTP relay (port 25, no credentials, no SSL). Contact VA IT for the relay hostname. When credentials are blank, SSL is automatically disabled.
ℹ Portability: The From address always reflects whatever SMTP_FromEmail is configured on the current server. Nothing is hardcoded — deploying iDash to a new machine automatically uses that machine’s Site Configuration SMTP settings.

🛠 Developer Reference — Architecture

The Support Request uses an AJAX (fetch) architecture instead of an ASP.NET postback. This was a deliberate design decision to solve modal reliability issues with full-page postbacks.

Why AJAX Instead of Postback?

The Support Request modal lives inside index.aspx — a complex page with a large form, ViewState, and many server controls. A full-page postback had several problems:

  • Modal hang: ASP.NET postback submits the entire form, reloads the page, and discards the modal state. The “Sending…” button would stay frozen because the page was waiting for the server to finish sending the email before returning the response.
  • ViewState bloat: The large page ViewState made every postback slow, even before the SMTP send.
  • User experience: Any server-side error during the SMTP send would close the modal and require re-opening it to see what happened.

The AJAX approach sends only the 5 form fields to a lightweight .ashx handler. The modal stays open, the button shows a spinner, and the JSON response updates the modal in-place — no page reload, no ViewState, instant feedback.

ℹ Session Requirement: The support_send.ashx handler implements IRequiresSessionState so it can check Session["IdashSiteAccess"] to verify the user is authenticated. Without this interface, ASP.NET handlers don’t have access to session state.

📁 Developer Reference — File Map

FileRole
index.aspx Modal UI & JavaScript. Contains the modal overlay HTML (plain HTML inputs, not asp:TextBox server controls), CSS styles, and the sendSupportRequest() JavaScript function that validates fields and calls fetch(). The subject is auto-populated server-side via <%= GetSiteLabel() %>.

support_send.ashx AJAX endpoint. Lightweight HTTP handler that receives the form POST, validates inputs server-side, builds the HTML email body, and calls EmailHelper.SendDirectEmail(). Returns JSON: {"ok":true} on success or {"ok":false,"error":"..."} on failure. Implements IRequiresSessionState for authentication checks.
App_Code/EmailHelper.cs Shared SMTP engine. The SendDirectEmail() method uses the identical SMTP client setup as SendEmail() (used by ENNX reports). Reads SMTP_* settings from web.config, configures SSL/credentials, and sends with a 15-second timeout to prevent indefinite hangs.

🔌 Developer Reference — EmailHelper.SendDirectEmail()

Added to App_Code/EmailHelper.cs to support sending emails to arbitrary addresses (not just the ENNX recipient list). Uses the exact same SMTP setup as the existing SendEmail() method.

Method Signature

public static void SendDirectEmail( string toAddress, // Primary recipient email string toName, // Primary recipient display name string ccAddress, // CC recipient email (can be empty) string ccName, // CC recipient display name string replyTo, // Reply-To email (can be empty) string replyToName, // Reply-To display name string subject, // Email subject line string body, // HTML email body string fromDisplayName // From display name (default: "iDash") )

Key Behaviors

  • Timeout: 15-second hard limit via SmtpClient.Timeout. Prevents indefinite hangs when firewalls silently drop TCP connections.
  • SSL: Enabled only when SMTP_User and SMTP_Password are both non-empty. This automatically handles both Office 365 (SSL + credentials) and internal VA relays (no SSL, no credentials).
  • From address: Always uses SMTP_FromEmail from web.config. The fromDisplayName parameter only sets the display name, not the email address.
  • Reusable: Can be used by any future feature that needs to send email to a specific address (not the ENNX recipient list). Just call EmailHelper.SendDirectEmail(...).

🚧 Troubleshooting

SymptomCauseFix
“Network error: Unexpected token” The .ashx handler returned an HTML error page instead of JSON. Usually a compilation error in the handler or a missing dependency. Open /iDash/support_send.ashx directly in a browser to see the full ASP.NET error page. Fix the compilation error and recycle the app.
“Not authenticated” Session expired or the handler can’t access session state. Verify IRequiresSessionState is implemented on the handler class. Refresh the page and log in again.
“Failed to send via smtp.office365.com” SMTP credentials invalid, or the VA firewall is blocking outbound port 587. Check Site Configuration SMTP settings. For VA servers, use the internal relay (port 25, no creds).
Button stays on “Sending…” for 15+ seconds SMTP timeout (15s). Firewall silently dropping TCP connection. Verify SMTP connectivity: Test-NetConnection smtp.office365.com -Port 587 from PowerShell on the server.
ENNX reports send but Support Request doesn’t Should not happen after v2.0 — both use the same EmailHelper code path. If it does, check browser DevTools console for JavaScript errors. Open DevTools (F12) → Network tab, click Send, and inspect the support_send.ashx request/response.

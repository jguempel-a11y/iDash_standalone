1. Overview: The "Cherry-Picking" Trap vs. Full Site Sync

When updating remote iDash instances (such as biomedical carts, field laptops, or secondary staging nodes), engineers often attempt to copy only the 2 or 3 files they recently edited (e.g. va_asset_master.aspx or va_inventory.aspx). In practice, this cherry-picking approach consistently causes environment drift and failures:

  • Dashboard & Navigation Disconnect: If index.aspx on the target machine is not updated, it will still show deprecated tiles (e.g. the old standalone Printer Administration tile) or point to pages that have been relocated into unified hubs (e.g. Site Configuration).
  • Missing Dependency DLLs: Modern reporting features depend on updated binaries in bin/ (e.g. ClosedXML.dll replacing EPPlus.dll). If code-behinds reference new namespaces but the remote bin/ was not synced, pages fail on compilation with CS0246.
  • Missing Supporting Gateway Pages: Specialized navigation hubs like va_alerts.aspx or va_notifications.aspx will return HTTP 404 (The resource cannot be found) if their corresponding code-behind and template files are missing.
✅ The Solution: Full-Site Baseline Synchronization.
Instead of manual cherry-picking, package the entire web application and deploy it as a unified baseline. By establishing a Safe Migration Boundary, you achieve 100% identical UI tiles, navigation, and features on the target machine without touching the target's SQL database, connection strings, or user accounts.

2. The Safe Migration Boundary: What Gets Synced vs. Kept

A successful replication replaces the software layer while preserving the remote machine's local identity and database connection. The table below specifies exactly what travels and what remains untouched:

Component / Directory Action Rationale & Protection Rule
Root Web Pages (*.aspx, *.aspx.cs) 🔃 OVERWRITE Ensures index.aspx, va_asset_master.aspx, va_site_config.aspx, and va_alerts.aspx match localhost 1:1.
Compiled Binaries (bin/*.dll) 🔃 OVERWRITE Deploys ClosedXML.dll, DocumentFormat.OpenXml.dll, and memory stream libraries.
Application Code (App_Code/*.cs) 🔃 OVERWRITE Synchronizes UserManager.cs, LoginAuditHelper.cs, and facility multi-tenant boundary filters.
API Endpoints (api/*.ashx) 🔃 OVERWRITE Deploys LiveScanHandler.ashx, v_asset.ashx, and fail-closed security guards on va_remote_import.ashx.
User Controls & Assets (controls/, Assets/) 🔃 OVERWRITE Synchronizes top-bar user menus, branding logos, RFID icons, and typography.
Documentation Suite (documentation/*) 🔃 OVERWRITE Provides updated technical manuals, third-party SBOMs, and compliance standards directly on the target machine.
Styling & Scripts (theme.css, theme-init.js) 🔃 OVERWRITE Ensures dark/light theme switching, button states, and CSS variables match.
web.config 🔒 PRESERVE / KEEP CRITICAL: Contains the remote machine's local SQL Server instance name (e.g. .\SQLEXPRESS) and connection strings. Do NOT overwrite.
App_Data/ 🔒 PRESERVE / KEEP Preserves local user logins (idash_users.json) and site database seed files.
downloads/ 🔒 PRESERVE / KEEP Excludes large archive payloads (1.4+ GB) to keep migration packages compact (≤ 140 MB).
logs/ & uploads/ 🔒 PRESERVE / KEEP Preserves active operator audit logs and incoming customer file drops.

3. Method A: 1-Click Over-the-Air (OTA) Web Update (Recommended — Zero Scripts)

This is the primary, zero-command-line update method. It executes directly inside the web browser on the target machine with a live glassmorphic progress overlay, real-time download and file extraction tickers, IIS AppPool recycling, and automatic Safe Migration Boundary protection.

⚠️ One-Time Bootstrap Requirement for Older Systems:
Older field laptops or secondary servers that do not yet have va_system_update.aspx and va_system_update.aspx.cs must be seeded with these two files once. You can copy them over via Windows file sharing (\\<target-laptop>\c$\inetpub\wwwroot\AssetWorx.WebClient\iDash\), via USB drive, or by running the initial PowerShell sync script once.
Once va_system_update.aspx is in place, all future updates and releases can be applied 100% via the web interface with 1-click!

1 Package the Latest Master Baseline

On your master development workstation (localhost / LingCod), run the package builder in Administrator PowerShell:

& "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\tools\Build-IdashMigrationPackage.ps1"

This generates the clean, compressed baseline archive (idash_full_site.zip, ~85 MB) and publishes it automatically to /iDash/downloads/idash_full_site.zip.

2 Open System Update & Deployment on the Remote Machine

Open your browser and navigate to the remote system's update page:

🚀 Open System Update & Deploy Tool → (https://laptop-e74ckmo5.tail2fc4c5.ts.net/idash/va_system_update.aspx)

Alternative navigation: On the remote machine's dashboard (index.aspx), log in under AssetWorx SQL Administrator, then click the green 🚀 System Update & Deploy (1-Click OTA) tile under Admin Tools.

3 Select Your Update Source

Choose where the remote system should pull its update from:

  • Master Node (LingCod Tailscale): https://lingcod.tail585c9b.ts.net/iDash/downloads/idash_full_site.zip — Direct P2P sync across your secure Tailscale mesh.
  • GitHub Official Release: https://github.com/jguempel-a11y/iDash/releases/latest/download/idash_full_site.zip — Ideal fallback if the master development workstation is offline.
  • GitHub Main Branch Zip: https://github.com/jguempel-a11y/iDash/archive/refs/heads/main.zip — Direct snapshot of the latest Git commits.
  • Custom Package URL: Point to any internal staging server or cloud bucket.

4 Click "Start System Update Now" & Monitor Live Progress

Click the green Start System Update Now button. The interactive glassmorphic modal overlay will automatically engage:

  • Live Percentage & Speed Bar: Shows download progress (e.g. 42.5 MB / 85.6 MB • 50%).
  • Unpacking Verification: Unpacks the clean archive safely into an isolated scratch directory.
  • File Copy Ticker: Displays every active file being synchronized (e.g. Deploying: va_inventory.aspx (480 of 975)).
  • Zero Downtime IIS Refresh: Recycles the IIS Application Pool automatically so new code and assemblies load immediately.
  • Anti-Refresh Protection: Built-in browser protection prompts if the tab is accidentally refreshed or closed during an update.
✅ Update Complete: Upon reaching 100%, the completion banner confirms the exact number of synchronized files and initiates a 5-second countdown timer redirecting you back to the updated dashboard.

4. Method B: Automated Push via Tailscale & Web SQL Uploader (Secondary Automated Method)

This automated method leverages SQL Server xp_cmdshell to execute the update when web-based updates are restricted or when executing headless migrations:

1 Build the Clean Migration Package on Localhost

On your local development machine (localhost / LingCod), open Windows PowerShell (Run as Administrator) and run the built-in migration builder script:

💡 Recommended (Best Way): Run this single command in PowerShell. It automatically stages all 1,200+ application files, strictly preserves the Safe Migration Boundary, and generates the compressed package in seconds with zero risk of syntax errors:
& "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\tools\Build-IdashMigrationPackage.ps1"

Expected Output in PowerShell:

========================================================== iDash Full-Site Migration Package Builder ========================================================== [1/3] Staging application files (enforcing Safe Migration Boundary)... Staged 1229 files successfully. [2/3] Compressing into migration archive: C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\downloads\idash_full_site.zip... [3/3] Migration package created successfully: 142.59 MB
Alternative: Run raw PowerShell inline (click to expand)

If you cannot run scripts due to execution policies, paste this single continuous command (semicolon-separated to prevent line-flattening errors):

$zipPath = "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\downloads\idash_full_site.zip"; $tempStage = "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\scratch\stage_full_site"; if (Test-Path $zipPath) { Remove-Item $zipPath -Force }; if (Test-Path $tempStage) { Remove-Item $tempStage -Recurse -Force }; New-Item -ItemType Directory -Path $tempStage | Out-Null; robocopy "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash" $tempStage /E /XD ".git" "scratch" "downloads" "App_Data" "logs" "uploads" "temp" /XF "web.config" "*.log" | Out-Null; Add-Type -AssemblyName System.IO.Compression.FileSystem; [System.IO.Compression.ZipFile]::CreateFromDirectory($tempStage, $zipPath); Remove-Item $tempStage -Recurse -Force; $mb = [math]::Round((Get-Item $zipPath).Length / 1MB, 2); Write-Host "Migration package ready: $zipPath ($mb MB)" -ForegroundColor Green

2 Verify the Download Endpoint

Because the ZIP file is stored in iDash\downloads\, it is immediately downloadable over IIS or Tailscale Funnel. You can test it locally via curl:

curl.exe -k -I https://lingcod.tail585c9b.ts.net/iDash/downloads/idash_full_site.zip # Verify that it returns: HTTP/1.1 200 OK with Content-Type: application/x-zip-compressed

Reference: Complete Migration SQL Code

For reference or audit inspection, here is the exact script executed by Step 3:

-- 1. Enable xp_cmdshell for the duration of the transfer EXEC sp_configure 'show advanced options', 1; RECONFIGURE; EXEC sp_configure 'xp_cmdshell', 1; RECONFIGURE; -- 2. Download, extract, and copy over the web root CREATE TABLE #p (line NVARCHAR(MAX)); INSERT INTO #p EXEC xp_cmdshell 'powershell.exe -ExecutionPolicy Bypass -Command "[System.Net.ServicePointManager]::ServerCertificateValidationCallback = {$true}; [Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12; $z = ''C:/Windows/Temp/idash_full_site.zip''; (New-Object Net.WebClient).DownloadFile(''https://lingcod.tail585c9b.ts.net/iDash/downloads/idash_full_site.zip'', $z); Add-Type -AssemblyName System.IO.Compression.FileSystem; $t = ''C:/Windows/Temp/stage_full_site''; if (Test-Path $t) { Remove-Item $t -Recurse -Force }; [System.IO.Compression.ZipFile]::ExtractToDirectory($z, $t); Copy-Item -Path ''C:/Windows/Temp/stage_full_site/*'' -Destination ''C:/inetpub/wwwroot/AssetWorx.WebClient/iDash'' -Recurse -Force; Copy-Item -Path ''C:/Windows/Temp/stage_full_site/*'' -Destination ''C:/inetpub/wwwroot/idash'' -Recurse -Force; (Get-Item ''C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\web.config'').LastWriteTime = Get-Date; Remove-Item $t -Recurse -Force; Remove-Item $z -Force; Write-Output ''FULL_SITE_MIGRATION_COMPLETE_SUCCESS'';"'; -- 3. Recycle the IIS App Pool to clear ASP.NET VirtualPath cache INSERT INTO #p EXEC xp_cmdshell '%windir%\system32\inetsrv\appcmd.exe recycle apppool "DefaultAppPool"'; -- 4. Re-lock SQL Server security immediately EXEC sp_configure 'xp_cmdshell', 0; RECONFIGURE; EXEC sp_configure 'show advanced options', 0; RECONFIGURE; -- 5. Review results SELECT line AS MigrationResult FROM #p WHERE line IS NOT NULL; DROP TABLE #p;
📷 Figure 1: Running the automated migration and security lockdown through va_sql_upload.aspx.
🔒 Security Assurance: Step 4 explicitly restores xp_cmdshell = 0 within the same SQL transaction batch, ensuring SQL Server remains locked down in compliance with NIST SP 800-53 (AC-3 / SC-7).

5. Method C: Direct Manual Copy & PowerShell Robocopy Script

If you prefer not to use web-based updaters or SQL scripts, you can deploy files directly using the generated PowerShell robocopy script or a USB drive / Windows file sharing (\\<remote-host>\c$). Follow these exact steps:

1 Package the Local Workstation

On your local development machine, run the builder script in Administrator PowerShell to produce the clean baseline ZIP:

& "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\tools\Build-IdashMigrationPackage.ps1"

Copy the resulting file (C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\downloads\idash_full_site.zip) onto your USB thumb drive or network drop folder.

2 Copy and Extract on the Remote Target

  1. On the target laptop or server, extract idash_full_site.zip into a temporary directory (e.g. C:\temp\stage\).
  2. Copy all contents from C:\temp\stage\ and paste them into:
    C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\
  3. When prompted by Windows Explorer: Click “Replace the files in the destination”.
    Note: Because web.config was excluded from the ZIP, your database credentials remain completely safe.
  4. If a separate virtual directory exists at C:\inetpub\wwwroot\idash\, copy the files there as well.

3 Set NTFS Permissions

When files are copied from external drives or temporary folders, Windows may assign restrictive access control lists. Open an Administrator PowerShell on the target and run:

icacls "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash" /grant "IIS_IUSRS:(OI)(CI)RX" /grant "Users:(OI)(CI)RX" /T

4 Recycle the IIS Application Pool

Force IIS to invalidate compiled page caches and reload the fresh baseline:

# In elevated PowerShell or Command Prompt & "$env:windir\system32\inetsrv\appcmd.exe" recycle apppool "DefaultAppPool"

7. Troubleshooting & Common Pitfalls

⚠ Pitfall 1: Virtual Directory Path Mismatch (/idash vs /AssetWorx.WebClient/iDash)

On some field systems, IIS contains two applications or virtual directories: one at /idash and another at /AssetWorx.WebClient/iDash. If /idash was pointed to an empty directory (e.g. C:\inetpub\wwwroot\idash), new pages will return HTTP 404 (The file does not exist) even though they exist on disk.

Fix: Re-align the virtual directory physical path using appcmd:

& "$env:windir\system32\inetsrv\appcmd.exe" set vdir "Default Web Site/idash" -physicalPath:"C:\inetpub\wwwroot\AssetWorx.WebClient\iDash"

⚠ Pitfall 2: ASP.NET VirtualPath Cache Stale (HTTP 404 on newly added pages)

ASP.NET caches its virtual directory structure in temporary compilation files. When new .aspx files are copied in, the runtime might not immediately detect them.

Fix: Touch web.config to force an application pool recycle:

(Get-Item "C:\inetpub\wwwroot\AssetWorx.WebClient\iDash\web.config").LastWriteTime = Get-Date

⚠ Pitfall 3: Missing Code-Behind in Web Site Projects

In ASP.NET Web Site projects, every template page that uses server-side logic must have a matching .aspx.cs file declaring public partial class <name> : Page. Pages defined purely inline without a code-behind can fail with CheckVirtualFileExists exceptions under strict IIS configurations.

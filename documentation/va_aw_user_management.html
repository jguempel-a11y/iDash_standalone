This page provides a self-contained interface inside iDash for creating, editing, and deleting scanner & system user accounts — the sysuser records that control who can log in to the iDash web application at http://localhost.

This is the easiest tool for managing RFID scanner login credentials and permissions. Use it to add, remove, or edit the username, password, user type, and site assignment for any handheld RFID scanner operator — without needing to open the iDash web UI.

This is separate from iDash User Management. iDash users (stored in App_Data/idash_users.json) control portal access to iDash itself. scanner users (stored in dbo.sysuser) control who can log in to the main iDash application, the mobile handheld client, and the API.
⚠ Do NOT sign in to this page as superadmin or admin. Those are scanner user accounts created for internal UI functions — they are not SQL Server credentials and will not work here. Sign in with idashadmin, which is the standard SQL Server account used for database management operations.

📱 Primary Use Case: RFID Scanner User Management

The most common use of this page is managing login credentials for RFID handheld scanners. Each scanner operator needs a sysuser account with:

  • Username & Password — what the operator types on the scanner login screen
  • User Type — "Create, Edit, Delete" for field techs who tag and scan, or "View Only" for observers
  • Company (Site) — which VA medical center the operator is assigned to
  • Restrict Edit on Mobile toggle — prevents the operator from modifying asset records on the handheld
  • Inventory Limited User toggle — restricts the operator to limited inventory functions

Instead of navigating to http://localhost, logging in as admin, and using the iDash UI, you can do all of this directly from iDash in seconds.

Why This Was Built

The Problem

Creating an scanner user account previously required:

  1. Navigating to http://localhost (the iDash web application)
  2. Logging in with an existing admin account
  3. Using the built-in scanner user management interface

This was problematic for several reasons:

  • Network dependency: The iDash web application runs on a .NET Core pipeline that requires the full iDash application stack to be running — including license checks, Redis/local cache, MQTT workers, and various background services. If any of these are down or misconfigured, the UI is inaccessible.
  • No standalone access: You cannot create the first admin user without an already-working admin user. If the default admin/admin account is locked or its password has been changed, there’s no UI-based recovery path short of direct SQL manipulation.
  • Operational friction: During site deployments, field installations, and break-fix scenarios, having to start the full iDash application just to add or modify a user account is unnecessary overhead. The iDash portal is already running and authenticated.

The Solution

The new Scanner & System User Management page in iDash provides direct SQL access to the dbo.sysuser table. It bypasses the iDash .NET Core application entirely and writes directly to the database using the same parameterized SQL patterns used throughout iDash. This means:

  • Users can be created even when the iDash web application is offline
  • Password hashing is performed using a binary-compatible implementation of the ASP.NET Core Identity PasswordHasher V3 algorithm (see Password Hashing section)
  • All 17 columns of the sysuser table are exposed as form fields, including the toggle options that control mobile restrictions and inventory limitations

How It Works

The page operates in a two-phase workflow:

Phase 1: Connect

  1. Administrator enters SQL Server credentials (server, database, username, password)
  2. Fields are pre-populated from web.config using the existing iDash connection string, so in most cases only the password needs to be entered
  3. On connect, the page validates the connection and confirms the dbo.sysuser table exists
  4. The connection string is stored in the ASP.NET session (memory-only, never persisted to disk)

Phase 2: Manage

  1. Once connected, all existing sysuser records are displayed in a data grid
  2. The grid joins sysuser with dbo.company to display the human-readable site name alongside each user’s companyid
  3. The Add User modal and Edit User modal expose every writable column
  4. All SQL operations use parameterized queries (@param style) — no string concatenation
Session-scoped connection. The database connection credentials are held in the ASP.NET session only. They are not written to any file. Closing the browser or session timeout clears them. The "Disconnect" button explicitly removes the stored connection.

Why user-supplied credentials instead of just using web.config?

This is intentional. The page is designed to work against any iDash database, not just the one in web.config. During multi-site deployments, a technician may need to manage users on a different SQL instance. The pre-population from web.config is a convenience for the default case.

Password Hashing — ASP.NET Core Identity V3 Compatibility

Critical implementation detail. iDash runs on ASP.NET Core and uses Microsoft.AspNetCore.Identity.PasswordHasher<T> to hash passwords. iDash runs on classic ASP.NET Framework 4.8. Rather than reference .NET Core DLLs from .NET Framework code (fragile cross-framework reference), we implemented a binary-compatible password hasher from scratch.

The Binary Format

ASP.NET Core Identity V3 passwords are stored as base64-encoded byte arrays with this structure:

OffsetLengthValueDescription
01 byte0x01Format marker (V3)
14 bytes0x00000001PRF algorithm (HMACSHA256 = 1)
54 bytes0x00002710Iteration count (10,000)
94 bytes0x00000010Salt length (16 bytes)
1316 bytes(random)Cryptographic salt
2932 bytes(derived)PBKDF2-derived subkey

Total: 61 bytes → base64-encoded = 84 characters, always starting with AQAAAA.

Our Implementation

// Using .NET Framework 4.8's Rfc2898DeriveBytes with SHA256
private static string HashPasswordV3(string password)
{
    const int SaltSize   = 16;   // 128-bit
    const int SubkeySize = 32;   // 256-bit
    const int Iterations = 10000;

    byte[] salt = new byte[SaltSize];
    using (var rng = RandomNumberGenerator.Create()) { rng.GetBytes(salt); }

    byte[] subkey;
    using (var kdf = new Rfc2898DeriveBytes(password, salt, Iterations,
                                             HashAlgorithmName.SHA256))
    {
        subkey = kdf.GetBytes(SubkeySize);
    }

    // Build output: marker(1) + prf(4) + iter(4) + saltLen(4) + salt + subkey
    byte[] output = new byte[1 + 4 + 4 + 4 + SaltSize + SubkeySize];
    output[0] = 0x01;  // V3 format marker

    WriteNetworkByteOrder(output, 1, 1);           // PRF = HMACSHA256
    WriteNetworkByteOrder(output, 5, Iterations);  // 10000
    WriteNetworkByteOrder(output, 9, SaltSize);    // 16

    System.Buffer.BlockCopy(salt,   0, output, 13, SaltSize);
    System.Buffer.BlockCopy(subkey, 0, output, 13 + SaltSize, SubkeySize);

    return Convert.ToBase64String(output);
}

Why this matches what iDash expects

The ASP.NET Core source code for PasswordHasher<T>.HashPassword() uses the same algorithm:

  • Same format marker byte (0x01 for V3)
  • Same PRF (HMACSHA256, enum value 1)
  • Same default iteration count (10,000 for .NET Core 2.x/3.x; 100,000 for .NET 6+)
  • Same salt size (128-bit) and subkey size (256-bit)
  • Same big-endian (network byte order) encoding for the header integers

When iDash calls PasswordHasher.VerifyHashedPassword(), it reads the format header from the stored hash to determine the PRF, iteration count, and salt length, then re-derives the subkey and compares. Because our header values match, the verification succeeds.

Note on iteration count: The existing iDash passwords on this server use 10,000 iterations (the .NET Core 2.x default). Our implementation matches this. If iDash is ever upgraded to a version using 100,000 iterations (the .NET 6+ default), the existing passwords created by iDash will still verify correctly because the iteration count is embedded in each password hash. New passwords created by iDash would just use the higher count.

Creating, Editing & Deleting Users

Create User

  1. Click “+ Add scanner user” button
  2. Fill in the form fields. Only Username is strictly required. Password is optional (can be set later via iDash or via Edit).
  3. Select a User Type (“Create, Edit, Delete” for full access, “View Only” for read-only)
  4. Select a Company (Site) from the dropdown, or “None” for a super admin account
  5. Toggle any options: Hide Admin Popups, Inventory Limited User, Restrict Edit on Mobile
  6. Click “Create User”

The SQL executed is:

INSERT INTO dbo.sysuser
    (username, password, firstname, lastname, email, phone, cardid, rfidtag,
     usertype, companyid, hideadminpopups, inventorylimiteduser, restricteditmobile)
VALUES
    (@username, @password, @firstname, @lastname, @email, @phone, @cardid, @rfidtag,
     @usertype, @companyid, @hidePopups, @invLimited, @restrictMobile)

Uniqueness is enforced before insert:

SELECT COUNT(*) FROM dbo.sysuser WHERE username = @u

Edit User

  • Click the Edit button on any row in the grid
  • The modal pre-populates all current values
  • Password field is blank — leaving it blank preserves the existing password. Entering a new password overwrites it with a freshly hashed value.
  • Username cannot be changed after creation (it’s the login identity)

The update uses a conditional SQL statement — if a new password is provided, the password column is included in the UPDATE. If not, it’s excluded entirely to avoid overwriting the existing hash with NULL.

Delete User

  • Click the Delete button on any row
  • A JavaScript confirm() dialog prompts for confirmation
  • The delete executes: DELETE FROM dbo.sysuser WHERE id = @id
Warning: Deleting a user from the sysuser table is permanent. There is no soft-delete or recycle bin. The user will immediately lose the ability to log in to iDash.

Security & Access Control

Access Gate

The page uses the same access gate as va_user_management.aspx:

bool isAdmin = Session[SESSION_AUTH] != null &&
               (bool)Session[SESSION_AUTH] &&
               (((string)Session[SESSION_ROLE] == UserManager.ROLE_ADMIN) || hasTileAccess);

Only iDash administrators or users with the admin_users tile permission can access the page. Non-authorized users see an “Access Restricted” screen.

SQL Injection Prevention

All database operations use parameterized queries exclusively. User input is never concatenated into SQL strings.

cmd.Parameters.AddWithValue("@username", username);
cmd.Parameters.AddWithValue("@password", (object)hashedPw ?? DBNull.Value);
// ... all fields use parameters
